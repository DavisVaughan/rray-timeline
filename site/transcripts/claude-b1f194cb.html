17	//
18	// - Cast `y` through `int64_t` to keep its sign, then add to `lo` as an
19	//   unsigned value. The low part wraps at 2^64.
20	// - Add -1 to `hi` when `y` is negative, then add 1 if `lo` wrapped.
21	//

23	// The upper part becomes `0 - 1 + 1 = 0`, so the sum is 0.

26	  const int64_t hi = x.hi + (y < 0 ? -1 : 0) + (lo < x.lo);

What collapses

  • Switch and wrappers. rray_mean_switch() loses its na_rm ? a : b ternaries. The two lgl wrappers become one, and so do the two int wrappers. Same for the two forced-fallback test hooks, as in sum.

  • Double path. rray_mean_dbl() and rray_mean_dbl_na_rm() become one function. The sum pass and the correction pass each get an if (na_rm) { ... } else { ... }, like rray_sum_dbl(). The counts buffer is only allocated when na_rm is true. The divisor becomes na_rm ? v_counts[i] : count.

The one real design choice

The two int paths track NA differently today:

  • Int64 path: sets one any_missing flag for the whole array. If it ends up true, a second pass over x (rray_mean_lgl_or_int_propagate_na()) writes the NAs.

  • Int128 fallback: keeps a per-slot v_missings buffer, like sum.

I'd switch the int64 path to v_missings. Then mean's int code matches sum's line for line, and the propagate helper is deleted. The cost is one extra 1-byte read and write per element when the output is strided (reducing along a non-leading axis), even when there are no NAs. The current design avoids that cost. Sum already pays it, so I'd benchmark against main before committing to it.

A more radical option

Always track per-slot counts, in both modes. The walk is then the same loop for both: sum += na ? 0 : x; count += !na. Only the final step branches:

if (na_rm) {
  v_out[i] = rray_mean_int64(v_sums[i], v_counts[i]);
} else {
  v_out[i] = v_counts[i] == count ? rray_mean_int64(v_sums[i], count) : na_dbl;
}

That removes the if/else from every hot int loop, and the same trick would work for sum. The downside is in the strided case without na_rm: an 8-byte count per output slot instead of a 1-byte flag, so per-slot memory goes from 9 bytes to 16. It's more elegant, but I'd only pick it if a benchmark shows the cost is small. It also moves away from what sum just shipped, unless we change sum too.

Yes. v_missings is only used when na_rm = FALSE. It's allocated in the else branch, and v_counts is allocated when na_rm = TRUE:

if (na_rm) {
  r_obj* counts = KEEP_N(r_alloc_raw0(out_size * sizeof(r_ssize)), &n_prot);
  v_counts = (r_ssize*) r_raw_begin(counts);
} else {
  r_obj* missings = KEEP_N(r_alloc_raw0(out_size * sizeof(bool)), &n_prot);
  v_missings = (bool*) r_raw_begin(missings);
}

The two modes need different things per output slot:

  • na_rm = FALSE: the divisor is the same for every slot (count). The only per-slot question is whether any NA was seen, so a 1-byte flag is enough. At the end: v_missings[i] ? na_dbl : rray_mean_int64(v_sums[i], count).

  • na_rm = TRUE: NAs are skipped, so each slot needs its own divisor: rray_mean_int64(v_sums[i], v_counts[i]).

This is also why only the na_rm = FALSE case got slower along axis 2 with no NAs. Main tracked one any_missing flag for the whole array. The branch writes a per-slot flag, which costs an extra read and write per element when the output is strided. In the na_rm = TRUE case, main already wrote per-slot counts, so nothing changed there.

Integer sum (rray_sum_lgl_or_int() and rray_sum_int_fallback()) uses the same split, and so did mean's int128 fallback on main.

So on your Mac, base mean() returns NA or NaN depending on argument order.

The docs say this is allowed:

  • ?NaN (src/library/base/man/is.finite.Rd): "Computations involving NaN will return NaN or perhaps NA: which of those two is not guaranteed and may depend on the R platform (since compilers may re-order computations)."

  • ?NA (src/library/base/man/NA.Rd): "a possible exception is where NaN is also involved, in which case either might result (which may depend on the R platform). However, this is not guaranteed and future CPUs and/or compilers may behave differently."

  • ?mean (mean.Rd) says nothing about NA vs NaN, so those general rules are all you get.

The C code shows why. real_mean() in src/main/summary.c:479 just adds the values into a LDOUBLE and divides. It never checks for NA specifically, so the hardware decides which value comes through.

## Array API Standard `take()` Function

The `indices` parameter for the `take()` function must be one-dimensional and have an integer data type.

### What the Function Does

The `take()` function returns elements of an array along an axis. The output array must have the same rank (i.e., number of dimensions) as the input array and must have the same shape as the input array, except for the axis specified by axis whose size must equal the number of elements in indices.

### Rationale

While the search results I found show the technical specification for the `take()` function, they do not contain an explicit statement of the rationale for why indices must specifically be one-dimensional. However, the documentation does indicate that explicit indexing via arrays of indices is not currently supported in this specification due to concerns regarding `__setitem__` and array mutation semantics. This design constraint appears to influence the simpler one-dimensional indices requirement.

If you need the full rationale behind this design decision, you may want to consult the Array API Standard's GitHub repository or design documentation directly, as this detailed reasoning doesn't appear in the public-facing API specification pages.

# Summary of PR #416: Adding `take()` Specification

## Restriction to 1-D Indices

The PR restricted the `indices` parameter to one-dimensional arrays following consensus reached at the Consortium meeting on September 22, 2022. The contributor noted that "for now, the API will not support multi-dimensional arrays for the `indices` kwarg. In the interim, array API consumers should be able to use `reshape` to achieve something similar."

## Required `axis` Parameter for N-D Input

The specification mandates the `axis` argument only when input arrays exceed one dimension. This design balances practical usage patterns with backward compatibility. Analysis of scikit-learn's codebase showed that most `np.take()` calls involved 1-D inputs, where `axis` becomes unnecessary. One reviewer observed this makes sense since "arr[index] is practically identical" for 1-D cases.

## Out-of-Bounds and Mode Behavior

The PR left mode and boundary handling unspecified, deferring these details. The conservative approach focused on establishing core functionality first, allowing libraries flexibility in implementation details.

## Exclusion of NumPy's N-D Index Behavior

NumPy's traditional flattening behavior—where multi-dimensional indices flatten the input array—was explicitly excluded. PyTorch's current behavior performs this flattening by default, but the standard requires explicit `axis` specification instead, ensuring clearer, more predictable semantics across implementations.

# Summary of RFC #177: Array Indexing APIs

## Proposal
Add `take`, `put`, `take_along_axis`, and `put_along_axis` functions to the array API specification for extracting and setting elements via index lists.

## Key Motivations

**1. Fancy Indexing Gap**
The specification lacks direct support for "providing a list of indices to index into an array." While full fancy indexing was avoided due to dynamic shape concerns with accelerator libraries, basic indexed access remains useful.

**2. API Output Consumption**
Several existing functions return indices that cannot be readily consumed without workarounds:
- `argsort` returns index arrays
- `unique` (with `return_index=True`) returns indices

These outputs are naturally consumed by `take_along_axis` and `put_along_axis` in NumPy.

## Library Implementation Landscape

The table reveals significant variation:
- **`take`**: Implemented across NumPy, CuPy, Dask, MXNet, PyTorch, and TensorFlow
- **`put`**: Only NumPy and CuPy provide this
- **`take_along_axis`/`put_along_axis`**: Primarily NumPy and CuPy; TensorFlow uses `gather_nd` instead

Most libraries implement some indexing mechanism, though naming and semantics vary considerably (torch uses `gather`, TensorFlow uses `gather`/`gather_nd`).

Short answer: it was not a "can't", it was a "not yet". The consortium restricted indices to 1-D by consensus when take() was first specified (PR #416, decided at the 2022-09-22 meeting), with the explicit note that consumers could use reshape() in the interim. It is still 1-D in the 2025.12 spec.

The reasons behind that consensus:

The N-D shape rule is strange. NumPy's take produces x.shape[:axis] + indices.shape + x.shape[axis+1:]. It splices an entire shape into the middle of another shape. Nothing else in the standard has a rule like that, and it is hard to state without just pointing at NumPy.

Backend support is uneven at N-D but uniform at 1-D. torch.index_select() requires a 1-D index tensor. torch.take() only works on the flattened array. tf.gather() is closer to NumPy. 1-D indices plus an explicit axis is exactly the intersection everyone already implements, so the spec picked that.

The usage evidence was thin. A survey of scikit-learn found most np.take() calls were on 1-D input, where axis is not even needed and x[idx] is equivalent.

Minimalism is the standard's default posture. Adding later is easy, removing is not. The same instinct dropped NumPy's axis=None flatten-first default (the spec requires axis for N-D input) and dropped mode=, leaving out-of-bounds behavior unspecified because bounds checking is expensive on accelerators.

Worth separating two things that get conflated: general fancy indexing was left out of the standard for a different reason, namely data-dependent output shapes (boolean masks) and NumPy's advanced-indexing edge cases, like the rule where index arrays separated by a slice move the broadcast dimensions to the front. take() with 1-D indices sidesteps all of that.

The N-D need did get addressed, just not by overloading take. take_along_axis() landed in 2024.12 for the case where indices has the same rank as x, which is what you actually want for consuming argsort() output. And RFC #669 (shoyer, 2023) proposes real multi-dimensional integer array indexing as its own feature, designed to avoid NumPy's edge cases rather than inherit them. It has not landed.

For rray4 that split is probably the interesting part: take(x, indices, axis) and take_along_axis(x, indices, axis) are two genuinely different operations, and NumPy only merges them by accident of the N-D shape rule.

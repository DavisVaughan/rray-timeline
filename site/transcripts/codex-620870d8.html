// up the subspace. So as you walk the output's point space you can create

Clarifying zero-dimensional iteration handling

Detailing axes semantics and special cases

No, I would not ban integer(). And yes, reducing over all axes still needs this case.

There are two symmetric paths in reduce.c:

  • axes = integer() makes the inner plan empty. Each value is reduced by itself.
  • axes = seq_len(dimensionality) makes retained_axes empty. The outer plan must run exactly once for the single result.

So banning empty user axes would only remove the first path. Reducing over all axes would still reach the special case through retained_axes.

This is more about the iterator than rray lacking 0D arrays. A zero-axis iteration space contains one point, but the iterator requires a first axis for its run size. The synthetic dimension [1] with stride [0] in reduce.c represents that one point.

I think integer() has useful, composable semantics: reduce over no axes. I would keep it. If the special case feels too implicit, a named scalar or unit iterator-plan constructor could make the intent clearer.

Evaluating dimensionality coalescing strategies

It needs one explicit normalization. The size falls out of the math, but the run representation does not.

rray_size_from_dimensions(..., 0) correctly returns 1. However, the iterator models every traversal as runs along a first axis. A zero-axis space has one point but no first axis, so there is no dimension or stride for the accessors to read.

The cleanest approach is to normalize it once in each iterator constructor:

plan.size = rray_size_from_dimensions(v_dimensions, dimensionality);

if (dimensionality == 0) {
  plan.v_dimensions[0] = 1;
  plan.v_strides[0] = 0;
  plan.dimensionality = 1;
  return plan;
}

For rray_strided_iterator2_plan(), initialize both first strides to zero.

Then rray_reduce_axes_plan() can lose its special case entirely. It just builds the selected dimensions and passes axes_size, including zero, to the constructor.

Trying to make it “fall out” completely would require changing the iterator representation so run size and run stride are separate from the axes. That is a much larger change. With the current first-axis run design, a small constructor special case is the clean and honest solution. It also keeps zero-dimensional checks out of the hot iteration loops.

Analyzing zero-axis iterator use cases

Evaluating zero-dimensional operation feasibility

In the current code, only nested reduction can produce a zero-axis iterator plan.

Other apparent cases do not currently reach the iterator that way:

  • split() can have an empty axis set or complement, but it turns those into full-dimensional shapes containing dimensions of 1.
  • squeeze() explicitly rejects removing every axis.
  • permute() always uses every axis.
  • Broadcasting and binary operations iterate over full array dimensions, which must contain at least one dimension.

It could appear later in any operation that divides axes into two iterator spaces:

  • Other nested reductions, such as variance, min, max, or quantiles.
  • Contractions, dot products, or matrix multiplication. Either the contracted axes or the retained axes can be empty.
  • Axis-based matching, grouping, or sorting.
  • Supporting actual 0D arrays in the future.
  • Refactoring split() to iterate directly over selected and retained axis subsets.

So reduction is the only current trigger, but it exposes a general hole in the iterator contract. I would support zero axes in both iterator constructors. That makes “a zero-axis point space contains one point” a property of the iterator, ready for the next operation that divides axes into subspaces.

#' Insert array axes
#'
#' `rray_insert_axes()` inserts new axes with a dimension of 1.
#'
#' @details
#' `axes` are locations in the result, not locations in `x`. Inserting 2 axes
#' into an array with a dimensionality of 3 gives a result with a
#' dimensionality of 5 (2 + 3), so `axes` can be any value between 1 and 5.
#'
#' To work out the result, write out the resulting axes and mark the locations
#' listed in `axes` with 1. Then use the dimensions of `x` to fill in the rest
#' in order.
#'
#' ```
#' x       (2, 3, 4)
#' axes    2
#'
#' result  (x, 1, x, x)
#'       = (2, 1, 3, 4)
#' ```
#'
#' This allows you to insert two axes side by side:
#'
#' ```
#' x       (2, 3, 4)
#' axes    c(2, 3)
#'
#' result  (x, 1, 1, x, x)
#'       = (2, 1, 1, 3, 4)
#' ```
#'
#' Inserted axes have no names. The axes of `x` keep their names and carry them
#' to their new locations.
#'
#' @param x An array.
#'
#' @param axes An integer vector of locations in the _result_ to insert axes at.
#'   It must be in strictly increasing order.
#'
#' @returns
#' An array with new axes of dimension 1 at `axes`.
#'
#' @seealso [rray_squeeze()]
#'
#' @export
#' @examples
#' x <- array(1:24, c(2, 3, 4))
#'
#' # Insert one axis in the middle
#' # (2, 3, 4) -> (2, 1, 3, 4)
#' rray_dimensions(rray_insert_axes(x, 2))
#'
#' # Insert at the front and at the back
#' # (2, 3, 4) -> (1, 2, 3, 4, 1)
#' rray_dimensions(rray_insert_axes(x, c(1, 5)))
#'
#' # Two new axes side by side
#' # (2, 3, 4) -> (2, 1, 1, 3, 4)
#' rray_dimensions(rray_insert_axes(x, c(2, 3)))
#'
#' # Inserting no axes returns `x` unchanged
#' rray_insert_axes(x, integer())
#'
#' # `rray_squeeze()` undoes an insertion
#' rray_squeeze(rray_insert_axes(x, 2), 2)
rray_insert_axes <- function(x, axes) {
  .Call(ffi_rray_insert_axes, x, axes, environment())
}

Yes, it's weird, and it's the only case in the package.

The split

Seven arguments in the package are named axes. Six of them mean "axes of x":

  • rray_squeeze(x, axes)
  • rray_permute_axes(x, axes)
  • rray_move_axes(x, axes, to)
  • rray_split(x, axes)
  • rray_sum_along(x, axes) and friends

rray_insert_axes(x, axes) is the one that means "locations in the result". So the name carries two meanings, and insert is the lone outlier.

It's not just pedantic

The wrong reading gives a wrong answer:

rray_insert_axes(x, c(2, 3))   # x is (2, 3, 4)

"axes of x"      -> (2, 1, 3, 1, 4)
"result location" -> (2, 1, 1, 3, 4)   <- actual

That's exactly the case your @details has to spend a paragraph defusing. The name is pointing readers at the wrong door and the docs are pulling them back.

You already coined the word

rray_move_axes(x, axes, to) makes the distinction explicit: axes are in x, to is in the result. Insert needs the same treatment. to reads badly without a "from", so I'd use at:

rray_insert_axes(x, at = c(2, 3))

Then the rule is clean: axes always means axes of x, and result locations get their own word (to when it's directional, at when it's positional). Two spellings for result location is fine; one spelling for two concepts is not.

Note at doesn't delete the docs, the side-by-side behaviour still needs explaining. It just stops the argument name from arguing against the explanation.

One smaller thing while you're here

insert-axes.R says "locations" (you standardized that in b9b6331), but move-axes.R, permute-axes.R, and squeeze.R all still say "positions" for the same idea. Worth picking one. "Locations" is the better word since it's what you use in the insert docs and it doesn't collide with vctrs' "position" usage.

  r_obj* x_names = r_dim_names(x);

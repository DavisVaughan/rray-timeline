Yes, I think it's a good change. The lgl and int kernels are identical apart from two things: the NA value they compare against, and r_lgl_cbegin() vs r_int_cbegin(). Passing both in as arguments keeps the NA check type-correct. Each wrapper still hands over its own r_globals.na_lgl or r_globals.na_int, so it doesn't break the rule about never running int helpers on logical data.

How I'd do it:

  • Pass const int* v_x and int na, not x. Each wrapper calls its own typed cbegin, so the shared kernel never needs to know whether it has logical or integer data.

  • Pass count in as well. rray_mean_int() already computes it for the overflow check, so the shared kernel doesn't need x at all. In the na_rm case this also removes the rray_mean_count() call that rray_mean_int_na_rm() makes only for its check.

  • The overflow check stays in the int wrappers only. Logical never needs it: with 0/1 values the sum can't exceed the count. So rray_mean_int() becomes "check count, maybe return the fallback, otherwise call the shared kernel", and rray_mean_lgl() just calls the shared kernel.

  • Merge the propagate_na pair the same way. rray_mean_lgl_propagate_na() and rray_mean_int_propagate_na() also differ only by NA value, so that's a third shared function. The two int fallbacks are int-only and stay as they are.

The result:

static r_obj* rray_mean_lgl(...) {
  const r_ssize count = rray_mean_count(x, out_size);
  const int* v_x = r_lgl_cbegin(x);
  return rray_mean_lgl_or_int(v_x, r_globals.na_lgl, count, out_size, ...);
}

static r_obj* rray_mean_int(...) {
  const r_ssize count = rray_mean_count(x, out_size);

  if (count > RRAY_MEAN_INT64_MAX_COUNT) {
    return rray_mean_int_fallback(...);
  }

  const int* v_x = r_int_cbegin(x);
  return rray_mean_lgl_or_int(v_x, r_globals.na_int, count, out_size, ...);
}

The na_rm pair gets the same treatment through rray_mean_lgl_or_int_na_rm().

It should cost nothing in speed. The kernels already read na from r_globals at runtime, so the compiler was never treating it as a constant. Since these are static functions, they may well get inlined anyway. I can still benchmark against main to confirm.

I'd use plain functions rather than a macro like RRAY_INDEX_ATOMIC in src/index.c. Here only a value changes, not a type, and functions are easier to read and debug.

It looks like the rescale functions could be merged if na_rm were passed as an argument. Does it make a performance difference if we check na_rm && !ISNAN() in those loops? Especially if we pass na_rm as a constant true or false?

Claude

Short answer: no measurable difference, and you may not need na_rm at all.

You don't need an na_rm argument. The two rescale functions differ in two ways: the !ISNAN(x_elt) check and the count used. The !ISNAN(x_elt) check is already correct without na_rm. Rescale only touches cells where isinf(v_out[out_loc]) holds. Without na_rm, a cell that holds a NaN or NA has a NaN mean, never Inf, because NaN plus anything is NaN. So in those cells !ISNAN(x_elt) is always true, and the na_rm condition isinf(v_out[out_loc]) && !ISNAN(x_elt) works for both modes.

The real difference is the count. Plain rescale divides by one count. The na_rm version divides by v_counts[out_loc]. To merge them, the plain path needs a per-cell count too. Two options:

  • Allocate a counts buffer in rray_mean_dbl(), filled with count, only when any_infinite is true. Then there's one rray_mean_dbl_rescale(v_x, v_out, v_counts, ...). The extra allocation only happens on a path that is already rare. This is the simplest option, and the one I'd pick.

  • Pass both count and a v_counts that may be NULL, and pick per element. This avoids the allocation, but adds a branch in the loop and makes the signature murkier.

On performance, if you did add na_rm &&:

  • The branch costs almost nothing. na_rm never changes inside the loop, so the CPU predicts it perfectly. Each element already does a load and an isinf() check, plus a floating-point division, which costs far more.

  • Passing a literal true or false doesn't guarantee the branch is compiled away. The function is called from two places with different values. Compiling a separate copy for each value (GCC's constant-propagation cloning) or hoisting the branch out of the loop (loop unswitching) mostly happens at -O3. R builds packages at -O2. Inlining would remove it, but these functions are large enough that the compiler may not inline them.

  • It's a rare path either way. Rescale only runs when a sum overflows to ±Inf, so its speed matters very little.

Right. Neither int fallback does a correction pass. Each one sums into a double and divides once.

Where error comes in. Integers are exact in a double, but a running total past 2^53 gets rounded on every add. The fallback only runs once a cell has more than 2^32 elements, so the total can reach about 2^31 × 2^32 = 2^63, well past 2^53. For example, take the long-vector test (every value .Machine$integer.max):

  • Near 2^63, adjacent doubles are 2048 apart.

  • So each add of 2147483647 rounds up to 2147483648, an error of +1.

  • The errors all point the same way and pile up, giving a relative error of about 5e-10.

That's why the test uses expect_equal() and not expect_identical().

R doesn't correct here either. integer_mean() in src/main/summary.c sums into a LDOUBLE (long double) and divides once:

LDOUBLE s = 0.0;
for (R_xlen_t i = 0; i < n; i++) {
  ...
  s += xi;
}
return ScalarReal((double) (s/n));

On x86 a long double has 64 mantissa bits, so R is exact there. On arm64 macOS a long double is just a double, so R has the same rounding we do on your machine.

A fix. Add the same second pass the double kernels use. Compute the mean, then sum x_elt - mean over each cell and add correction / count. The differences are small, so this second sum stays accurate and removes nearly all of the first-pass error. It costs an extra pass over the data, but only in a path that runs for cells with more than 2^32 elements. The na_rm fallback would get the same change, dividing by v_counts[i].

I'd add it. That gives the int fallbacks the same accuracy as the double kernels, and it doesn't depend on how wide long double is on the platform. Want me to?

Yes. Each term is already divided by count before it's added, so once the first pass ends the buffer holds the mean, not a sum. The rest of the function already treats it as a mean:

  • The correction pass subtracts it from each element, which is what you do with a mean: (v_x[i] - v_sums[out_loc]) / count.

In rray_mean_dbl() the plain sum works differently. The total is divided only after the loop, so during the loop sum really is a sum. The rescale functions divide every term, so the running total is always heading towards the mean.

Mostly it's all needed. Each piece covers a real case, and the double kernels follow the same steps as R's real_mean() in src/main/summary.c: sum and divide, retry with scaled terms if the sum overflows, then a correction pass. The repetition comes from two sources, and only one of them is worth reducing.

What has to stay (to keep the same accuracy):

  • The int64 path for lgl/int. It's exact and fast.

  • The correction pass. It is what makes our results match mean() bit for bit. A one-pass method such as Kahan summation would be just as accurate, but it wouldn't round the same way as R. The tests that compare against mean() with expect_identical() would break.

  • Rescale, for sums that overflow to Inf. R has the same step.

  • propagate_na, to keep NA apart from NaN.

  • The int fallbacks. Without them, an int64 sum can overflow once a cell has more than 2^32 elements.

  • Separate na_rm kernels. The two loops have different hot paths.

Where the repetition comes from:

  1. Iterator boilerplate. Every pass repeats about 15 lines of rray_run_iterator setup and the run loop. Most passes also split on out_stride == 0. This is most of the file's length, and it's the price of the iterator API, not of the mean algorithm.

  2. Type × na_rm combinations. The int fallbacks are the double algorithm (sum, divide, correct) with integer loads. That's about 180 lines repeating the shape of rray_mean_dbl() and rray_mean_dbl_na_rm().

Ways to cut it, best first:

  • Drop the out_stride == 0 split in the two int fallbacks. That's about 30 fewer lines and changes no results. The rescale and propagate_na passes already skip the split. The catch: the fallbacks only run on cells with more than 2^32 elements. That's rare, but each call is huge, and the split is what keeps the running sum in a local. So this trades speed on exactly the arrays where it costs the most. I'm on the fence about it.

  • Generate the int fallback and double kernels from one macro body, as RRAY_INDEX_ATOMIC does in src/index.c. This saves the most, perhaps 150 lines. But the double kernels have rescale and NA-vs-NaN steps that integers never need, so the macro would need branches inside it. I think it would read worse than what's there now.

  • Remove the int fallbacks by splitting each value into high and low 16-bit halves and summing each in int64. Both stay exact for any realistic length. But it costs an extra add and an extra buffer in the main int path, which every integer mean runs through. I wouldn't do this.

My take: the algorithm itself has no spare parts. What's left is iterator boilerplate and the type × na_rm product. I'd leave it as is, or at most drop the split in the int fallbacks, and only if you're fine with the speed cost on huge arrays.

Does the int fallback need rescale? Just curious

Claude

No. The int fallback's sum can never overflow to Inf, so rescale would never run.

The worst case:

  • Each element: an integer is at most 2^31 in size.

  • Elements per cell: at most R's longest vector, R_XLEN_T_MAX = 2^52.

  • The total: at most 2^31 × 2^52 = 2^83.

A double only overflows to Inf past about 2^1024, so the sum is nowhere close. The correction pass is safe for the same reason. Each x_elt - mean is at most 2^32 in size, so those totals stay under 2^84.

Doubles need rescale only because a single double element can already be close to DBL_MAX, so even two of them can overflow. Integers are too small for that.

I found two real weaknesses and some smaller ones. I didn't change anything.

1. We only match mean() on platforms where long double is just a double. R sums in LDOUBLE. On x86 Linux and Windows that's an 80-bit float: more precision and a much wider range. On your Mac it's a plain double (.Machine$sizeof.longdouble is 8), so there our steps match R bit for bit. On x86 they won't:

  • Last-bit differences. The tests that check against mean() with expect_identical() (for example "matches mean() over every combination of axes" with its 1e16 values) could fail on x86.

  • Range. See point 2: R on x86 gets a case right that we get wrong.

  • CI can't catch this. R-CMD-check.yaml only runs macos-latest. The Ubuntu and Windows rows are commented out.

So the real question is whether "identical to mean()" is a promise. If it is, we'd have to accumulate in long double too, which means 16-byte buffers and slow x87 maths on x86. If it isn't, the tests that compare against mean() should use expect_equal().

2. The correction pass can overflow and wreck a finite mean. With m <- .Machine$double.xmax:

x <- c(m, -m, m)
rray_mean(x, 1L)
#> -Inf
m / 3
#> 5.99231e+307

The sum is finite, so the mean is finite (about 6e307). But the residual -m - mean overflows to -Inf, and adding that correction ruins the result. na_rm = TRUE does the same. R on this Mac also returns -Inf, since it uses the same steps in plain double. R on x86 gets it right because of the wider long double. The fix is cheap: only apply the correction if it's finite, and otherwise keep the uncorrected mean. That changes one line in each final loop of rray_mean_dbl(), rray_mean_dbl_na_rm() and the two int fallbacks. (The int fallbacks can't actually hit this, as we worked out for rescale.)

Smaller things:

  • rray_mean_int64() isn't always correctly rounded once the sum passes 2^53. (double) (sum / count) + (double) (sum % count) / count rounds twice, so in rare cases it can be off by 1 ulp (one step between neighbouring doubles). R does no better. I checked negative sums and they come out right, but no test covers them. Adding a negative version of "integer means are exact when the total is above 2^53" would be cheap.

  • The fallbacks never run in CI. Their tests need about 16 GB and are skipped by default. That's fine, but it means we only exercise them by hand, like today.

  • A single Inf in the input triggers the rescale passes. Two extra full passes over x, even if only one cell is infinite. R does the same per vector, so it's only a speed cost, and only on input that contains Inf.

I'd fix point 2 now. Point 1 needs your call on whether matching mean() exactly on every platform is a goal.

Can rescale reuse an existing corrections vector?

Claude

Yes. By the time rescale runs, rray_mean_dbl() has already used its corrections buffer to finish every finite cell, so nothing reads it again. Rescale could take v_corrections from its caller instead of allocating its own:

  • Zeroing is already handled. Rescale's first loop zeroes both its buffers before using them. If it zeroes the caller's buffer instead, the old values left in it (x - Inf for infinite cells) are cleared too.

  • The same works for na_rm. rray_mean_dbl_na_rm() has its own corrections buffer to pass to rray_mean_dbl_rescale_na_rm().

means still needs its own buffer. Rescale uses isinf(v_out[out_loc]) to pick which cells to work on. If it summed the means straight into v_out, it would overwrite exactly the values it checks, so it needs somewhere else to put them. There are ways around that, such as marking the infinite cells somewhere else, but they're more clever than this rare path deserves.

So the change is: pass v_corrections into both rescale functions and drop one allocation and one KEEP() from each. That's a small win, since it only runs when some sum overflowed. It does also make the rescale functions a little less self-contained, which you may or may not care about.

Any other obvious chance for reuse?

Claude

One, and it's on the main path, unlike the rescale change.

rray_mean_lgl_or_int() and its na_rm version could sum straight into out. Right now each one allocates an int64 sums buffer and then a separate out buffer of doubles, both with out_size elements. Both element types are 8 bytes, so the int64 sums could live in out's memory:

  1. Allocate out first and zero it. All-zero bits is 0 as an int64.

  2. Sum into it through an int64_t*.

  3. Convert each cell in place: read the int64 at index i, then write the double mean back to index i. Each cell is read before it is written, so nothing gets overwritten too early.

This saves one out_size-sized allocation on every integer and logical mean, which matters when out is large, such as reducing axis 1 of a wide matrix. The catch is C's strict aliasing rule: reading memory through one pointer type after writing it through another can be undefined behaviour. In practice it's fine here, because R's memory has no declared type and each element is written as int64, then read as int64, then written as double. To be strictly correct, I'd do the in-place read with memcpy() into a local int64_t. Compilers turn that into a plain load.

Nothing else is worth it:

  • The means buffer in rescale. Rescale needs three things at once: which cells are infinite (read from v_out), the running means, and the corrections. That's three arrays, and only two are free to reuse.

  • The corrections buffers in the double kernels and int fallbacks. The correction pass needs the mean and the correction at the same time.

  • The counts buffers in the na_rm kernels. They're needed right to the end, including by rescale.

Yes, I think that's the right fix. It also matches what RRAY_BINARY already does, so it's a consistency win and not just a workaround.

What changes

  • rray_reduce_fn takes a struct r_lazy error_call, and rray_reduce() passes its own through.

  • RRAY_REDUCE gets a last ONE_ARGS parameter, and its two call sites become ONE(v_out[out_loc], v_x[i] ONE_ARGS).

  • Every flat reduce kernel takes error_call (extremum, logical, prod, sum). Kernels that don't need it pass the no-args marker. Binary kernels already work this way: rray_add_lgl_dbl() takes error_call and passes RRAY_BINARY_NO_ARGS.

What it lets one-add.h drop

  • check_sum_int_overflow() goes away. That also gets rid of its bare r_abort(), which ignores error_call. The snapshot shows rray_sum() only because r_abort() picks up the current R frame, so the error call would be wrong if another C function ever called rray_sum().

  • rray_sum_int_one() goes away, and rray_sum_int passes rray_add_int_one with the args marker instead.

  • rray_sum_int_one_na_rm() shrinks to a missing check on x, then return rray_add_int_one(out, x, error_call). The add helper re-checks out for NA, which is redundant here but cheap.

  • rray_sum_lgl_one() stays. Per the earlier rule, int helpers don't run on logical data.

One thing I'd change in your plan: the marker name

RRAY_BINARY_ARGS / RRAY_BINARY_NO_ARGS live in binary.h, and seeing RRAY_BINARY_ARGS(error_call) inside a reduce kernel reads wrong. The macro is just , __VA_ARGS__, so nothing about it is specific to binary ops. I'd rename it to RRAY_ONE_ARGS(...) / RRAY_ONE_NO_ARGS, to match the ONE_ARGS parameter both macros take, and put it in one small shared header that binary.h and reduce.h both include. The other option is a parallel RRAY_REDUCE_ARGS, which duplicates a one-line macro under a second name.

Other options, both worse

  • Keep r_abort() in the sum helpers. The error call stays wrong and the duplicate overflow check stays.

  • Pass state through a context struct or a static. That's more machinery than one extra argument, and it breaks the pattern binary already set.

Questions before I'd start

  1. Should the nested path (rray_reduce_nested_fn, RRAY_REDUCE_OUTER) get error_call too, for symmetry? Mean accumulates in double, so nothing needs it today. I lean yes so the two reduce APIs look the same, but it's dead weight for now.

  2. Should rray_sum_dbl_one(), rray_sum_cpl_one(), rray_prod_dbl_one(), and rray_prod_cpl_one() stay as thin wrappers? Once ONE_ARGS exists, the kernels could pass rray_add_dbl_one and friends directly. But the wrappers hold your comments about c(NA, NaN) and recovering infinities, and those would need a new home. I'd keep the wrappers.

  3. Should the marker rename be its own PR first, with the reduce change stacked on top? I'd split it that way.

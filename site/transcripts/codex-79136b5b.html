# Integer coordinate indexing plan

## Recommendation

Add one fully specified coordinate function and one directional one-axis
specialization:

```r
rray_index(x, ...)
rray_index_assign(x, ..., value)

rray_index_axis(x, i, ..., axis)
rray_index_assign_axis(x, i, ..., axis, value)
```

`rray_index()` requires exactly one integer coordinate array for every source
axis. The arrays broadcast to common dimensions and are read pointwise. The
common dimensions are the result dimensions.

`rray_index_axis()` accepts one integer array for the selected source axis and
supplies identity coordinates for every other axis. `i` must broadcast to the
dimensions of `x` outside `axis`. The result has the same dimensionality as
`x`, every unselected axis keeps its source dimension, and only the selected
axis can change.

Every source coordinate is explicit. Different partial indexing behaviors are
represented by shaping full coordinate arrays in different ways.

The complete family is:

| Operation | Read | Assign |
|---|---|---|
| Orthogonal subscripts | `rray_slice()` | `rray_slice_assign()` |
| One-axis subscript | `rray_slice_axis()` | `rray_slice_assign_axis()` |
| First axis subscript | `rray_slice_rows()` | `rray_slice_assign_rows()` |
| Second axis subscript | `rray_slice_columns()` | `rray_slice_assign_columns()` |
| One-axis coordinate array | `rray_index_axis()` | `rray_index_assign_axis()` |
| Full coordinate arrays | `rray_index()` | `rray_index_assign()` |
| Flat subscript or point matrix | `rray_extract()` | `rray_extract_assign()` |

Do not add replacement functions. Every `_assign()` function returns a
modified copy of `x`.

## Subscripts and coordinates

A subscript describes a set of positions. It can be negative, logical,
character, missing, or `NULL`. Subscript normalization produces a
one-dimensional sequence of positive or missing locations. Subscripts on
different axes form a Cartesian product.

A coordinate array has a narrower meaning. Each non-missing element is one
positive, one-based position on one source axis. Its dimensions connect that
coordinate to an output point. Coordinates on different source axes broadcast
and pair pointwise.

```r
rray_slice_axis(x, -1L, axis = 2L)
# Complement selection

rray_index_axis(x, array(-1L, rray_dimensions(x)), axis = 2L)
# Error: coordinates must be positive
```

The function name determines the input rules. The shape or class of `i` never
changes a slice into coordinate indexing.

## Full coordinate model

Let:

- `D` be the source dimensions.
- `n` be the dimensionality of `x`.
- `L[a]` be the coordinate array supplied for source axis `a`.
- `G` be the common dimensions of all `L[a]`.

`rray_index()` requires exactly `n` coordinate arrays. At every output point
`g` in `G`, each broadcast coordinate array supplies one component of the
source coordinate:

```text
source[a] = broadcast(L[a])[g]
out[g] = x[source[1], source[2], ..., source[n]]
```

The result dimensions are exactly `G`:

```text
out_dimensions = common_dimensions(L[1], ..., L[n])
```

The output can have lower, equal, or greater dimensionality than `x`. There is
no source-axis placement rule because every output axis belongs to the common
coordinate space.

Singleton dimensions and missing trailing dimensions follow rray's
left-aligned broadcasting rules.

## Coordinate validation

Each argument in `...` and `i` in `rray_index_axis()` must be a bare integer
vector or array. Bare vectors are one-dimensional arrays. Factors and other
classed integer objects are errors.

Every non-missing coordinate must be positive, one based, and no greater than
the dimension of its source axis:

- Positive integers identify one source position.
- Zero and negative integers are errors.
- Missing coordinates produce missing output when reading.
- Missing coordinates are errors when assigning.
- Out-of-bounds coordinates are errors.

Logical, character, and double inputs are errors. Logical values are masks,
character values require name matching, and doubles weaken the strict
coordinate contract. Those inputs belong to slicing or extraction.

Validation happens before allocating or copying the result. Every coordinate
array is validated even when the common result has size zero.

## `rray_index()`

- `x` must be an array or bare vector supported by rray.
- Bare vectors normalize to one-dimensional arrays.
- `...` must contain exactly one coordinate array per source axis.
- Argument position identifies the source axis.
- Coordinate arguments must be unnamed.
- Dynamic splicing is supported.
- All coordinate arrays broadcast to common dimensions.
- The result has the same storage type as `x`.
- The resulting dimensionality must not exceed rray's supported maximum.

`value` follows `...` in `rray_index_assign()`, so it must be supplied by

### Missing coordinates

If any coordinate at an output point is missing, the result at that point is
missing:

| Type | Missing output |
|---|---|
| logical | `NA` |
| integer | `NA_integer_` |
| double | `NA_real_` |
| complex | `NA_complex_` |
| character | `NA_character_` |
| raw | `as.raw(0)` |
| list | `NULL` |

Zero dimensions follow the existing common-dimension rules:

- Equal zero dimensions are compatible.
- Zero and one combine to zero.
- Zero and a dimension greater than one are incompatible.

### Summary¶

GatherElements takes two inputs `data` and `indices` of the same rank r >= 1 and an optional attribute `axis` that identifies an axis of `data` (by default, the outer-most axis, that is axis 0). It is an indexing operation that produces its output by indexing into the input data tensor at index positions determined by elements of the `indices` tensor. Its output shape is the same as the shape of `indices` and consists of one value (gathered from the `data`) for each element in `indices`.

      out[i][j][k] = input[i][j][index[i][j][k]] if axis = 2,

# numpy.choose#

numpy.choose(a, choices, out=None, mode='raise')[source]#
    

Construct an array from an index array and a list of arrays to choose from.

First of all, if confused or uncertain, definitely look at the Examples - in its full generality, this function is less simple than it might seem from the following code description:
    
    np.choose(a,c) == np.array([c[a[I]][I] for I in np.ndindex(a.shape)])
    

But this omits some subtleties. Here is a fully general summary:

L101: ## Abstractcite69†# L102: 
L103: NumPy’s “advanced” indexing support for indexing array with other arrays is one of its most powerful and popular features. Unfortunately, the existing rules for advanced indexing with multiple array indices are typically confusing to both new, and in many cases even old, users of NumPy. Here we propose an overhaul and simplification of advanced indexing, including two new “indexer” attributes `oindex` and `vindex` to facilitate explicit indexing.
L104: 
L105: ## Backgroundcite70†# L106: ### Existing indexing operationscite71†# L107: 
L108: NumPy arrays currently support a flexible range of indexing operations:
L109: 
L110:   * “Basic” indexing involving only slices, integers, `np.newaxis` and ellipsis (`...`), e.g., `x[0, :3, np.newaxis]` for selecting the first element from the 0th axis, the first three elements from the 1st axis and inserting a new axis of size 1 at the end. Basic indexing always return a view of the indexed array’s data.
L111:   * “Advanced” indexing, also called “fancy” indexing, includes all cases where arrays are indexed by other arrays. Advanced indexing always makes a copy:
L112: 
L113:     * “Boolean” indexing by boolean arrays, e.g., `x[x > 0]` for selecting positive elements.
L114:     * “Vectorized” indexing by one or more integer arrays, e.g., `x[[0, 1]]` for selecting the first two elements along the first axis. With multiple arrays, vectorized indexing uses broadcasting rules to combine indices along multiple dimensions. This allows for producing a result of arbitrary shape with arbitrary elements from the original arrays.
L115:     * “Mixed” indexing involving any combinations of the other advancing types. This is no more powerful than vectorized indexing, but is sometimes more convenient.
L116: 
L117: For clarity, we will refer to these existing rules as “legacy indexing”. This is only a high-level summary; for more details, see NumPy’s documentation and Examples below.
L118: ### Outer indexingcite72†# L119: 
L120: One broadly useful class of indexing operations is not supported:
L121:   * “Outer” or orthogonal indexing treats one-dimensional arrays equivalently to slices for determining output shapes. The rule for outer indexing is that the result should be equivalent to independently indexing along each dimension with integer or boolean arrays as if both the indexed and indexing arrays were one-dimensional. This form of indexing is familiar to many users of other programming languages such as MATLAB, Fortran and R.
L122: The reason why NumPy omits support for outer indexing is that the rules for outer and vectorized conflict. Consider indexing a 2D array by two 1D integer arrays, e.g., `x[[0, 1], [0, 1]]`:
L123: 
L124:   * Outer indexing is equivalent to combining multiple integer indices with `itertools.product()`. The result in this case is another 2D array with all combinations of indexed elements, e.g., `np.array([[x[0, 0], x[0, 1]], [x[1, 0], x[1, 1]]])`
L125:   * Vectorized indexing is equivalent to combining multiple integer indices with `zip()`. The result in this case is a 1D array containing the diagonal elements, e.g., `np.array([x[0, 0], x[1, 1]])`.
L126: 
L127: This difference is a frequent stumbling block for new NumPy users. The outer indexing model is easier to understand, and is a natural generalization of slicing rules. But NumPy instead chose to support vectorized indexing, because it is strictly more powerful.
L128: It is always possible to emulate outer indexing by vectorized indexing with the right indices. To make this easier, NumPy includes utility objects and functions such as `np.ogrid` and `np.ix_`, e.g., `x[np.ix_([0, 1], [0, 1])]`. However, there are no utilities for emulating fully general/mixed outer indexing, which could unambiguously allow for slices, integers, and 1D boolean and integer arrays.
L129: ### Mixed indexingcite73†# L130: 
L131: NumPy’s existing rules for combining multiple types of indexing in the same operation are quite complex, involving a number of edge cases.
L132: 
L133: One reason why mixed indexing is particularly confusing is that at first glance the result works deceptively like outer indexing. Returning to our example of a 2D array, both `x[:2, [0, 1]]` and `x[[0, 1], :2]` return 2D arrays with axes in the same order as the original array.
L134: However, as soon as two or more non-slice objects (including integers) are introduced, vectorized indexing rules apply. The axes introduced by the array indices are at the front, unless all array indices are consecutive, in which case NumPy deduces where the user “expects” them to be. Consider indexing a 3D array `arr` with shape `(X, Y, Z)`:
L135: 
L136:   1. `arr[:, [0, 1], 0]` has shape `(X, 2)`.
L137: 
L138:   2. `arr[[0, 1], 0, :]` has shape `(2, Z)`.
L139: 
L140:   3. `arr[0, :, [0, 1]]` has shape `(2, Y)`, not `(Y, 2)`!
L141: These first two cases are intuitive and consistent with outer indexing, but this last case is quite surprising, even to many highly experienced NumPy users.
L142: Mixed cases involving multiple array indices are also surprising, and only less problematic because the current behavior is so useless that it is rarely encountered in practice. When a boolean array index is mixed with another boolean or integer array, boolean array is converted to integer array indices (equivalent to `np.nonzero()`) and then broadcast.
L143: For example, indexing a 2D array of size `(2, 2)` like `x[[True, False], [True, False]]` produces a 1D vector with shape `(1,)`, not a 2D sub-matrix with shape `(1, 1)`.
L144: Mixed indexing seems so tricky that it is tempting to say that it never should be used. However, it is not easy to avoid, because NumPy implicitly adds full slices if there are fewer indices than the full dimensionality of the indexed array. This means that indexing a 2D array like `x[[0, 1]]` is equivalent to `x[[0, 1], :]`. These cases are not surprising, but they constrain the behavior of mixed indexing.
L145: ### Indexing in other Python array librariescite74†# L146: 
L147: Indexing is a useful and widely recognized mechanism for accessing multi-dimensional array data, so it is no surprise that many other libraries in the scientific Python ecosystem also support array indexing.
L148: Unfortunately, the full complexity of NumPy’s indexing rules mean that it is both challenging and undesirable for other libraries to copy its behavior in all of its nuance. The only full implementation of NumPy-style indexing is NumPy itself. This includes projects like dask.array and h5py, which support most types of array indexing in some form, and otherwise attempt to copy NumPy’s API exactly.
L149: Vectorized indexing in particular can be challenging to implement with array storage backends not based on NumPy. In contrast, indexing by 1D arrays along at least one dimension in the style of outer indexing is much more achievable. This has led many libraries (including dask and h5py) to attempt to define a safe subset of NumPy-style indexing that is equivalent to outer indexing, e.g., by only allowing indexing with an array along at most one dimension.
L150: However, this is quite challenging to do correctly in a general enough way to be useful. For example, the current versions of dask and h5py both handle mixed indexing in case 3 above inconsistently with NumPy. This is quite likely to lead to bugs.
L151: These inconsistencies, in addition to the broader challenge of implementing every type of indexing logic, make it challenging to write high-level array libraries like xarray or dask.array that can interchangeably index many types of array storage. In contrast, explicit APIs for outer and vectorized indexing in NumPy would provide a model that external libraries could reliably emulate, even if they don’t support every type of indexing.
L152: ## High level changescite75†# L153: 
L154: Inspired by multiple “indexer” attributes for controlling different types of indexing behavior in pandas, we propose to:
L155: 
L156:   1. Introduce `arr.oindex[indices]` which allows array indices, but uses outer indexing logic.
L157: 
L158:   2. Introduce `arr.vindex[indices]` which use the current “vectorized”/broadcasted logic but with two differences from legacy indexing:
L159: 
L160:      * Boolean indices are not supported. All indices must be integers, integer arrays or slices.
L161:      * The integer index result dimensions are always the first axes of the result array. No transpose is done, even for a single integer array index.
L162: 
L163:   3. Plain indexing on arrays will start to give warnings and eventually errors in cases where one of the explicit indexers should be preferred:
L164: 
L165:      * First, in all cases where legacy and outer indexing would give different results.
L166: 
L167:      * Later, potentially in all cases involving an integer array.
L168: These constraints are sufficient for making indexing generally consistent with expectations and providing a less surprising learning curve with `oindex`.
L169: 
L170: Note that all things mentioned here apply both for assignment as well as subscription.
L171: Understanding these details is not easy. The Examples section in the discussion gives code examples. And the hopefully easier Motivational Example provides some motivational use-cases for the general ideas and is likely a good start for anyone not intimately familiar with advanced indexing.
L172: ## Detailed descriptioncite76†# L173: ### Proposed rulescite77†# L174: 
L175: From the three problems noted above some expectations for NumPy can be deduced:
L176: 
L177:   1. There should be a prominent outer/orthogonal indexing method such as `arr.oindex[indices]`.
L178: 
L179:   2. Considering how confusing vectorized/fancy indexing can be, it should be possible to be made more explicitly (e.g. `arr.vindex[indices]`).
L180:   3. A new `arr.vindex[indices]` method, would not be tied to the confusing transpose rules of fancy indexing, which is for example needed for the simple case of a single advanced index. Thus, no transposing should be done. The axes created by the integer array indices are always inserted at the front, even for a single index.
L181:   4. Boolean indexing is conceptually outer indexing. Broadcasting together with other advanced indices in the manner of legacy indexing is generally not helpful or well defined. A user who wishes the “`nonzero`” plus broadcast behaviour can thus be expected to do this manually. Thus, `vindex` does not need to support boolean index arrays.
L182:   5. An `arr.legacy_index` attribute should be implemented to support legacy indexing. This gives a simple way to update existing codebases using legacy indexing, which will make the deprecation of plain indexing behavior easier. The longer name `legacy_index` is intentionally chosen to be explicit and discourage its use in new code.
L183:   6. Plain indexing `arr[...]` should return an error for ambiguous cases. For the beginning, this probably means cases where `arr[ind]` and `arr.oindex[ind]` return different results give deprecation warnings. This includes every use of vectorized indexing with multiple integer arrays. Due to the transposing behaviour, this means that `arr[0, :, index_arr]` will be deprecated, but `arr[:, 0, index_arr]` will not for the time being.
L184:   7. To ensure that existing subclasses of ndarray that override indexing do not inadvertently revert to default behavior for indexing attributes, these attribute should have explicit checks that disable them if `__getitem__` or `__setitem__` has been overridden.
L185: 
L186: Unlike plain indexing, the new indexing attributes are explicitly aimed at higher dimensional indexing, several additional changes should be implemented:
L187:   * The indexing attributes will enforce exact dimension and indexing match. This means that no implicit ellipsis (`...`) will be added. Unless an ellipsis is present the indexing expression will thus only work for an array with a specific number of dimensions. This makes the expression more explicit and safeguards against wrong dimensionality of arrays.
L188: There should be no implications for “duck typing” compatibility with builtin Python sequences, because Python sequences only support a limited form of “basic indexing” with integers and slices.
L189:   * The current plain indexing allows for the use of non-tuples for multi-dimensional indexing such as `arr[[slice(None), 2]]`. This creates some inconsistencies and thus the indexing attributes should only allow plain python tuples for this purpose. (Whether or not this should be the case for plain indexing is a different issue.)
L190: 
L191:   * The new attributes should not use getitem to implement setitem, since it is a cludge and not useful for vectorized indexing. (not implemented yet)
L192: ### Open Questionscite78†# L193: 
L194:   * The names `oindex`, `vindex` and `legacy_index` are just suggestions at the time of writing this, another name NumPy has used for something like `oindex` is `np.ix_`. See also below.

## Assignment

```r
rray_index_assign(x, ..., value)
rray_index_assign_axis(x, i, ..., axis, value)
```

Assignment follows the same coordinate plan as reading:

1. Normalize and validate `x` and every coordinate.
2. Compute the indexing result dimensions.
3. Reject missing target coordinates.
4. Cast `value` losslessly to the type of `x`.
5. Broadcast the cast value to the indexing result dimensions.
6. Copy `x`.
7. Write in column-major result order.

The operation cannot change the type, size, dimensions, or names of `x`.
Repeated source coordinates use deterministic final-write-wins behavior. The
last value visited in column-major result order wins.

An error occurs before copying or writing. Casting and broadcasting `value`
before copying also handles `value` equal to `x`.

`NULL` is not an array and cannot be an assignment value. To assign `NULL` into
a list array, use a list array containing `NULL`.

Analyzing indexing semantics and naming conventions

You are not missing a more fundamental justification for rray_index_axis(). It is one useful shape contract among several operations that lower to rray_index().

ONNX provides the clearest taxonomy:

Family Common names Index meaning Relation to rray_index()
Full coordinate gather vectorized indexing, pointwise indexing, GatherND One coordinate for several or all source axes Essentially rray_index()
Independent axis gather take, Gather, index_select The same index array is used in every lane Identity coordinates plus one independent coordinate array
Per-lane axis gather take_along_axis, GatherElements, torch.gather The selected coordinate can vary in every lane Identity coordinates plus one coordinate field
Batched axis gather tf.gather(..., batch_dims=) Some leading axes identify lanes, remaining index axes are inserted A hybrid of independent and per-lane gathering
Flat gather flat take, torch.take Positions in the flattened array Unravel positions, then call rray_index()

The direct name for rray_index()

The operation itself is normally called vectorized integer indexing, pointwise indexing, or a full coordinate gather.

The Array API standard describes exactly the rray model: integer coordinate arrays broadcast to a common shape and are zipped together into coordinates. NumPy calls this vectorized or advanced indexing. NEP 21 contrasts it with orthogonal indexing by describing it as zip() rather than a Cartesian product. The main rray differences are one-based coordinates, left-aligned broadcasting, strict bounds, and missing-coordinate behavior. Array API integer indexing, NumPy NEP 21

Other presentations of the same operation include:

  • ONNX/TensorFlow GatherND packs coordinates into the final dimension of one index tensor. Full-depth GatherND is rray_index() with the coordinate arrays stacked instead of passed separately. Partial-depth GatherND returns trailing slices, which can be expressed by supplying identity coordinates for the omitted axes. ONNX GatherND
  • Julia pointwise indexing uses an array of CartesianIndex values. Julia explicitly calls this “pointwise indexing.” Julia Cartesian indices
  • Base R matrix indexing packs one coordinate tuple into each row of a matrix. This is the one-dimensional-output case of rray_index(). R extraction
  • xarray vectorized indexing gives coordinate indexers shared named output dimensions, then broadcasts them. xarray vectorized indexing

So rray_index() already has several established names. “Broadcasted pointwise coordinate indexing” is probably the most precise description.

The axis specializations are not all the same

For axis a, all these operations use the same basic equation:

out[g] = x[g[1], ..., i[g], ..., g[n]]

What differs is the shape contract.

  1. take_along_axis()

    NumPy and the Array API require x and i to have the same dimensionality. Outside the selected axis they broadcast, while the selected result dimension comes from i. This is almost exactly the proposed rray_index_axis() contract. NumPy take_along_axis, Array API take_along_axis

  2. PyTorch gather() and ONNX GatherElements

    These use the same coordinate equation, but their shape contract is different. The result has exactly the shape of index; there is no broadcasting, and unselected dimensions may be smaller than those of the source. PyTorch gather, ONNX GatherElements

    Therefore Torch gather is representable by rray_index(), but it is not fully equivalent to rray_index_axis(). It agrees only when all unselected index dimensions already equal the corresponding source dimensions.

  3. take() / ONNX Gather

    Here the index does not depend on the other source coordinates. A multidimensional index replaces one source axis with all the index dimensions:

    x:       (A, B, C)
indices: (J, K)
axis:    2
result:  (A, J, K, C)

    That is NumPy take() and ONNX Gather. NumPy take, ONNX Gather

    A one-dimensional version is also called torch.index_select(). PyTorch index_select

  4. TensorFlow batched gather

    tf.gather(..., batch_dims = b) makes the first b dimensions lane identifiers, while the remaining index dimensions are inserted at the selected axis. It fills the space between take() and take_along_axis(). With suitable transposition and all other axes treated as batch axes, it can express take-along behavior. TensorFlow gather

A few further named lowerings

These are also useful, although they do not suggest new primitives:

  • choose() is a per-position gather from a stack of choices. Stack the choices on a new axis and gather along that axis. NumPy choose
  • Embedding lookup is ordinarily just take() or Gather on the first axis.
  • Diagonal and anti-diagonal extraction are pointwise gathers with linked coordinate sequences.
  • Sorting from argsort, selection from argmax, and top-k value extraction are location-producing operations followed by take_along_axis().
  • Boolean masking, compress(), and masked_select() become coordinate gathering after nonzero() computes the selected locations.
  • XLA/StableHLO Gather is broader than rray_index(): it gathers whole windows and can place or collapse dimensions. rray_index() is its scalar-window case. XLA Gather

The assignment duals have corresponding names:

  • put_along_axis, Torch scatter, and ONNX ScatterElements
  • scatter_nd, tensor_scatter_nd_update, and index_put

Those differ mainly in collision handling. Some require unique coordinates, some reduce duplicates, and rray currently proposes deterministic final-write-wins behavior.

My conclusion for rray

rray_index_axis() is not mathematically privileged, but it is not random either. It chooses a valuable invariant:

Only the selected axis can change. Every other source axis retains its dimension and names.

That is precisely why it works naturally with argmax(), argsort(), and other per-lane location producers. It is the take_along_axis() specialization of rray_index(), not the universal one-axis gather.

I would document the family as:

  • rray_index(): broadcasted pointwise coordinate indexing, equivalent in structure to vectorized indexing or full-depth GatherND.
  • rray_index_axis(): the rank-preserving take_along_axis() specialization.
  • rray_slice_axis(): one-dimensional take()/index_select, extended with ordinary R subscripts.
  • Multidimensional take(): representable through rray_index(), with a possible rray_take() wrapper only if the shape-insertion behavior proves common enough.
  • Torch-style contracting gather(): also representable through rray_index(), but deliberately not the contract of rray_index_axis().

So the main missing named forms are GatherND, Gather/take, GatherElements/Torch gather, and TensorFlow’s batched gather. They do not expose missing expressive power in rray_index(). They expose different, useful ways to manufacture the full coordinate arrays and decide the result shape.

Clarifying GatherND versus rray indexing with examples

GatherND and rray_index() perform the same pointwise lookup. They package the coordinates differently.

Suppose x is a matrix. We want these two points:

(1, 2)
(3, 4)

GatherND packs them as coordinate tuples:

coordinates <- rbind(
  c(1L, 2L),
  c(3L, 4L)
)

Conceptually:

GatherND(x, coordinates)
= c(x[1, 2], x[3, 4])

rray_index() splits the coordinate tuples into one array per source axis:

rows <- c(1L, 3L)
columns <- c(2L, 4L)

rray_index(x, rows, columns)
# c(x[1, 2], x[3, 4])

The conversion is simply:

rray_index(
  x,
  coordinates[, 1],
  coordinates[, 2]
)

The only convention difference is that TensorFlow and ONNX coordinates are normally zero-based, while rray coordinates are one-based.

Multidimensional result shapes

The equivalence is not limited to a list of points.

Suppose x is two-dimensional and a GatherND index has dimensions:

(2, 3, 2)

The final dimension contains the coordinate components:

indices[i, j, ] = c(row, column)

The leading dimensions (2, 3) describe the arrangement of the requested points. Consequently, the result has dimensions (2, 3).

With rray_index(), split the final coordinate dimension:

rows <- indices[, , 1]
columns <- indices[, , 2]

out <- rray_index(x, rows, columns)

Both coordinate arrays have dimensions (2, 3), so their common dimensions are (2, 3). At each output point:

out[i, j] = x[rows[i, j], columns[i, j]]

This is exactly the GatherND calculation.

The general equivalence for an n-dimensional x is:

GatherND representation:
indices[g, ] = (i1, i2, ..., in)

rray representation:
axis1[g] = i1
axis2[g] = i2
...
axisn[g] = in

Then both compute:

out[g] = x[i1, i2, ..., in]

GatherND stores an array of coordinate tuples. rray_index() stores one coordinate array per axis.

Where rray_index() is more flexible

GatherND normally requires all coordinate components to be packed into one tensor and therefore already have the same leading dimensions.

rray_index() accepts separate coordinate arrays and broadcasts them:

rows <- array(c(1L, 3L), c(2, 1))
columns <- array(c(1L, 2L, 4L), c(1, 3))

rray_index(x, rows, columns)

The coordinates broadcast to (2, 3), producing:

x[1, 1]  x[1, 2]  x[1, 4]
x[3, 1]  x[3, 2]  x[3, 4]

For GatherND, you would first broadcast these arrays and then pack them into a (2, 3, 2) index tensor.

Partial GatherND

There is one apparent difference. GatherND can supply fewer coordinates than x has axes.

For a three-dimensional x, this:

indices[g, ] = (row, column)

selects an entire trailing slice:

out[g, depth] = x[row, column, depth]

rray_index() requires a coordinate for every source axis, so the same operation makes the omitted coordinate explicit:

rows[g, depth]   = row[g]
columns[g, depth] = column[g]
depths[g, depth]  = depth

out = rray_index(x, rows, columns, depths)

Thus partial GatherND is still rray_index(), with identity coordinates automatically supplied for the trailing axes.

So the clean relationship is:

full-depth GatherND
    = rray_index() with packed coordinates split apart

partial-depth GatherND
    = rray_index() with packed coordinates split apart
      plus identity coordinates for trailing axes

This also explains why rray_extract(x, point_matrix) is the simplest R-shaped form of GatherND, while rray_index() is the more general broadcastable form.

I would keep rray_index(). I would not call it rray_gather().

“Gather” sounds standard, but it is overloaded across libraries:

  • ONNX Gather means NumPy-style take().
  • ONNX GatherElements means Torch-style per-lane gather.
  • GatherND means packed coordinate tuples.
  • XLA Gather is broader still and can gather slices or windows.

A bare rray_gather() would therefore not tell users which shape contract it implements.

rray_index() also fits its actual interface better. It accepts one coordinate array per source axis:

rray_index(x, rows, columns)

A function named gather_nd() usually accepts one packed coordinate tensor:

gather_nd(x, cbind(rows, columns))

There are two other naming advantages:

  • rray_index_assign() is a natural read/write pair. rray_gather_assign() is contradictory because “gather” specifically suggests reading. The conventional write-side name would be scatter, which would split one conceptual family across unrelated names.
  • “Index” describes the general semantic operation. take, take_along_axis, and GatherND are then special shape contracts built from indexing.

I would sharpen the documentation rather than rename it:

# Pointwise coordinate indexing
rray_index(x, ...)

The first sentence could be:

rray_index() performs broadcasted pointwise coordinate indexing, also known as vectorized integer indexing or a full coordinate gather.

I am less convinced by rray_index_axis(). Its contract is specifically take_along_axis(), not every possible one-axis indexing operation. The strongest choices are:

rray_index_axis()

if consistency with the full primitive is most important, or:

rray_take_along_axis()

if recognition of the standard operation is most important.

I would avoid rray_gather_axis(), because readers could reasonably expect either Torch gather, ONNX GatherElements, TensorFlow batched gather, or ordinary take() semantics.

If rray_index() still feels too broad, rray_index_coordinates() would be more precise than rray_gather(), but probably too long. My preference remains:

rray_index()
rray_index_assign()

rray_index_axis()
rray_index_assign_axis()

I'd keep _along. I think the scheme is already right, and rray_sum_along() only looks like a loss because you're comparing it to rray_sum(), which was never going to exist.

Why the current scheme holds up

rray4 already has a convention, you just haven't written it down: every binary elementwise op is unmarked.

rray_add(x, y)
rray_multiply(x, y)
rray_greater_than(x, y)
rray_max(x, y)
rray_min(x, y)

Elementwise is the default, so it gets the plain name. Reduction is the special case, so it gets the mark. Under that reading rray_max() / rray_max_along() isn't a collision you worked around, it's the convention working.

And rray_sum() isn't missing. The elementwise "sum" of two arrays is rray_add(). Same for rray_product_along(): its binary form is rray_multiply(). There is no unmarked name being wasted, because the unmarked slot is already filled by a differently spelled word.

Compare the alternative, which original rray took: rray_max() reduces, rray_maximum() is elementwise. Two characters apart, opposite meanings, silently wrong results if you pick the wrong one. _along is seven characters that can never be misread.

What I'd actually change

Pin down what _along means, because there are two readings and they diverge as soon as you add more functions:

  1. "reduces over axes" — rray_split(), rray_stack(), rray_unstack(), rray_permute_axes() all take axes and don't get the suffix, so this is the meaning you've been using.

  2. "takes an axes argument" — contradicted by the list above.

The test case is a cumulative op. rray_cumulative_sum(x, axis = 1) takes an axis but doesn't reduce. Under reading 1 it stays unsuffixed. Under reading 2 it'd be rray_cumulative_sum_along(). Decide now and it's free, decide later and it's a rename.

Second, the docs say "axes to reduce over" while the names say "along". Numpy uses "along", so I'd make the docs match the names rather than the other way round.

Two questions

What did you want the free rray_any() / rray_all() names for? You listed them as clashes, but nothing currently occupies them. If the plan is a whole-array version returning a bare TRUE (base R semantics), that's a genuinely nice pairing and it makes the suffix look deliberate everywhere:

rray_any(x)          # TRUE
rray_any_along(x, 1) # 1 x 2 logical array

But then you owe rray_sum(), rray_mean(), and the rest, and rray_max() / rray_min() can't be elementwise anymore. That's the expensive path, and it's the only version where the elementwise pair needs renaming.

Is rray_max_along() / rray_min_along() on the roadmap? If yes, the current scheme absorbs them with no work at all, which is the strongest evidence for leaving it alone.

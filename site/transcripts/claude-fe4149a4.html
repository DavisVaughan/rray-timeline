# Names and titles across several inputs

## Goal

When a function builds one result from several inputs, the inputs must agree
on names and titles. If they don't, the function errors instead of silently
picking one input's names.

```r
jan <- array(1:2, 2, dimnames = list(c("north", "south")))
feb <- array(3:4, 2, dimnames = list(c("south", "north")))

rray_stack(jan = jan, feb = feb, .axis = 2)
#> Error in `rray_stack()`:
#> ! Can't find common names at axis 1. `jan` and `feb` have different names at position 1: "north" and "south".
```

Today this succeeds, labels every row with the order of `jan`, and the `feb`
column is silently wrong.

There is no argument to choose another behavior. To resolve a conflict, remove
the names from one input with `rray_set_names()`, which returns a view and
does not copy the data.

// Strided iterator
//
// Optimizes and assists in walking a multidimensional point space defined by
// `v_dimensions`. As it walks, it updates the current `loc`ations in one or
// more alternate subspaces defined by `v_v_strides`.
//
// We've carefully tuned this iterator for both performance and flexibility. The
// caller MUST create the iterator INSIDE the function that utilizes it. If a
// pointer to the iterator is passed around, it can destroy performance due to
// the way the result is compiled.
//
// --------------------------------------------------------------------------
// Examples
//
// For broadcasting, the dimensions you broadcast to make up the larger point
// space. This is walked in order. The original dimensions of the array make
// up the subspace. So as you walk the output's point space you can create
// `location`s back into your original array to pull from.
//
// For reducing, it's actually a special form of broadcasting. The original
// dimensions of the array are the point space. The reduced dimensions are the
// subspace. So as you walk the original array, you can create `location`s into
// the output to accumulate the reduced result at.
//
// For permuting axes, the permuted dimensions make up the point space. The
// original dimensions of the array make up the subspace. So as you walk the
// output's point space you can create `location`s back into your original
// array to pull from.
//
// --------------------------------------------------------------------------
// Optimization - First axis runs
//
// After coalescing, the iterator walks the entire first axis in one inner run
// while holding all later axes fixed. It only updates the later point
// coordinates between runs, rather than checking and carrying them after every
// element. This gives the compiler a small loop where the index and locations
// advance by fixed strides, making it much easier to optimize and vectorize.
// This loop is typically what the caller writes.
//
// Practical examples of when this is useful:
//
// - Identically shaped binary array operations. Adding two [2, 4, 5] arrays
//   coalesces to dimensions [40], so the entire operation is one first axis run
//   where both input locations advance contiguously.
//
// - Broadcasting over a later axis. Broadcasting a [2, 3] array to [2, 3, 4]
//   coalesces to dimensions [6, 4] with location strides [1, 0]. The iterator
//   performs four first axis runs of size 6, copying six contiguous values
//   before updating the later axis.
//
// - Reducing over a later axis. Reducing a [2, 3, 4] array over its third axis
//   also coalesces to dimensions [6, 4] with output strides [1, 0]. Each first
//   axis run accumulates one contiguous slice into six output locations before
//   advancing along the reduced axis.
//
// --------------------------------------------------------------------------
// Optimization - Coalescing
//
// Coalescing axes is an important optimization used to reduce the number of
// axes we have to iterate over by "merging" adjacent compatible ones. This can
// improve performance by 3-5x on its own in some cases.
//
// Practical examples of when this is useful:
//
// - Identically shaped binary array operations. Adding two arrays with
//   dimensions [2, 4, 5] gives both inputs strides [1, 2, 8]. All adjacent axes
//   coalesce (2 * 1 = 2, 4 * 2 = 8) into one dimension [40] with stride [1],
//   resulting in one flat vectorizable loop.
//
// - Scalar broadcasting across an entire array. Adding a scalar to a [2, 4, 5]
//   array gives the array strides [1, 2, 8] and the scalar strides [0, 0, 0].
//   Both coalesce completely, producing a [40] loop with array stride [1] and
//   scalar stride [0].
//
// - Contiguous adjacent axes within a broadcast operation. Broadcasting a
//   [2, 3] array over point dimensions [2, 3, 4] produces location strides
//   [1, 2, 0]. The adjacent axes 1 and 2 coalesce (2 * 1 = 2) into size 6,
//   leaving dimensions [6, 4] and strides [1, 0].
//
// - Contiguous regions within a reduction. Reducing a [2, 3, 4] array over its
//   third axis maps into a [2, 3] result using location strides [1, 2, 0].
//   Coalescing produces dimensions [6, 4], making it the same as the broadcast
//   example above.
//

//   have strides [0, 1, 3]. The dimension 1 first axis is absorbed into the
//   dimension 3 second axis, adopting stride 1, after which the dimension 4
//   third axis also coalesces. The result is one dimension [12] with stride
//   [1]. Note that this isn't broadcasting. This is when both input and output
//   have an axis that stays dimension 1, which is somewhat rare.
//

// output dimensionality, so it's all or nothing.
//
// --------------------------------------------------------------------------

//
// After coalescing, the first axis is walked by the inner loop. A stride of 0
// on this axis means that a subspace location stays fixed while the point space
// moves along it. Broadcasting uses this to reuse an input value. Reducing uses
// it to accumulate into the same output location. A zero stride on a later axis
// does not use this path because later axes advance between inner runs.
//

//   array coalesces to point dimensions [40], with array strides [1] and scalar
//   strides [0]. The scalar location stays fixed while the array and output

// Create a read-only ALTREP view of an R object's data
//
// Useful when ONLY modifying the attributes of the new object, and NEVER the
// underlying data.
//
// The ALTREP view itself is immediately marked as immutable with
// `MARK_NOT_MUTABLE()`. This is extremely important! It ensures that R won't
// ever ask for a writable `DATAPTR()` without first calling `Duplicate()`.
//
// Note that R will VERY often use `REAL()` instead of `REAL_RO()` when it only
// needs a read-only pointer. This is due to `REAL_RO()` being a newer idea that
// was only introduced with ALTREP, and a lot of historical code hasn't been
// ported over. Because of that, our `DATAPTR()` ALTREP methods must return a
// pointer even in the `writable` case, but we expect that R (and all packages)
// hold up their side of the bargain by only actually writing to this pointer
// when they fully own it or when there are `NO_REFERENCES()`, which won't be
// the case since we've used `MARK_NOT_MUTABLE()`. The `NO_REFERENCES()` case is
// relevant for `x + y + 1` where R will attempt to reuse `x + y`'s temporary
// result since there aren't any other owners. We don't want
// `rray_set_dimensions(x) + 1` to look reusable!
r_obj* r_view(r_obj* x) {
  R_altrep_class_t cls = view_class(r_typeof(x));

  // If `x` is a view, take its original data and view that instead. This
  // avoids a proliferation of nested views. Refcounts on `x` itself should also
  // still be correct - each view looks like an individual user of `x`.
  r_obj* data = is_view(x) ? view_data(x) : x;

  // Reference count on `data` is bumped when we create the view here.
  // It now looks at least "referenced", but not necessarily "shared".
  r_obj* out = KEEP(R_new_altrep(cls, data, r_null));

  // The all important immutable marking of `out`, preventing any downstream C
  // code from requesting a writable pointer without duplicating first.
  MARK_NOT_MUTABLE(out);

  FREE(1);
  return out;
}

# Long vector tests

## Goal

Every exported function gets at least one basic test on an array with more
than `.Machine$integer.max` elements. Each test starts with
`skip_if_not_testing_long_vectors()`, so they only run when asked:

```sh
RRAY_TESTING_LONG_VECTORS=true Rscript -e "devtools::test()"
```

A few functions can't handle long vectors today. Those are fixed first, each
with its own test.

## How each test looks

```r
test_that("works with long vectors", {
  skip_if_not_testing_long_vectors()

  x <- array(as.raw(0), c(2^16, 2^15))
  x[length(x)] <- as.raw(1)

  out <- rray_reverse(x, axes = 2)

  expect_identical(dim(out), dim(x))
  expect_identical(out[2^16], as.raw(1))
})
```

- Use dimensions `c(2^16, 2^15)`. That is exactly `2^31` elements, so the last
  element sits at location `2^31`, the first location past
  `.Machine$integer.max`.

- Put one different value (the marker) at a location past
  `.Machine$integer.max`, usually the last one. Then check that the result
  has it in the right place. If any index gets cut down to an `int`, the
  marker shows up in the wrong place or not at all.

- Check a few positions with `[`. Never compare against a full base R result,
  since that doubles the memory.

- Use raw wherever the function accepts it (1 byte per element, 2 GiB). The
  numeric and logical functions don't accept raw, so they use logical (4
  bytes per element, 8 GiB).

- When the output is a different type than the input, keep the peak memory
  low by building the long output from small inputs through broadcasting.

- The test goes in `tests/testthat/test-{name}.R`, after the tests it is most
  like. Name it `"works with long vectors"`, or something more specific when a
  file has more than one.

- Memory below is the peak for one test. The heaviest is
  `rray_cumulative_prod()` at 24 GiB.

## Fixes needed first

All but the last were confirmed by running them on a 2^31 element raw array.
Each one ends in rlang's internal error
`Result can't be represented as 'int'`.

1. Plain vectors with no `dim`. `vec_as_array()` in `src/utils.c` turns the
   length into a 1D `dim` with `r_ssize_as_integer()`. A 1D array can't have
   more than `.Machine$integer.max` elements, so this must become a clear
   error. It affects every function, through `arg_as_array()`, and also the
   coordinate arrays of `rray_index()`, which go through `vec_as_array()`
   directly.

   ```r
   rray_size(raw(2^31))
   #> Error: Result can't be represented as `int`.
   #> This is an internal error that was detected in the rray package.
   ```

2. `rray_extract()` selecting more than `.Machine$integer.max` values. The
   result is a 1D array, so this can't work. The fix is a clear error, raised
   before the result is allocated. The `r_ssize_as_integer()` call is in
   `rray_extract()` in `src/extract.c`. The test helper
   `rray_subscript_as_list()` in `src/subscript.c` has the same call and
   should get the same check.

   ```r
   rray_extract(x, TRUE)
   ```

3. `rray_extract_assign()` with a selection of more than
   `.Machine$integer.max` values. This one should work. The size only goes
   through `int` so that it can be passed to `check_broadcastable()`, in
   `rray_extract_assign()` in `src/extract-assign.c`. A selection that large
   can only take a `value` of size 1, so check that directly when the size
   doesn't fit in an `int`.

   ```r
   rray_extract_assign(x, TRUE, as.raw(2))
   ```

4. `rray_slice()` and `rray_slice_assign()` with an index that selects more
   than `.Machine$integer.max` positions on one axis. That axis can't hold
   them, so this must become a clear error. Both functions call
   `r_ssize_as_integer()` on each axis subscript size (`src/slice.c` and
   `src/slice-assign.c`). The `rray_slice_*()` helpers, `rray_rep()`,
   `rray_rep_each()`, `rray_roll()`, and `rray_reverse()` all go through
   `rray_slice()`, but they build their own indices, which always fit.

   ```r
   rray_slice(array(as.raw(0), c(1, 1)), rep(1L, 2^31), 1L)
   ```

5. `rray_locate_max()` and `rray_locate_min()` along a first axis of exactly
   `.Machine$integer.max`. In the `RRAY_LOCATE` loop in `src/locate.c`, the
   `int position` counter steps once past the last element, which overflows
   to `.Machine$integer.max + 1`. Signed overflow is undefined behavior in C,
   even though the value is never used. Make `position` an `r_ssize` and cast
   it when storing. Found by reading the code, not by running it, since the
   result most likely comes out right anyway.

## Key GitHub Issue

The main issue is that `np.argmax`, `np.argmin`, `np.take_along_axis`, and `np.put_along_axis` should support tuple `axis` arguments similar to how `np.max` and `np.min` do.

## Specification

The specification for tuple argmax is that `np.take_along_axis(x, np.argmax(x, axis=axis, keepdims=True), axis=axis)` should always equal `np.max(x, axis=axis, keepdims=True)`.

## Background

Historically, `argmax` has not supported multiple axes, even in the Python API. However, the `max` operator in the Python API has support for multiple axes (i.e., a tuple of integers).

## Related Issues

The discussion also references issues #25622 and #9283, where related proposals and constraints for this feature have been discussed in detail.

This GitHub issue (#25623) represents an enhancement request to bring feature parity between `argmax`/`argmin` and their corresponding `max`/`min` functions by enabling tuple axis support.

There was never a decision to leave it out. argmax missed an upgrade that the other reductions got in 2012, and every later attempt to add it stalled on one question: what should it return?

1. Multi-axis support was added to ufuncs, and argmax is not a ufunc

NumPy 1.7 (2012) added axis=(i, j). The release notes scope it to ufunc reductions only:

Any ufunc.reduce function call, as well as other reductions like sum, prod, any, all, max and min support the ability to choose a subset of the axes to reduce over.

max is np.maximum.reduce, so it came along for free. argmax has its own code path. In calculation.c, PyArray_ArgMax moves the one axis to the end with PyArray_Transpose, makes a contiguous copy, and calls a per-dtype argmax function on each 1-D row. That design only works for a single axis, so the new tuple support never reached it.

2. The C API took a single int axis

In #6296 (2015), a user asked for multi-axis support in the C API. Charles Harris (charris, a core maintainer) replied:

we need to keep the C API stable. Probably the best way to go is add a new function to the API. The multiple axis option is fairly new as Numpy counts "new", and not completely implemented.

The same thread has the two technical objections:

  • Stephan Hoyer: it could be done with a transpose, a reshape and unravel_index, but then passing a tuple would have to return a tuple.

  • Sebastian Berg: "argmax is iteration order dependend, most other reduction like functions (max, percentile, etc.) are not." With ties, which index wins depends on the order you scan the reduced axes, so that order has to be defined.

3. The return type was never settled

A multi-axis argmax cannot return one integer per output cell unless you pick a format: a flat index into the reduced block, or one index array per axis. In #9283 (2017), Eric Wieser proposed the per-axis version:

  • axis=a returns an array

  • axis=(a,) returns (array,)

  • axis=(a, b) returns a tuple of two arrays

The rule he wanted to hold was arr[argmax(arr, axes, keepdims=True)] == max(arr, keepdims=True). People agreed with it, but no one wrote the code.

In #12516 (2018), Marten van Kerkwijk (mhvk) noted that a planned gufunc version of argmax could not easily express multiple axes either: "one would also need to think how one would return the output."

4. The array API standard copied the gap

The first draft of the searching functions spec (data-apis/array-api#23, 2020) flagged the problem:

Some discrepancy with max in that multiple axes cannot be specified (CuPy supports, but no one else) ... Should this be reconciled?

Athan Reines (kgryte, the spec author) asked again later in the thread, "should argmax and argmin accept a tuple of ints for the axis keyword?", and got no answer. The spec went ahead with only keepdims added. From memory, the spec's argmax still takes axis: Optional[int]; I didn't recheck the current spec text.

5. Still open

  • #6296 (2015), #9283 (2017) and #25623 (2024) are all still open.

  • #25623 was filed because a SciPy PR was blocked on it. It widened the request to cover take_along_axis and put_along_axis too, since the result is only useful if those functions accept the same tuple of axes.

Summary

The cause is an accident of implementation. Nobody rejected the idea on principle. If you add this to rray4, you'll face the same two decisions NumPy never made:

  • Return format: a flat index into the reduced block, or one index per reduced axis.

  • Tie order: which of equal values wins, which depends on the order you scan the reduced axes.

Here is one small array that shows all three problems. I ran it in R to check the values.

x <- array(c(1, 5, 5, 2, 0, 3, 0, 1, 2, 3, 9, 4), dim = c(2, 3, 2))
x
#> , , 1
#>      [,1] [,2] [,3]
#> [1,]    1    5    0
#> [2,]    5    2    3
#>
#> , , 2
#>      [,1] [,2] [,3]
#> [1,]    0    2    9
#> [2,]    1    3    4

Take the argmax over axes 1 and 2 (the function name rray_arg_max(x, axes = c(1, 2)) is made up). That leaves one answer per slice of axis 3:

  • Slice 1: the max is 5, and it appears twice, at [2, 1] and [1, 2].

  • Slice 2: the max is 9, and it appears once, at [1, 3].

1. What to return

Each answer is a position in a 2 x 3 block. There are three reasonable ways to return it:

# A: flat index into the 2 x 3 block
c(2, 5)

# B: one index vector per reduced axis
list(c(2, 1), c(1, 3))

# C: a matrix, one row per result, one column per reduced axis
rbind(c(2, 1), c(1, 3))

  • A returns a plain integer array, the same shape a single-axis argmax gives. But 5 means nothing until you convert it back with the block's dimensions.

  • B is Eric Wieser's proposal. It is the only option that works directly with a take_along_axis()-style lookup, so you can check x[argmax] == max.

  • C is what which(arr.ind = TRUE) returns. It is familiar in R, but it only works when a single axis is left over.

2. Which tie wins

Slice 1 has two 5s. Which one you find first depends on the order you scan the block:

# axis 1 varies fastest (R, column-major)
c(2, 1)

# axis 2 varies fastest (NumPy default, row-major)
c(1, 2)

A single-axis argmax has only one scan order, so the question never came up before. This is Sebastian Berg's point from #6296.

3. Does the order of axes matter?

Should axes = c(2, 1) give the same result as axes = c(1, 2)? It changes two things:

  • Output order: under B or C, whether you get axis 2's indices first.

  • Tie order: whether axis 2 is now the fastest-varying axis, which would turn slice 1's answer into c(1, 2).

max() doesn't care about the order of axes, so it never had to answer this.

My recommendation

For rray4 I'd pick:

  • B as the return format.

  • Column-major scan order, to match R and which.max().

  • Sorted axes, so their order changes nothing and both answers match max().

This combination is the only one where rray_max(x, axes) and the value at the argmax can always be checked against each other.

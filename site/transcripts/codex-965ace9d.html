You are not crazy. The alternate design is valid.

Because R is column-major, the reduced axes should move to the front:

permutation <- c(reduced_axes, retained_axes)

For dim = c(2, 3, 4) and axes = 2, that gives c(2, 1, 3). Each three-element reduction group then occupies one contiguous block. The reducer can walk the permuted x linearly and write each result sequentially.

The catch is that the current code already writes out sequentially in reduce.h. Its input traversal is also exactly the order that rray_permute_axes() would use to gather the permuted copy. Permuting therefore adds:

  1. The same irregular read from the original x.
  2. A full-size write into the permuted x.
  3. Another one or more full reads during reduction.

It could theoretically help double mean because that makes two passes over each group. However, those passes happen consecutively, so the second pass often finds the group in cache already. Logical and integer means only make one pass, so permutation has almost no chance of paying off.

I tried the composition rray_permute_axes() followed by rray_mean_along():

Input and reduction Current Permute first Extra allocation
1000 x 1000, axis 2 ~1.8 ms ~3.8 ms 7.6 MiB
4000 x 4000, axis 2 ~66 ms ~87 ms 122 MiB
400 x 200 x 200, axis 2 ~28 ms ~43 ms 122 MiB

A specialized implementation would remove some validation and metadata work, but not the large copy, so I would expect the conclusion to remain the same.

One useful related fast path exists: when the reduced axes are already a leading sequence, such as 1 or c(1, 2), groups are already contiguous and no permutation is needed. The current coalesced inner plan essentially reaches that layout already.

So: correct design, pleasantly simpler loop, but probably slower for mean and clearly worse for one-pass reducers. It may become worthwhile for a future reducer that makes many passes over each group.

Conceptually, yes. rray_reduce_grouped() traverses x in the same logical order as:

rray_permute_axes(x, c(reduced_axes, retained_axes))

But I would not call it rray_reduce_permuted(). Nothing is actually permuted, and that name strongly suggests an allocation or a permuted input.

grouped describes the important contract: it completes one reduction group before moving to the next. The permuted order is how that grouping is achieved.

If you want a more concrete name, rray_reduce_slices() or rray_reduce_by_slice() would also fit. I think rray_reduce_grouped() remains the least misleading.

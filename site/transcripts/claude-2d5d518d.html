10	// Strided iterator
11	//
12	// Optimizes and assists in walking a multidimensional point space defined by
13	// `v_dimensions`. As it walks, it updates the current `loc`ations in one or
14	// more alternate subspaces defined by `v_v_strides`.
15	//
16	// We've carefully tuned this iterator for both performance and flexibility. The
17	// caller MUST create the iterator INSIDE the function that utilizes it. If a
18	// pointer to the iterator is passed around, it can destroy performance due to
19	// the way the result is compiled.
20	//
21	// --------------------------------------------------------------------------
22	// Examples
23	//
24	// For broadcasting, the dimensions you broadcast to make up the larger point
25	// space. This is walked in order. The original dimensions of the array make
26	// up the subspace. So as you walk the output's point space you can create
27	// `location`s back into your original array to pull from.
28	//
29	// For reducing, it's actually a special form of broadcasting. The original
30	// dimensions of the array are the point space. The reduced dimensions are the
31	// subspace. So as you walk the original array, you can create `location`s into
32	// the output to accumulate the reduced result at.
33	//
34	// For permuting axes, the permuted dimensions make up the point space. The
35	// original dimensions of the array make up the subspace. So as you walk the
36	// output's point space you can create `location`s back into your original
37	// array to pull from.
38	//
39	// --------------------------------------------------------------------------
40	// Optimization - First axis runs
41	//
42	// After coalescing, the iterator walks the entire first axis in one inner run
43	// while holding all later axes fixed. It only updates the later point
44	// coordinates between runs, rather than checking and carrying them after every
45	// element. This gives the compiler a small loop where the index and locations
46	// advance by fixed strides, making it much easier to optimize and vectorize.
47	// This loop is typically what the caller writes.
48	//
49	// Practical examples of when this is useful:
50	//
51	// - Identically shaped binary array operations. Adding two [2, 4, 5] arrays
52	//   coalesces to dimensions [40], so the entire operation is one first axis run
53	//   where both input locations advance contiguously.
54	//
55	// - Broadcasting over a later axis. Broadcasting a [2, 3] array to [2, 3, 4]
56	//   coalesces to dimensions [6, 4] with location strides [1, 0]. The iterator
57	//   performs four first axis runs of size 6, copying six contiguous values
58	//   before updating the later axis.
59	//
60	// - Reducing over a later axis. Reducing a [2, 3, 4] array over its third axis
61	//   also coalesces to dimensions [6, 4] with output strides [1, 0]. Each first
62	//   axis run accumulates one contiguous slice into six output locations before
63	//   advancing along the reduced axis.
64	//
65	// --------------------------------------------------------------------------
66	// Optimization - Coalescing
67	//
68	// Coalescing axes is an important optimization used to reduce the number of
69	// axes we have to iterate over by "merging" adjacent compatible ones. This can
70	// improve performance by 3-5x on its own in some cases.
71	//
72	// Practical examples of when this is useful:
73	//
74	// - Identically shaped binary array operations. Adding two arrays with
75	//   dimensions [2, 4, 5] gives both inputs strides [1, 2, 8]. All adjacent axes
76	//   coalesce (2 * 1 = 2, 4 * 2 = 8) into one dimension [40] with stride [1],
77	//   resulting in one flat vectorizable loop.
78	//
79	// - Scalar broadcasting across an entire array. Adding a scalar to a [2, 4, 5]
80	//   array gives the array strides [1, 2, 8] and the scalar strides [0, 0, 0].
81	//   Both coalesce completely, producing a [40] loop with array stride [1] and
82	//   scalar stride [0].

86	//   [1, 2, 0]. The adjacent axes 1 and 2 coalesce (2 * 1 = 2) into size 6,

89	// - Contiguous regions within a reduction. Reducing a [2, 3, 4] array over its

93	//

98	//   [1]. Note that this isn't broadcasting. This is when both input and output
99	//   have an axis that stays dimension 1, which is somewhat rare.
100	//
101	// Note that all sets of strides must be coalescible, as coalescing changes the

104	// --------------------------------------------------------------------------
105	// Optimization - Fixed zero stride paths

Yes. size, v_dimensions, dimensionality, v_strides, and n never change after rray_run_iterator() returns, so they can all be const. It just isn't a one-word change.

Why const alone won't compile. Right now the constructor declares an empty it and fills it in field by field. Coalescing also edits it.v_dimensions and it.v_strides in place. Once a member is const, it can only be set when the struct is first created, so each of those writes becomes a compile error.

What works. Build the values in local variables first, then create the iterator in one go with a designated initializer ({.size = size, ...}). A plain array member can't be set from another array that way, so the two arrays would be wrapped in a small nested struct:

struct rray_run_iterator_shape {
  r_ssize v_dimensions[RRAY_MAX_DIMENSIONALITY];
  int dimensionality;
  r_ssize v_strides[RRAY_MAX_DIMENSIONALITY * RRAY_MAX_INPUTS];
  r_ssize n;
};

struct rray_run_iterator {
  const r_ssize size;
  const struct rray_run_iterator_shape shape;

  r_ssize v_point[RRAY_MAX_DIMENSIONALITY];
  r_ssize start;
  r_ssize end;
  r_ssize v_loc[RRAY_MAX_INPUTS];
};

The constructor fills a local shape, runs rray__run_iterator_axes_coalesce() on it, and then does struct rray_run_iterator it = {.size = size, .shape = shape};. Returning by value still works, and so does every caller, because they all write struct rray_run_iterator it = rray_run_iterator1(...). That line creates a new struct rather than assigning to an existing one.

I checked this with a small test file in my scratch folder. The const version compiles, and both a write to size and a write to shape.v_dimensions[0] are rejected by the compiler.

Costs:

  • Every read gets longer: it->shape.v_dimensions, it->shape.n, and so on. Most of these are in the three next helpers, which already copy the fields into const locals.

  • It doesn't make anything faster. The iterator is a local that gets fully inlined, and the compiler already knows the next loops never write to those fields. The gain is only a compile error if someone writes to them by mistake.

  • All the writes outside the constructor are already in this header, and callers only use the read-only accessor functions. So the risk it guards against is small.

My recommendation: it's a fair change if you want the compiler to enforce the rule, but it's tidying, not a fix. I'd only do it if the it->shape. prefix doesn't bother you. Want me to make the change?

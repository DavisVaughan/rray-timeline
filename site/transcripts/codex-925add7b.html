static r_obj* rray_rep_impl(

  const int dimension = v_dimensions[axis - 1];

  r_memcpy(v_out_dimensions, v_dimensions, sizeof(int) * dimensionality);
  v_out_dimensions[axis - 1] = out_dimension;

    v_out_dimensions,
    dimensionality,
    error_call

    inner *= v_dimensions[i];

static r_obj* arg_as_times(
  r_obj* times,
  r_ssize size,
  struct rray_arg* arg,
  struct r_lazy error_call
) {

  const r_ssize times_size = r_length(times);

The good part is the block model in rep.c:

  • rray_rep() repeats a block containing the whole axis.
  • rray_rep_each() repeats smaller blocks containing one axis slice.
  • Character and list vectors need a write barrier, while atomic vectors can copy memory directly.

The difficulty comes from representing this as four kernels:

  • uniform atomic
  • uniform barrier
  • ragged atomic
  • ragged barrier

That produces two dispatchers, four macros, fourteen thin functions, and fourteen declarations. The reader encounters the same traversal several times with small differences. The macros also silently depend on names such as x, out, block, times, and outer from the surrounding function. Their signatures do not tell you their real inputs.

I think the simplest structure is one general traversal:

block_size = each ? inner : inner * dimension;
blocks_per_outer = each ? dimension : 1;

for (outer_i = 0; outer_i < outer; ++outer_i) {
  for (block_i = 0; block_i < blocks_per_outer; ++block_i) {
    times = v_times[times_size == 1 ? 0 : block_i];

    for (repeat_i = 0; repeat_i < times; ++repeat_i) {
      copy_block();
    }
  }
}

Then retain only two body macros:

  • Atomic: copy_block() uses r_memcpy().
  • Barrier: copy_block() loops over the block using r_chr_poke() or r_list_poke().

  • one barrier body macro

  • no separate “ragged” family

3:## Recommendation
4:
5:Add two functions:
6:
7:```r
8:rray_roll(x, ..., n, axes)
9:rray_roll_each(x, ..., n, axis)
10:```
11:
12:Both move elements along an axis. An element pushed off one end comes back on
13:the other.
14:
15:- `rray_roll()` rolls one or more axes, with one shift per axis. Every lane
16:  through an axis moves by the same amount, so each output position has exactly
17:  one source position, and names roll with the data.
18:
19:- `rray_roll_each()` rolls one axis, with one shift per lane. Lanes can move by
20:  different amounts, so an output position can come from different source
21:  positions in different lanes. Names on the rolled axis are always dropped.
22:
23:The split mirrors pairs the package already has:
24:
25:| Every lane moves together | Each lane moves on its own |
26:|---|---|
27:| `rray_slice_axis()` | `rray_index_axis()` |
28:| `rray_rep()` | `rray_rep_each()` |
29:| `rray_roll()` | `rray_roll_each()` |
30:
31:The function decides what happens to names. The size or values of `n` never do.
32:A caller who wants names kept calls `rray_roll()`.
33:
34:## Terms
35:
36:- **Lane.** One run of elements along the rolled axis, with every other
37:  coordinate held fixed. For a matrix and `axis = 2`, each row is a lane. For
38:  dimensions `(A, B, C)` and `axis = 2`, there are `A * C` lanes, each of
39:  length `B`.
40:
41:- **Lane dimensions.** The dimensions of `x` with the rolled axis set to 1. For
42:  `(A, B, C)` and `axis = 2`, they are `(A, 1, C)`. There is one lane per
43:  element of an array with these dimensions.
44:
45:- **Shift.** The value of `n` for one lane or one axis. It can be negative,
46:  zero, or larger than the dimension.
47:
48:## Shared rules
49:
50:### Direction
51:
52:A positive shift moves elements toward higher positions, as in NumPy:
53:
54:```r
55:rray_roll(1:5, n = 2, axes = 1)
56:# [1] 4 5 1 2 3
57:```
58:
59:A negative shift moves them toward lower positions:
60:
61:```r
62:rray_roll(1:5, n = -1, axes = 1)
63:# [1] 2 3 4 5 1
64:```
65:
66:### Wrapping
67:
68:A shift is reduced modulo the dimension `d` of the rolled axis, into `[0, d)`:
69:
70:```text
71:k = n mod d
72:out[..., j, ...] = x[..., (j - k) mod d, ...]
73:```
74:
75:So a shift of `7` on a dimension of `5` is a shift of `2`, and a shift of `-1`
76:is a shift of `4`:
77:
78:```r
79:rray_roll(1:5, n = 7, axes = 1)
80:# [1] 4 5 1 2 3
81:```
82:
83:A shift of `0`, or any multiple of `d`, leaves the axis unchanged.
84:
85:### Values of `n`
86:
87:- Integers, and anything that casts losslessly to integer. Doubles holding
88:  whole numbers work and `1.5` is an error. Logicals work too, with `TRUE` as
89:  `1`, the same as `axes` and `times` accept them today.
90:
91:- Any sign and any magnitude within the R integer range, which is
92:  `-2147483647` to `2147483647`. `-2147483648` is reserved for `NA`, and a
93:  double outside the range fails the cast.
94:
95:- No missing values.
96:
97:- No classed objects.
98:
99:### Zero dimensions
100:
101:When the rolled axis has dimension 0, there is nothing to move. Every shift is
102:valid, and it is still validated. The result equals `x`, with the names rule of
103:the function applied.
104:
105:### Bare vectors
106:
107:`x` goes through `arg_as_array()`, so a bare vector is a one-dimensional array
108:and its names move to `dimnames`. The result is always an array.
109:
110:## `rray_roll()`
111:
112:```r
113:rray_roll(x, ..., n, axes)
114:```
115:
116:### Arguments
117:
118:- `x`: an array or bare vector.
119:
120:- `...`: must be empty. It forces `n` and `axes` to be named, as in
121:  `rray_rep()`.
122:
123:- `n`: a bare integer vector of size 1 or the size of `axes`, validated the
124:  same way as `axes`. A size 1 `n` is used for every axis in `axes`. Otherwise
125:  `n[[i]]` is the shift for `axes[[i]]`. `n` can't have attributes, so names,
126:  dimensions, and classes are all errors. Arrays of per-lane shifts belong to
127:  `rray_roll_each()`.
128:
129:- `axes`: a bare integer vector of axes. Required, with no default. Any order.
130:  An axis can't appear twice. `integer()` is allowed and rolls nothing.
131:
132:The result has the type, dimensions, and dimensionality of `x`.

899	Notes:
900	
901	- `n` is fully validated before the size check, with `check_broadcastable()`
902	  from `src/broadcast.h`. It checks the dimensions without allocating and gives
903	  the same messages as `rray_broadcast()`. So a bad `n` errors even when `x` is
904	  empty.
905	
906	- Nothing proportional to the lane count is allocated for an empty `x`. When
907	  the rolled axis has dimension 0, the lane dimensions can still be huge, for
908	  example `(100000, 1, 100000)` for `x` with dimensions `(100000, 0, 100000)`.
909	  Broadcasting `n` there would allocate ten billion integers for an empty
910	  result.
911	
912	- `block_size`, `n_groups`, and `n_lanes` are computed only when `size > 0`.
913	  Each is then a product of factors of `size`, so none can overflow. With a
914	  zero dimension elsewhere, a product of the other dimensions could overflow
915	  `r_ssize`.
916	
917	- `rray_broadcast()` returns its input unchanged when the dimensions already
918	  match. That input can be the caller's own `n`, so never write into it. The
919	  reduced shifts go into a separate `shifts` table.
920	
921	- `shifts` has `size / axis_dimension` elements, which is at most the size of
922	  `x` and usually much smaller. Reducing once per lane keeps `%` out of the main
923	  loop.
924	
925	- Skipping the fill when `size` is 0 also avoids reducing by an
926	  `axis_dimension` of 0.
927	
928	- `rray_reduce_names()` drops names on the given axes and keeps the rest. It
929	  returns `NULL` when nothing survives. Its meaning here is exactly the names
930	  rule for `rray_roll_each()`.
931	
932	#### The fill
933	
934	`rray_roll_each_fill()` switches on `r_typeof(x)` to seven cores, like
935	`rray_rep_fill_varying()`. Each core is one macro call, with
936	`RRAY_ROLL_EACH_FILL_ATOMIC` for logical, integer, double, complex, and raw,
937	and `RRAY_ROLL_EACH_FILL_BARRIER` for character and list. Undefine both after
938	the cores.
939	
940	The loop walks `out` in column-major order, so every write is sequential:
941	
942	```c
943	const CTYPE* v_x = CONST_DEREF(x);
944	CTYPE* v_out = DEREF(out);
945	
946	const r_ssize group_size = block_size * axis_dimension;
947	
948	r_ssize out_i = 0;
949	
950	for (r_ssize group = 0; group < n_groups; ++group) {
951	  const CTYPE* v_x_group = v_x + group * group_size;
952	  const int* v_group_shifts = v_shifts + group * block_size;
953	
954	  for (int j = 0; j < axis_dimension; ++j) {
955	    for (r_ssize i = 0; i < block_size; ++i) {
956	      const int shift = v_group_shifts[i];
957	      const int source =
958	        (j >= shift) ? j - shift : j - shift + axis_dimension;
959	
960	      v_out[out_i] = v_x_group[(r_ssize) source * block_size + i];
961	      ++out_i;
962	    }
963	  }
964	}
965	```
966	
967	The barrier version replaces the assignment with `POKE(out, out_i, ...)`.
968	
969	Reads stay inside the current group, so they stay close in memory. When `axis`
970	is 1, `block_size` is 1 and each lane is contiguous. A lane by lane path with
971	two `memcpy()` calls would be faster there. Add it only if a benchmark against
972	the general loop shows a real gap.

// Strided iterator plan
//
// Optimizes and assists in walking a multidimensional point space defined by
// `v_dimensions`. As it walks, it updates a user provided `start` in an
// alternate subspace defined by `v_strides`.
//
// For performance and flexibility, the user is responsible for managing the run
// loop along the first axis. We've tried many alternative approaches but they
// tend to tank performance quickly as you increase the level of abstractions.
//
// The plan holds only immutable state. The positions that change as it walks
// are managed by the caller. This lets the compiler keep these positions in
// registers, which has significant performance implications.
//
// --------------------------------------------------------------------------
// Examples
//
// For broadcasting, the dimensions you broadcast to make up the larger point
// space. This is walked in order. The original dimensions of the array make
// up the subspace. So as you walk the output's point space you can create
// `location`s back into your original array to pull from.
//
// For reducing, it's actually a special form of broadcasting. The original
// dimensions of the array are the point space. The reduced dimensions are the
// subspace. So as you walk the original array, you can create `location`s into
// the output to accumulate the reduced result at.
//
// For permuting axes, the permuted dimensions make up the point space. The
// original dimensions of the array make up the subspace. So as you walk the
// output's point space you can create `location`s back into your original
// array to pull from.
//
// --------------------------------------------------------------------------
// Optimization - First axis runs
//
// After coalescing, the iterator walks the entire first axis in one inner run
// while holding all later axes fixed. It only updates the later point
// coordinates between runs, rather than checking and carrying them after every
// element. This gives the compiler a small loop where the index and locations
// advance by fixed strides, making it much easier to optimize and vectorize.
//
// Practical examples of when this is useful:
//
// - Identically shaped binary array operations. Adding two [2, 4, 5] arrays
//   coalesces to dimensions [40], so the entire operation is one first axis run
//   where both input locations advance contiguously.
//
// - Broadcasting over a later axis. Broadcasting a [2, 3] array to [2, 3, 4]
//   coalesces to dimensions [6, 4] with location strides [1, 0]. The iterator
//   performs four first axis runs of size 6, copying six contiguous values
//   before updating the later axis.
//
// - Reducing over a later axis. Reducing a [2, 3, 4] array over its third axis
//   also coalesces to dimensions [6, 4] with output strides [1, 0]. Each first
//   axis run accumulates one contiguous slice into six output locations before
//   advancing along the reduced axis.
//
// --------------------------------------------------------------------------
// Optimization - Coalescing
//
// Coalescing axes is an important optimization used to reduce the number of
// axes we have to iterate over by "merging" adjacent compatible ones. This can
// improve performance by 3-5x on its own in some cases.
//
// Practical examples of when this is useful:
//
// - Identically shaped binary array operations. Adding two arrays with
//   dimensions [2, 4, 5] gives both inputs strides [1, 2, 8]. All adjacent axes
//   coalesce (2 * 1 = 2, 4 * 2 = 8) into one dimension [40] with stride [1],
//   resulting in one flat vectorizable loop.
//
// - Scalar broadcasting across an entire array. Adding a scalar to a [2, 4, 5]
//   array gives the array strides [1, 2, 8] and the scalar strides [0, 0, 0].
//   Both coalesce completely, producing a [40] loop with array stride [1] and
//   scalar stride [0].
//
// - Contiguous adjacent axes within a broadcast operation. Broadcasting a
//   [2, 3] array over point dimensions [2, 3, 4] produces location strides
//   [1, 2, 0]. The adjacent axes 1 and 2 coalesce (2 * 1 = 2) into size 6,
//   leaving dimensions [6, 4] and strides [1, 0].
//
// - Contiguous regions within a reduction. Reducing a [2, 3, 4] array over its
//   third axis maps into a [2, 3] result using location strides [1, 2, 0].
//   Coalescing produces dimensions [6, 4], making it the same as the broadcast
//   example above.
//
// - Point-space dimensions of size 1. Output point dimensions of [1, 3, 4] can
//   have strides [0, 1, 3]. The dimension 1 first axis is absorbed into the
//   dimension 3 second axis, adopting stride 1, after which the dimension 4
//   third axis also coalesces. The result is one dimension [12] with stride
//   [1]. Note that this isn't broadcasting. This is when both input and output
//   have an axis that stays dimension 1, which is somewhat rare.
//
// For iterator2, note that both sets of location strides must be coalescible,
// as coalescing changes the output dimensionality, so it's all or nothing.
//
// --------------------------------------------------------------------------
// Optimization - Fixed zero stride paths
//
// After coalescing, the first axis is walked by the inner loop. A stride of 0
// on this axis means that a subspace location stays fixed while the point space
// moves along it. Broadcasting uses this to reuse an input value. Reducing uses
// it to accumulate into the same output location. A zero stride on a later axis
// does not use this path because later axes advance between inner runs.
//
// When the inner loop receives the stride as a runtime value, the compiler
// can't prove that the location is fixed and falls back to a scalar loop. The
// public iteration macros check for a zero stride and pass a literal 0 to a
// specialized path. This lets the compiler see that the location does not
// change. For binary operations, it can then hoist the fixed load out of the
// loop and vectorize the remaining stride 1 work.
//
// Practical examples of when this is useful:
//
// - Scalar broadcasting across an entire array. Adding a scalar to a [2, 4, 5]
//   array coalesces to point dimensions [40], with array strides [1] and scalar
//   strides [0]. The scalar location stays fixed while the array and output
//   advance contiguously. The same path is used by arithmetic, comparison,
//   equality, and extrema operations.
//
// - Row broadcasting within a matrix. Adding a [1, 4] row to a [2, 4] array
//   gives the array strides [1, 2] and row strides [0, 1]. Each inner run
//   therefore reuses one row value while the array and output advance
//   contiguously.
//
// - Higher dimensional row broadcasting. Adding a [1, 3, 4] array to a
//   [2, 3, 4] array coalesces to dimensions [2, 12], with array strides [1, 2]
//   and broadcast strides [0, 1]. Each of the 12 inner runs uses the fixed
//   path.
//
// - Shared leading dimensions of size 1. Adding [1, 1, 4] to [1, 3, 4]
//   absorbs the shared first axis and produces dimensions [3, 4], with first
//   input strides [0, 1] and second input strides [1, 3].
//
// - Reducing over the first axis. Reducing a [2, 3, 4] array to [1, 3, 4]
//   produces output strides [0, 1, 3], which coalesce to dimensions [2, 12]
//   with output strides [0, 1]. Each inner run accumulates into one fixed
//   output location.
struct rray_strided_iterator_plan {
  r_ssize size;

  // Since coalescing can multiply two axes' dimensions together, we use an
  // `r_ssize` here even though an individual dimension can't be above an `int`.
  r_ssize v_dimensions[RRAY_MAX_DIMENSIONALITY];
  int dimensionality;

  r_ssize v_strides[RRAY_MAX_DIMENSIONALITY];
};

static inline struct rray_strided_iterator_plan rray_strided_iterator_plan(
  const int* v_dimensions,
  int dimensionality,
  const r_ssize* v_strides
) {
  check_dimensionality(dimensionality);

    dimensionality

}

+#### The shifts
+
+`rray_roll_each_shifts()` walks the lane dimensions with the broadcast
+iterator, reads each lane's value from `n`, and writes its reduced shift. It
+follows the loop in `RRAY_BROADCAST_ATOMIC` in `src/broadcast.c`, including the
+fixed path for a zero run stride, which reduces a shift once per run instead of
+once per lane:

+```c
+static r_obj* rray_roll_each_shifts(
+  r_obj* n,
+  const struct rray_strided_iterator_plan* plan,
+  int axis_dimension
+) {
+  const r_ssize size = rray_strided_iterator_plan_size(plan);
+
+  r_obj* out = KEEP(r_alloc_integer(size));
+  int* v_out = r_int_begin(out);
+
+  const int* v_n = r_int_cbegin(n);
+
+  r_ssize run_start = 0;
+  const r_ssize run_size = rray_strided_iterator_plan_run_size(plan);
+
+  r_ssize n_start = 0;
+  const r_ssize n_run_stride = rray_strided_iterator_plan_run_stride(plan);
+
+  r_ssize v_point[RRAY_MAX_DIMENSIONALITY];
+  rray_strided_iterator_plan_point_init(plan, v_point);
+
+  while (run_start != size) {
+    const r_ssize run_end = run_start + run_size;
+    r_ssize n_loc = n_start;
+
+    if (n_run_stride == 0) {
+      const int shift = rray_roll_shift(v_n[n_loc], axis_dimension);
+      for (r_ssize i = run_start; i < run_end; ++i) {
+        v_out[i] = shift;
+      }
+    } else {
+      for (r_ssize i = run_start; i < run_end; ++i) {
+        v_out[i] = rray_roll_shift(v_n[n_loc], axis_dimension);
+        n_loc += n_run_stride;
+      }
+    }
+
+    run_start = run_end;
+    RRAY_STRIDED_ITERATOR_NEXT(n_start, v_point, plan);
+  }
+
+  FREE(1);
+  return out;
+}
+```
+
+For a size 1 `n`, the plan coalesces to one run with stride 0, so there is one
+`%` for the whole table.

I made your iterator change to plans/roll.md. On the size > 0 check, I kept it, and here is the case that still needs it.

The size > 0 check. Two of the three reasons the plan gave for it were weak, and I cut them:

  • Dividing by a zero dimension: rray_roll_shift() already returns 0 when the dimension is 0, so the check isn't needed for that.

  • Overflow of block_size and n_groups: src/rep.c computes the same products with no check, so this plan shouldn't treat it differently.

The reason left is memory. The shifts table has one entry per lane, and the iterator doesn't change that. Take x with dimensions (100000, 0, 100000) and axis = 2. x is empty, but it has 100000 * 100000 lanes. Without the check, shifts would be ten billion integers, about 40 GB, for an empty result. The plan already has a test for exactly this case. The notes now say this is the only reason for the check.

A narrower guard, axis_dimension > 0, would work too, since a zero on any other axis gives zero lanes. I kept size > 0 because it reads more simply. Tell me if you'd rather have the narrower one.

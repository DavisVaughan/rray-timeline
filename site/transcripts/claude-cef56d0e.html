I found relevant information about the `keepdims` default in NumPy. Here are the key results:

The most relevant GitHub issue is Issue #12559, which proposes that `sum` should return a row or column vector by default depending on whether axis is set to 0 or 1, rather than returning a rank 1 matrix, eliminating the need for programmers to remember to set `keepdims` to True.

However, it's important to note that NumPy's default value for `keepdims` is effectively False. NumPy uses a special `_NoValue` sentinel to distinguish "user did not specify a keepdims value" from "user explicitly specified the value that would be the default, anyway," because if the default value is passed, then `keepdims` will not be passed through to the sum method of sub-classes of ndarray, however any non-default value will be.

So while there was a proposal to change the default to `keepdims=True` (Issue #12559), NumPy has maintained `False` as the default, with special handling to distinguish whether the user explicitly specified the parameter or relied on the default.

Based on the search results, I found information about the `keepdims` parameter in the Array API standard:

## Overview

In the Array API standard, the `keepdims` parameter is a boolean where if True, the reduced axes (dimensions) must be included in the result as singleton dimensions and the result must be compatible with the input array through Broadcasting; otherwise, if False, the reduced axes (dimensions) must not be included in the result, with a default of False.

## Usage Across Functions

This parameter is consistently applied across multiple reduction functions in the Array API standard, including:

- The `argmin` and `argmax` functions require the `keepdims` keyword argument, similar to `min` and `max`, although in NumPy, `min` and `max` have this keyword argument but `argmin` and `argmax` do not
- Functions like `std` follow the same pattern where if True, reduced axes must be included as singleton dimensions for Broadcasting compatibility, and if False they must not be included, with a default of False

## Discussion

There has been discussion about whether the `keepdims` keyword argument actually makes sense for `argmin` and `argmax` functions, or whether it was just added by mistake because they are also in the non-arg variants.

The choice of `False` as the default maintains backward compatibility with existing NumPy behavior for most reduction operations.

```

## Tensorflow

```

* * *

The minimum common API across **most** libraries is

```
<name>(x, axis=None, keepdims=False, out=None)
```

For example,

```
mean(x, axis=None, keepdims=False, out=None)
```

* * *

## Proposal

Signature of the form:

```
<name>(x, *, axis=None, keepdims=False, out=None)
```

APIs:

```
mean(x, *, axis=None, keepdims=False, out=None)
var(x, *, axis=None, keepdims=False, out=None)
std(x, *, axis=None, keepdims=False, out=None)
sum(x, *, axis=None, keepdims=False, out=None)
prod(x, *, axis=None, keepdims=False, out=None)
min(x, *, axis=None, keepdims=False, out=None)
max(x, *, axis=None, keepdims=False, out=None)
```

## Notes

-   Statistical functions are not as easily generalizable in a broad sense, as certain functions may benefit from additional parameters. For example,

    -   an initial value when computing the sum/product

        ```
        numpy.sum(a, axis=None, dtype=None, out=None, keepdims=<no value>, initial=<no value>, where=<no value>) → ndarray
        ```

    -   a correction factor when computing the variance

        ```
        numpy.var(a, axis=None, dtype=None, out=None, ddof=0, keepdims=<no value>) → ndarray
        ```

    Accordingly, we'll likely want to investigate slightly bespoke interfaces for each function, but the above should provide a common starting point.

-   Optional arguments as [keyword-only](https://www.python.org/dev/peps/pep-3102/) arguments for the following reasons:

    1.  Avoid potential positional variation amongst library implementations.
    2.  Favor explicit interfaces and minimize readers' need to intuit an optional positional argument's meaning.

I found no evidence of regret. The record shows NumPy defending the default, and the rest of the Python ecosystem choosing it again when it had a clean slate.

1. The one direct proposal was closed the same day. numpy#12559 (2018) asked for keepdims=True by default in sum(). Eric Wieser, a NumPy maintainer, closed it and argued on the merits, not only on compatibility:

Changing behavior like this would break thousands of users.

I also don't think that would even be a better default. As designed, np.sum([1, 2]) and the built-in sum([1, 2]) match. Under your proposition, they would not.

I think you need to stop thinking in terms of "matrices" or "vectors". Numpy is all about n-dimensional arrays.

Sebastian Berg, another maintainer, agreed that the pain the issue describes is real, but blamed .T on 1-D arrays, not keepdims.

2. The array API standard kept False without any debate I could find. This was the ecosystem's chance to fix NumPy's mistakes, and it did change other things, such as type promotion and keyword-only arguments. In array-api#10, Athan Reines listed the reduction signatures of NumPy, CuPy, Dask, JAX, MXNet, PyTorch and TensorFlow. All of them default to False (NumPy's default only looks different because it is a sentinel), and the proposal went with keepdims=False. In array-api#109, the only keepdims question was whether argmin()/argmax() should accept it at all. The answer was yes, to match min()/max(), still with False as the default.

3. NumPy 2.0 did not touch it. 2.0 was the release where NumPy allowed itself breaking changes. The 2.0.0 release notes change type promotion and remove many APIs, but say nothing about the keepdims default.

4. NumPy has only added more keepdims support. It was added to many functions in 1.12.0, and later to argmin()/argmax(). The pattern is "make opting in easy", not "we picked the wrong default".

A caveat. Complaints do exist, but they come from users, mostly people coming from MATLAB or linear algebra who expect a row or column vector back. The regret you would be looking for would come from maintainers, and I found none. My search was not exhaustive: I checked GitHub issues and release notes, not the mailing list archives.

The counterexample you may want is outside Python. Julia's sum(A; dims = 1) keeps the reduced axis as size 1 by default, and so does MATLAB. So there is a real split between languages, but it is not something NumPy regrets.

No to both. I'd keep rray_remove_axes() and leave drop out, which is also what plans/implementation.md:1007 already decided for reductions ("There is no keep_dimensions argument").

Why not a drop argument

  • For slicing, drop has no good meaning. Base R drops every axis that ends up with a dimension of 1, so the result's shape depends on the data. x[i, ] gives a matrix until i happens to select one row. That is the bug drop = FALSE exists to avoid. NumPy avoids it by treating x[1] and x[[1]] differently, but R can't tell 1 from c(1). So in rray_slice() and its shortcuts, drop = TRUE would either depend on the data or be impossible to define.

  • For reductions, it's well defined but only saves one call. The reduced axes are exactly the ones to drop, and they always have a dimension of 1, so this already works:

    rray_sum_along(x, 2) |> rray_remove_axes(2)

  • Every function would need its own edge case rules. Take rray_sum_along(x, c(1, 2), drop = TRUE) on a matrix. rray_remove_axes() requires at least one axis to remain, so each function would have to either error or invent a zero-dimension result. It would also need its own tests and docs for that. Right now there is one rule: dimensionality never changes unless you ask for it, and that decision sits in one function.

  • NumPy's keepdims doesn't apply here. NumPy needs keepdims=True because its default drops axes and you can't cheaply get them back without knowing which ones. rray keeps them by default, and removing them later is one explicit call with the same axes.

Why not the rename

  • rray_insert_axes() / rray_remove_axes() is a clean pair. "Drop" has no natural opposite ("drop" / "add"? "drop" / "insert"?).

  • "Drop" already means other things in the docs: negative subscripts "drop positions", and several functions "drop names".

  • The main reason to rename would be to match a drop argument. Without the argument, that reason goes away.

If you want the convenience anyway, I'd limit it to the reduction family, where the meaning is clear. Then I'd rename to rray_drop_axes() so the function and the argument share a word. I'd still skip slicing, rray_index(), and the rest.

With the scope limited to the reducers, I'd say yes to both. drop then has one clear meaning (remove the axes you just reduced), and once it exists, rray_drop_axes() is worth the rename so the function and the argument share a word. The main gain is that you write axes once instead of twice, so the two calls can't drift apart:

rray_sum_along(x, c(1, 3), drop = TRUE)

# instead of
rray_sum_along(x, c(1, 3)) |> rray_remove_axes(c(1, 3))

There is one decision you need to make first: what happens when drop = TRUE would remove every axis. rray_remove_axes() errors in that case (I checked: "axes can't remove every axis"). If the reducers reuse that rule, then summing a 1-D array errors:

rray_sum_along(1:5, 1, drop = TRUE)
#> Error: `axes` can't remove every axis.

That is probably the most common full reduction there is, so an error there would hurt. The options:

  • Error, same as rray_remove_axes(). Consistent, but it breaks the most common use.

  • Keep the last axis. The result is int [1(1d)] 15, the same thing you get today without drop. The rule becomes "dimensionality is max(1, d - length(axes))". That's simple, but drop = TRUE sometimes drops fewer axes than you asked for.

  • Return a plain length-1 vector with no dim. This matches base R's drop(), but it would be the first rray function to return a value with no dim. That breaks the promise that rray always returns an array.

I'd pick the second option, and have rray_drop_axes() follow the same rule so the two stay consistent. That means relaxing its current error rather than giving the reducers their own special case.

Two smaller things to confirm:

  • Default drop = FALSE, placed after ..., like na_rm. That keeps the current behavior and forces the argument to be named.

  • The planned rray_max_along() and rray_min_along() get it too, and plans/implementation.md:1007 gets updated so it no longer says there is no such argument.

No. Every NumPy function with keepdims is a reducer. I listed them all by checking which functions in NumPy 2.5.3 accept the argument. The ones that are easy to miss:

  • Position reducers: argmax(), argmin(), nanargmax(), nanargmin() (the arg versions got keepdims in 1.22). Your plan's rray_max_pos() and rray_min_pos() (plans/implementation.md:1024) are the same thing, so they should get the argument too, even though they take a single axis.

  • Counting: count_nonzero().

  • Order statistics: median(), quantile(), percentile() and their nan versions.

  • Weighted and range reducers: average() (with weights) and ptp() (max minus min).

  • Norms: linalg.norm(), linalg.vector_norm(), linalg.matrix_norm().

  • Generalized ufuncs that return one value per input: vecdot() accepts keepdims through the general ufunc machinery. np.vecdot(ones((2, 3)), ones((2, 3)), keepdims=True) has shape (2, 1). It's a reducer in disguise: it collapses the shared axis. Your plan lists rray_dot() as out of scope, so this doesn't matter for now.

Everything else that changes shape (cumsum(), diff(), sort(), unique(), slicing) has no keepdims. So "only the reducers" is exactly NumPy's line.

On remove = FALSE: keeping the rray_remove_axes() name and using the same word for the argument works. My one worry is how it sits next to na_rm, since "rm" already means "remove":

rray_sum_along(x, 2, na_rm = TRUE, remove = TRUE)

When you read that call, it isn't obvious that remove means axes and not values. remove_axes = TRUE would fix that, because it matches the function name exactly, but it's longer. I'd accept the extra length, but I don't feel strongly about it.

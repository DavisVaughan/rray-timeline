Yes, it's possible, and base R's sum() works this way. But I don't think it's worth doing for rray_mean().

How base R does it. isum() in src/main/summary.c:52 sums integers into a 64-bit integer. Overflow is impossible for the first 2^32 elements, so it doesn't check during that stretch. After that, every 1000 additions it checks whether the running total has passed about 9e15. If it has, it doesn't error. It starts over and sums in a double instead (irsum()).

The check has to come before the overflow, not after. Overflowing a signed integer is undefined behavior in C, so you can't add first and then look for a wrapped value.

Why I wouldn't do it here:

  1. Erroring on overflow is worse than what we have now. The error would depend on the values, not just the shape. A 2^33 element array full of 5s would work, and the same array full of INT_MAX would fail. Both have a valid, finite mean. Today's fallback never fails.

  2. Switching to a double on overflow (base R's way) doesn't save any code. The fallback still has to exist. We'd also add a guarded int64 loop for large counts. So the result is more code, plus a third path that's even harder to test.

  3. The check is awkward with our iterator. Base R walks one flat vector with one total. We have one total per output value. Stride 0 runs could do one check per run. Non zero stride runs add one element to each output value per run, so they'd need a branch on every element, or a periodic scan of every output value.

  4. The precision gain is small. The fallback sums in a double and then runs the correction pass, which recovers most of what the double sum loses. Exact int64 sums would only beat that in very large reductions, and only by a little.

I'd keep the current design: exact int64 whenever overflow is impossible, and a corrected double sum otherwise. It's simple, it never errors, and its precision matches or beats base R's mean().

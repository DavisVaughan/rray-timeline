// Broadcasting of array names
//
// Assumes the inputs are validated arrays and are broadcastable to the
// `dimensions`. The caller typically checks all of this already.
static r_obj* rray_broadcast_names_fill(
  r_obj* out,
  r_obj* x,
  r_obj* dimensions,
  const bool* v_ignored
) {
  r_obj* x_names = rray_names(x, rray_args.x, r_lazy_null);
  if (x_names == r_null) {
    return out;
  }
  KEEP(x_names);

  r_obj* const* v_x_names = r_list_cbegin(x_names);

  r_obj* x_dimensions = KEEP(rray_dimensions(x, rray_args.x, r_lazy_null));
  const int* v_x_dimensions = r_int_cbegin(x_dimensions);
  const int x_dimensionality =
    rray_dimensionality_from_dimensions(x_dimensions);

  const int* v_dimensions = r_int_cbegin(dimensions);
  const int dimensionality = rray_dimensionality_from_dimensions(dimensions);

  r_keep_loc out_loc;
  KEEP_HERE(out, &out_loc);

  for (int i = 0; i < x_dimensionality; ++i) {
    if (v_ignored[i]) {
      continue;
    }
    if (v_x_names[i] == r_null) {
      // No names to contribute on this axis
      continue;
    }
    if (v_x_dimensions[i] != v_dimensions[i]) {
      // No names to contribute when axis is broadcast
      continue;
    }
    if (out != r_null && r_list_get(out, i) != r_null) {
      // Names already exist on this axis
      continue;
    }
    if (out == r_null) {
      out = r_alloc_list(dimensionality);
      KEEP_AT(out, out_loc);
    }
    r_list_poke(out, i, v_x_names[i]);
  }

  FREE(3);
  return out;
}

I agree. Right now the code merges names per axis, and the first input wins. You can see it in rray_broadcast_names_fill() in src/broadcast-names.c:95-115. That causes two problems:

  • Different names on the same axis are ignored. If x has rownames a, b and y has rownames c, d, you get a, b without any signal.

  • Names from different inputs get mixed. If x has only rownames and y has only colnames, the result gets both, even though no input ever had those names together.

Base R doesn't merge either. For x + y, it takes all of x's dimnames if x has any, and otherwise all of y's. Your rules are stricter than that, which I think is right for rray.

A tighter way to state your rules

Your five rules reduce to one:

  1. For each input, work out what names it contributes: its names, with every broadcast axis set to NULL. An input that ends up with no names contributes nothing.

  2. If every input that contributes has the same names on every axis (NULL included), use those names. Otherwise, drop all names.

Rules 1 to 4 are special cases of this. Rule 5 is the "otherwise".

One case your rules leave open

x has names (r, c) and y has names (r, NULL), with the same r.

  • Under the formulation above, this is a conflict because the lists differ on axis 2. All names are dropped.

  • Under a per-axis reading of your rules 1 and 3, axis 1 matches and only x contributes on axis 2. That gives (r, c). But then rule 4 can't hold as stated, because now names come from two inputs.

I'd go with the strict version (conflict). It's the only reading where rule 4 fits cleanly, and it means the result's names always match some single input's names exactly. The lenient version brings back a mild form of merging.

Other things to decide

  • Silent drop, warning, or error? I'd drop silently. An error would make plain x + y fail too often. A warning would be noisy in pipelines where names are incidental.

  • N-ary functions. rray_broadcast_names_common_opts() (used by combine.c) would follow the same rule: any conflict among any inputs drops everything. The axis being combined along is skipped as it is now. For bind-style functions that seems right, but it's worth confirming, since one stray rowname on one input would remove every name on the result.

  • What "the same" means. I'd compare element by element. R reuses one object for equal strings (it caches them), so a pointer check is usually enough, with a fallback for strings in different encodings. There's also a fast path when both inputs share the very same names vector, like x + x.

  • What stays the same. Single-input rray_broadcast_names() and the reduce names in src/reduce-names.c only ever have one input, so they don't change.

If you settle the (r, c) vs (r, NULL) case and the silent-drop question, I can write this up as a plan in plans/.

The fix is that a broadcast axis has no say at all. It's not the same as "unnamed". Per axis, each input is in one of three states:

  • Broadcast. It has no say on this axis and never conflicts.

  • Unnamed. Full dimension, no names.

  • Named. Full dimension, with names.

Is that a fully commutative / associative (not sure which) rule with >2 inputs?

Claude

It is commutative but not associative. No rule shaped like this one can be associative.

Commutative: yes. Order doesn't matter, whether there are 2 inputs or many. The rule only asks, per axis, whether the named inputs agree, and swapping inputs doesn't change that answer.

Associative: no. A conflict drops the names, and an unnamed result has no say in the next step. So the conflict is forgotten. Here's a one-axis example with three 2x2 matrices, where r1 and r2 are different rownames:

a: rownames r1
b: rownames r1
c: rownames r2

(a + b) + c   # a + b is r1, then r1 vs r2 conflicts: no names
a + (b + c)   # b + c conflicts, so no names; then a + that is r1

An n-ary function that sees all three inputs at once finds the conflict and drops everything. So rray_bind(a, b, c) can differ from rray_bind(rray_bind(a, b), c). For arithmetic, R always groups left to right, so a + b + c gives the first of the two answers above.

Why no fix exists within this rule. To be associative, a conflict would have to stick: once it happens, every later step would also have to drop names. But the result is a plain array with dimnames, and it has nowhere to record "this conflicted". Unnamed is the only way to show a conflict, and unnamed has to be neutral or the sum case breaks. Dropping only the conflicting axis doesn't help either. The same example still fails.

The current first-wins rule is the reverse: associative but not commutative. It fills each axis from the first input that has names, so grouping doesn't matter but order does.

I think commutativity is the one to keep. x + y and y + x giving different names would be a real surprise. Associativity only fails when there's already a conflict, and in that case every answer is "names were lost somewhere", which is the signal you wanted. The main thing to document is that the n-ary functions check all their inputs together, so they can drop names in cases where a chain of two-input calls would keep some.

Axes are matched by name, not position. Every dimension has a name, like "time" or "station". Broadcasting lines dimensions up by name, and a dimension missing from one input gets broadcast. There's no position-based broadcasting, so "x's axis 1 vs y's axis 2" can't come up.

The result keeps only the labels in both, and the values are lined up by label. Labels in a different order get reordered. An axis with no labels matches by position. If one input has labels on a dimension and the other doesn't, the sizes must match and the labels are kept. That is the lenient choice from before.

Reductions drop the dimension. x.sum("col") removes "col" completely, so the size-1 axis from the divide-by-sum case never exists. Broadcasting it back works by name.

Extra labels that don't index anything are dropped one at a time. xarray also has coordinates that aren't the main index of a dimension. If two inputs disagree on one of those, I believe that coordinate is dropped and the others are kept. That's per-item, not "drop everything".

What this means for rray

xarray's approach doesn't carry over, because rray names are R dimnames. Base R never matches on them, and a user who writes x + y expects position-based math. Joining on names would change results depending on the names, which is a big step away from base R.

Parts of it do match what we've discussed:

  • Unnamed has no say (the lenient rule). xarray does the same.

  • Conflicts are handled per axis, not by dropping everything. For index labels, that's a join or an error. For other coordinates, it's a per-item drop. Nothing in xarray drops all labels because one axis conflicted.

That second point is a reason to reconsider your rule 5. Dropping only the conflicting axis is closer to what xarray does. It's still commutative. It isn't associative, but as we saw, neither is dropping everything. The case for dropping everything is that a conflict on one axis suggests the inputs weren't meant to line up at all, so the other axes' names shouldn't be trusted either. Which of those two views matches what you're after?

Here are the refined rules. The rest of the design follows from our discussion. You still need to confirm how conflicts are handled, which I cover at the end.

Rules

Each axis is decided on its own. On a given axis, each input is in one of three states:

  • Broadcast: its dimension is 1 and the output's dimension is larger, or the input doesn't have this axis at all.

  • Unnamed: full dimension, no names.

  • Named: full dimension, with names.

The output names for that axis are then:

  1. Broadcast inputs have no say.

  2. Unnamed inputs have no say.

  3. If no input is named, the axis has no names.

  4. If every named input has the same names, the axis gets those names.

  5. If named inputs disagree, the axis has no names. Other axes are not affected.

If every axis ends up without names, the result has no dimnames at all.

Examples

# Divide by a sum: s broadcasts on axis 2, so it has no say there
x: (r, c)    s: (r, broadcast)     ->  (r, c)

# Unnamed has no say
x: (r, c)    y: (r, NULL)          ->  (r, c)

# Names on different axes combine
x: (r, NULL) y: (NULL, c)          ->  (r, c)

# A conflict only affects its own axis
x: (r1, c)   y: (r2, c)            ->  (NULL, c)

Details

  • If every input has dimension 1 on an axis, none of them are broadcast, so their names are compared as usual. This matches the current check in rray_broadcast_names_fill().

  • N-ary functions check every input at once. The axis being combined along is skipped, as it is now.

  • "Same names" means the same strings in the same order, compared one by one. Two inputs that share the exact same names vector (like x + x) can skip the comparison.

  • Order of inputs doesn't matter, but grouping does. (a + b) + c can differ from a + (b + c). That only happens once there's a conflict.

How much changes

Very little. Today's code already gives broadcast and unnamed inputs no say, and it already fills different axes from different inputs. The only change is rule 5: today the first input wins a conflict, and under these rules the axis loses its names.

Your decision

Rule 5 is where this differs from what you first proposed. You wanted any conflict to drop all names. I'd recommend dropping only the conflicting axis:

  • It's one rule applied to each axis, which is easier to explain.

  • Agreement on the other axes is real evidence that they line up.

  • It matches xarray, where nothing drops every label because one axis conflicted.

The case for dropping everything: a conflict anywhere means the inputs probably weren't meant to line up, so none of their names should be trusted. If that's the behaviour you want, only rule 5 changes, to "if named inputs disagree on any axis, the result has no names".

Which version of rule 5 do you want? Once you've picked, I can write the plan in plans/.

So an unnamed axis has no say, which is your rule 2. Broadcasting lines axes up from the right, like NumPy. Mismatched names raise an error. Dropping names is not an option.

Julia NamedDims.jl. Same idea. The wildcard name :_ matches anything, and a mismatch is an error.

pandas, for the name of an index. A pandas axis has a single optional .name. When two inputs are combined, the result keeps the name if both inputs share it and sets it to None if they differ. That's your rule 5 applied per axis, and the result drops the name without any warning.

Libraries that label along an axis

Base R (checked in src/main/arithmetic.c:693-696). If x has dimnames, the result takes all of x's dimnames. Otherwise it takes all of y's. There's no per-axis merge and no conflict check. For plain vectors (arithmetic.c:699-702), names come from whichever input has the same length as the result.

pandas, for the labels themselves. Labels are keys. Arithmetic lines rows up by label using an outer join and fills the gaps with NaN, so it changes the data rather than the names. It's the same approach as xarray's, but with a different default join.

Julia AxisKeys.jl and DimensionalData.jl. As far as I remember, broadcasting checks that the labels match and raises an error if they don't. DimensionalData lets you relax that check. I'm less sure of the details here.

NumPy, JAX and MATLAB arrays don't have labels, so the problem doesn't come up.

What this means for your rules

  • Rules 1 to 4 are well supported. Every library with names treats "no name" as a wildcard, and each output axis takes the name that isn't missing.

  • Handling conflicts splits three ways.

    • Error: PyTorch, NamedDims, AxisKeys.

    • Silent drop on that axis only: pandas index names.

    • Change the data by joining on labels: pandas, xarray.

  • Nothing I know of drops every axis's names because of a conflict on one axis. That's more evidence for dropping per axis.

Raising an error is a real third option that we haven't discussed. It would be strictest and would also fix the associativity problem, because a conflict would stop the computation instead of being forgotten. The downside is that x + y would fail on inputs that base R handles fine, which seems too harsh for R dimnames. Most R users treat dimnames as labels for printing, not as something to check. I'd still go with dropping per axis, but raising an error would be consistent with PyTorch and Julia if you want rray to be strict.

.Ops.rvar <- function(f, e1, e2, preserve_dims = FALSE) {
  c(e1, e2) %<-% conform_rvar_nchains(list(e1, e2))
  draws_x <- draws_of(e1)
  draws_y <- draws_of(e2)

  # broadcast draws to common dimension
  new_dim <- dim2_common(dim(draws_x), dim(draws_y))
  # Most of the time we don't broadcast scalars (constant rvars of length 1).
  # With broadcast_scalars = FALSE broadcast_array will return a vector (no dims)
  # version of the input, which works unless *both* x and y are constants
  # (because then the correct output shape is lost; in this case we do need to
  # broadcast both x and y in case their dimensions are not equal; e.g. if x is
  # 1x1 and y is 1x1x1x1 we must broadcast both to 1x1x1x1)
  broadcast_scalars = length(draws_x) == 1 && length(draws_y) == 1
  draws_x <- broadcast_array(draws_x, new_dim, broadcast_scalars = broadcast_scalars)
  draws_y <- broadcast_array(draws_y, new_dim, broadcast_scalars = broadcast_scalars)

  draws <- f(draws_x, draws_y)

  # for factors, we must copy the dims back over after, because base-R factor
  # operations destroy dims (while base-R numeric array operations do not)
  if (preserve_dims) {
    # in the case where one of e1 or e2 is scalar and the other is not,
    # we need to source the dims from whichever is *not* scalar, which will be
    # the longer of the two. In any other case, we give preference to e1
    # (draws_x) to be consistent with base R behavior
    if (length(draws_y) > length(draws_x)) {
      dim_source <- draws_y
    } else {
      dim_source <- draws_x
    }
    draws <- copy_dims(dim_source, draws)
  }

  new_rvar(draws, .nchains = nchains(e1))
}

.Ops.rvar_factor <- function(.Generic, e1, e2, ordered = FALSE) {

#' # Decompose Sigma into R s.t. R'R = Sigma ...
#' R <- chol(d$Sigma)
#' # ... and recreate Sigma using matrix multiplication
#' t(R) %**% R
#'
#' @importFrom tensorA mul.tensor as.tensor
#' @export
`%**%` <- function(x, y) {
  # Fast version of rdo(x %*% y)

  # convert both objects into rvars if they aren't already (this will ensure
  # we have a 3d draws array for each variable)
  x <- as_rvar(x)
  y <- as_rvar(y)

  if (is_rvar_factor(x) || is_rvar_factor(y)) {
    stop_no_call("Cannot apply `%**%` operator to rvar_factor objects.")
  }

  # ensure everything is a matrix by adding dimensions as necessary to make `x`
  # a row vector and `y` a column vector
  ndim_x <- length(dim(x))
  if (ndim_x == 1) {
    dim(x) <- c(1, dim(x))
  } else if (ndim_x != 2) {
    stop_no_call("First argument (`x`) is not a vector or matrix, cannot matrix-multiply")
  }

  ndim_y <- length(dim(y))
  if (ndim_y == 1) {
    dim(y) <- c(dim(y), 1)
  } else if (ndim_y != 2) {
    stop_no_call("Second argument (`y`) is not a vector or matrix, cannot matrix-multiply")
  }

  # conform the draws dimension in both variables
  c(x, y) %<-% conform_rvar_ndraws_nchains(list(x, y))

  # drop the names of the dimensions (mul.tensor gets uppity if dimension names
  # are duplicated, but we don't care about that)
  x_tensor <- as.tensor(draws_of(x))
  y_tensor <- as.tensor(draws_of(y))
  names(dim(x_tensor)) <- NULL
  names(dim(y_tensor)) <- NULL

  # do a tensor multiplication equivalent of the requested matrix multiplication
  result <- unclass(mul.tensor(x_tensor, 3, y_tensor, 2, by = 1))

  # move draws dimension back to the front
  result <- aperm(result, c(3,1,2))

  # restore dimension names (as.tensor adds dummy names to dimensions)
  names(dim(result)) <- NULL
  result <- copy_dimnames(draws_of(x), 1:2, result, 1:2)
  result <- copy_dimnames(draws_of(y), 3, result, 3)

  new_rvar(result, .nchains = nchains(x))
}

I've finished reading posterior's source. Here's what I found.

Posterior uses R dimnames in two ways: as labels along each axis, and as axis names (names(dimnames(x)), like A and B). Its rule for arithmetic is base R's rule after broadcasting. It doesn't compare labels, so it has no idea of a conflict, and the rule isn't commutative. It does preserve axis names everywhere, which rray4 currently doesn't.

I read a fresh clone of stan-dev/posterior (commit acf2447) in /tmp/posterior. I didn't run any of it.

How posterior handles arithmetic

.Ops.rvar() in R/rvar-math.R:16-49 works in three steps:

  1. Work out the common shape with dim2_common().

  2. Broadcast each input with broadcast_array(). That function sets the dimnames of each broadcast axis to NULL before copying values (R/rvar-.R:708-715). Its comment explains why: after broadcasting, those names would repeat and so wouldn't be unique any more.

  3. Call the base R operator on the broadcast arrays.

So the names come from base R: all of x's dimnames if x has any, and otherwise all of y's. Applied to our examples:

  • Divide by a sum. x / s gives (r, c), because x has names and wins. s / x gives (r, NULL): the broadcast step dropped s's axis 2 names, but s still has names on axis 1, so it wins and the column names are lost. Swapping the inputs changes the result.

  • Names on different axes. (r, NULL) with (NULL, c) gives x's names, (r, NULL). The two are never merged.

  • Conflicting names. (r1, c) with (r2, c) gives (r1, c). There's no check.

That supports two parts of your rules: a broadcast axis shouldn't contribute names, and a whole list should never be built by merging names from different inputs. Posterior never tries to be commutative, though, because it simply uses base R's rule.

Where posterior does take care: axis names

Posterior handles axis names carefully in the functions it writes itself:

  • copy_dimnames() (R/rvar-.R:750-775) copies an axis's labels and its axis name together. If every axis name ends up empty, it removes the axis names entirely.

  • Matrix multiplication (%**%) takes the row labels and row axis name from x, and the column labels and column axis name from y (R/rvar-math.R:206-207). The test at tests/testthat/test-rvar-math.R:248-251 checks that {a, b} %**% {c, d} gives list(a = ..., d = ...). Each output axis comes from exactly one input, so conflicts can't happen. That's a useful model for rray's own matrix multiplication, if it ever has one.

  • Binding uses abind(use.dnns = TRUE), which keeps axis names (R/rvar-bind.R:114).

  • Permuting axes keeps axis names too (tests/testthat/test-rvar-math.R:404-413).

What rray4 does with axis names today

rray4 drops axis names on every path I tried:

x <- matrix(1:6, 2, dimnames = list(row = c("a", "b"), col = c("x", "y", "z")))

names(dimnames(rray_add(x, 1L)))           # NULL, was c("row", "col")
names(dimnames(rray_sum(x, 2)))            # NULL
names(dimnames(rray_broadcast(x, c(2, 3, 2))))  # NULL

The cause is in rray_broadcast_names_fill(): the output list comes from r_alloc_list() and never gets a names attribute. The reduce path behaves the same way. Base R arithmetic keeps axis names, so this is a step back from base R as well as from posterior.

What this means for the rules

If axis names are supported, the rules need to cover them. I'd treat the axis name as part of an axis's names, following posterior's copy_dimnames():

  • Broadcast or unnamed: no say on either the labels or the axis name.

  • Agreement: two named inputs agree only if both their labels and their axis names match. row = c("a", "b") and c("a", "b") with no axis name would be a conflict under the strict reading.

  • Axis names only. An axis can have an axis name but no labels, for example dimnames = list(row = NULL, ...). Base R allows this. I'd say that input is named on that axis, so its axis name counts.

The second and third points are choices for you to make. One lenient option is to treat an empty axis name like a missing label, so it has no say.

Two decisions are still open:

  • Rule 5: drop only the conflicting axis, or drop all names.

  • Axis names: should an empty axis name have no say, or should it conflict with a non-empty one?

Fixing the loss of axis names is needed whichever way you decide, so it could be its own PR ahead of the rules change.

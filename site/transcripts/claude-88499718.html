# `rray_modulo()` and `rray_integer_divide()`

Future work. This document collects what we worked out about `%%` and `%/%`
before deciding to defer them, so that work isn't lost. Nothing here is built.

---

# Part 1: Types

Same family as `rray_add()` and friends: `lgl`, `int`, `dbl`. `cpl` errors, the
same way `chr`, `raw` and `list` do for every arithmetic operator. Base R does
the same — `1i %% 1` is "unimplemented complex operation".

Promotion table, matching the shape of 2.4 in `plans/implementation.md`:

| op | lgl | int | dbl | cpl |
|---|---|---|---|---|
| `%%` `%/%` | int | int | dbl | error |

So the switch has the same 16 arm shape as `rray_add_switch()`, except the four
`cpl` arms (`logical_complex`, `integer_complex`, `double_complex`,
`complex_complex`) join the `chr`/`raw`/`list` arms calling
`stop_unsupported_arithmetic()`, the way `rray_exponentiate_switch()` already
does it. That means two scalar operations per operator, `_int_one` and
`_dbl_one`, not three — there is no `_cpl_one`.

---

# Part 2: Why the double core isn't just `fmod()`

The obvious definition is `x %% y = x - floor(x / y) * y` and
`x %/% y = floor(x / y)`. That's what R computes, but not how R computes it.
`src/main/arithmetic.c` in R's own source has two static functions, `myfmod()`
and `myfloor()`, that compute it more carefully:

- A short circuit for `fabs(x1) <= fabs(x2)`, which avoids a division (and the
  rounding error a division introduces) whenever the direct sign comparison
  already gives the answer.

- A `long double` intermediate in the general case
  (`tmp = (long double)x1 - floor(q) * (long double)x2`), which halves the
  rounding error against doing the same arithmetic purely in `double`.

- A warning ("probable complete loss of accuracy in modulus") when
  `fabs(q) * DBL_EPSILON > 1`, i.e. when the quotient is large enough that the
  double subtraction can't be trusted at all.

- `x2 == 0` returns `NaN` for `%%`, not `NA`. `myfloor()` doesn't special case
  it at all — `x1 / 0.0` is already `Inf`, `-Inf` or `NaN` under IEEE 754, which
  is exactly what R's `%/%` returns for a double `0` divisor.

Neither function is exported. They're `static` in `arithmetic.c`, not declared
in `Rmath.h`, so matching R here means porting the logic, not calling into R.

The comment directly above `myfmod()` reads "Keep myfmod() and myfloor() in
step" — they're two instances of the same idea (division with a
precision-guarded remainder), and R's own maintainers treat them as a pair that
has to be changed together. Do the same if either one is ever touched.

# Part 3: The int core doesn't need its own version of this

For `%%`, R's int arm is:

```c
(x1 >= 0 && x2 > 0) ? x1 % x2 : (int) myfmod((double) x1, (double) x2);
```

C's `%` truncates (sign follows the dividend), but `%%` is documented to floor
(sign follows the divisor) — the same convention Python uses. Those only agree
when both operands are non-negative, which is the fast path above. Everywhere
else, R doesn't hand-roll a second floored-mod implementation in integer
arithmetic — it reuses `myfmod()` by promoting to `double`. That round trip is
exact: R's integer range fits inside ±2^31, and a `double` mantissa holds
integers exactly up to 2^53, so nothing is lost. One canonical implementation
of "floored modulo, correctly signed, correctly handling zero" beats two copies
that have to be kept in agreement forever.

`%/%`'s int arm doesn't need any of this:

```c
(int) floor((double) x1 / (double) x2);
```

`floor()` already gives the floor regardless of sign, unlike `%`'s truncation,
so there's no fast/slow split and no call into `myfloor()`. The asymmetry is
real: `%%` needs the precision-guarded fallback for integers, `%/%` doesn't.

Both int arms return `NA_INTEGER` for `x2 == 0`, unlike the double arms, which
return `NaN`/`Inf` instead of `NA`. That's a real asymmetry in base R, not a
simplification we'd be introducing.

# Part 4: What the ported code would look like

Each operator gets its own `src/arithmetic-{op}.c`/`.h` pair, same shape as
`src/arithmetic-add.c`: `ffi_rray_{name}()`, `rray_{name}()`, a static
`rray_{name}_switch()`, its 12 non-error cores (16 arms, minus the 4 that error
on `cpl`), and two scalar operations.

`rray_myfmod()` would live as a `static inline` helper in
`src/arithmetic-modulo.c`, next to `rray_modulo_dbl_one()`. `rray_myfloor()`
the same way in `src/arithmetic-integer-divide.c`. Ported from
`src/main/arithmetic.c`, `myfmod()`/`myfloor()`, dropping the `warning()` call
(open question below) and writing `DBL_EPSILON` in place of R's internal
`c_eps`, since we don't need the long double PowerPC workaround R carries:

```c
static inline double rray_myfmod(double x1, double x2) {
  if (x2 == 0.0) {
    return R_NaN;
  }

  if (fabs(x2) * DBL_EPSILON > 1 && R_FINITE(x1) && fabs(x1) <= fabs(x2)) {
    if (fabs(x1) == fabs(x2)) {
      return 0;
    }
    return ((x1 < 0 && x2 > 0) || (x2 < 0 && x1 > 0)) ? x1 + x2 : x1;
  }

  const double q = x1 / x2;
  const long double tmp = (long double) x1 - floor(q) * (long double) x2;
  return (double) (tmp - floorl(tmp / x2) * x2);
}

static inline double rray_myfloor(double x1, double x2) {
  const double q = x1 / x2;

  if (x2 == 0.0 || fabs(q) * DBL_EPSILON > 1 || !R_FINITE(q)) {
    return q;
  }

  if (fabs(q) < 1) {
    if (q < 0) {
      return -1;
    }
    return ((x1 < 0 && x2 > 0) || (x1 > 0 && x2 < 0)) ? -1 : 0;
  }

  const long double tmp = (long double) x1 - floor(q) * (long double) x2;
  return (double) (floor(q) + floorl(tmp / x2));
}
```

`R_NaN` and `R_FINITE()` come from `Rmath.h`, already linked. The scalar
operations that use them:

```c
static inline int rray_modulo_int_one(int x, int y, struct r_lazy error_call) {

    return r_globals.na_int;
  }

    return x % y;
  }
  return (int) rray_myfmod((double) x, (double) y);

static inline double rray_modulo_dbl_one(double x, double y, struct r_lazy error_call) {
  return rray_myfmod(x, y);
}
```

```c
static inline int rray_integer_divide_int_one(int x, int y, struct r_lazy error_call) {
  if (x == r_globals.na_int || y == r_globals.na_int || y == 0) {
    return r_globals.na_int;
  }
  return (int) floor((double) x / (double) y);
}

static inline double rray_integer_divide_dbl_one(double x, double y, struct r_lazy error_call) {
  return rray_myfloor(x, y);
}
```

Both `int` cores are shared across the `lgl_lgl`, `lgl_int`, `int_lgl` and
`int_int` type pairs, the way `rray_multiply_int_one()` is. Both `dbl` cores
are shared across every pair involving a `dbl`, the way `rray_divide_dbl_one()`
is.

Tests: `tests/testthat/test-arithmetic-modulo.R` and
`tests/testthat/test-arithmetic-integer-divide.R`, one file per operator as
usual, working through all 12 non-error type combinations in both positions,
plus `NA`, `NaN`, `Inf` and `y == 0` on both sides.

Yes. It changes the plan a lot, and the biggest change is that the licensing problem mostly goes away.

1. The main reason to port R's code is gone. The plan gives two reasons for porting R's myfmod() and myfloor(): the long double step that halves rounding error, and matching R exactly. With double only, the first reason disappears. What is left of R's code is the textbook formula x - floor(x / y) * y, plus a fix-up step and a short circuit. On your Mac, long double is already just double (.Machine$longdouble.digits is NULL on aarch64), so R itself runs that double-only version there. R's own %% results already differ between x86_64 Linux and arm64 macOS, so "bit for bit with R" was never one fixed target.

2. That makes an independent version easy. C's fmod() gives the exact remainder for any two doubles. Floored modulo is one sign fix on top of it:

static inline double rray_modulo_dbl_one(double x, double y, struct r_lazy error_call) {
  if (y == 0.0) {
    return R_NaN;
  }
  double out = fmod(x, y);
  if (out != 0.0 && (out < 0.0) != (y < 0.0)) {
    out += y;
  }
  return out;
}

I compared this with R's %% on this Mac over 3 million random pairs (normal, uniform, and rounded to 2 decimals, with divisors like 0.1, 0.3, -0.7 and 7). There were 0 mismatches. 1e20 %% 3 matches too.

What this removes:

  • Licensing (Part 5). This is the standard definition built on a C library function, not R's code. That open question mostly goes away.

  • The "loss of accuracy" warning (Part 5). fmod() is exact, so the precision collapse the warning guards against cannot happen. The open question goes away. The result can only differ from R when R's own answer is the inaccurate one.

  • The short circuit, floorl(), c_eps, and the PowerPC note (Part 4). None of it is needed.

  • The int %% slow path (Part 3). It still promotes to double and calls the double core. That core is now about four lines.

3. %/% is the part that still needs work. floor(x / y) alone can be off by one, because x / y rounds before floor() sees it. A good approach is to derive it from the same fmod(), as CPython's float_divmod() does: (x - mod) / y, then round to the nearest whole number. CPython's license is permissive and works with MIT. It also keeps %% and %/% in step automatically, which is the same goal as R's "keep these in step" comment. I have not tested this against R's %/%. That test would be the first step when this gets picked up.

One correction to the plan. Part 2 describes R's short circuit as applying "for fabs(x1) <= fabs(x2)". In R's source it only applies when fabs(x2) * c_eps > 1 as well, meaning the divisor is larger than about 4.5e15. It is a guard for huge divisors, not a general shortcut. It no longer matters if the plan switches to fmod().

#include <math.h>

static double floor_divide(double x, double y) {
  if (y == 0.0 || !isfinite(x)) {
    return x / y;
  }
  double mod = fmod(x, y);
  double div = (x - mod) / y;
  if (mod != 0.0 && (mod < 0.0) != (y < 0.0)) {
    div -= 1.0;
  }
  if (div == 0.0) {
    return copysign(0.0, x / y);
  }
  double out = floor(div);
  if (div - out > 0.5) {
    out += 1.0;
  }
  return out;
}

The approach that works: floor(x / y) with an fma() fix-up

static inline double rray_integer_divide_dbl_one(double x, double y, struct r_lazy error_call) {
  const double q = x / y;
  if (y == 0.0 || !isfinite(q) || fabs(q) > 0x1p52) {
    return q;
  }
  const double out = floor(q);
  const double r = isfinite(y) ? fma(-out, y, x) : x;
  if (r != 0.0 && (r < 0.0) != (y < 0.0)) {
    return out - 1.0;
  }
  return out;
}

How it works:

  • fma(a, b, c) computes a * b + c with a single rounding step.

  • So r = x - out * y (the leftover) always has the correct sign.

  • If the leftover's sign does not match y, then x / y rounded up past a whole number. In that case floor() is one too high, and we subtract 1.

  • floor() can never be one too low. A rounded quotient cannot drop below a whole number that the true quotient is at or above.

  • Quotients bigger than 2^52 are returned as is, the same as R. Above that size every double is already a whole number.

  • On arm64, fma() is a single hardware instruction.

# `rray_modulo()` and `rray_integer_divide()`

Future work. This document collects what we worked out about `%%` and `%/%`
before deciding to defer them, so that work isn't lost. Nothing here is built.

# Part 1: Types

Same family as `rray_add()` and friends: `lgl`, `int`, `dbl`. `cpl` errors, the
same way `chr`, `raw` and `list` do for every arithmetic operator. Base R does
the same: `1i %% 1` is "unimplemented complex operation".

Promotion table, matching the shape of 2.4 in `plans/implementation.md`:

| op | lgl | int | dbl | cpl |
|---|---|---|---|---|
| `%%` `%/%` | int | int | dbl | error |

So the switch has the same 16 arm shape as `rray_add_switch()`, except the four
`cpl` arms (`logical_complex`, `integer_complex`, `double_complex`,
`complex_complex`) join the `chr`/`raw`/`list` arms calling
`stop_unsupported_arithmetic()`, the way `rray_exponentiate_switch()` already
does it. That means two scalar operations per operator, `_int_one` and
`_dbl_one`, not three. There is no `_cpl_one`.

# Part 2: Why we don't port R's code

R computes `%%` and `%/%` with two static functions in `src/main/arithmetic.c`,
`myfmod()` and `myfloor()`. They are not exported, so matching R would mean
porting them. We don't, for three reasons.

- **They lean on `long double`.** Both compute a correction term in
  `long double` to cut rounding error. rray only uses `double`. On arm64 macOS,
  `long double` is the same as `double`, so R itself already runs the double
  only version there, and R's results differ between x86_64 Linux and arm64
  macOS. "Bit for bit with R" was never one fixed target.

- **Licensing.** R is GPL-2 and rray is MIT. Porting R's specific
  implementation into an MIT package is a problem. Writing the operations from
  their definitions, on top of C's `fmod()`, `floor()` and `fma()`, is not.

- **There is a simpler, more accurate route.** C's `fmod()` returns the exact
  remainder of two doubles, with no rounding at all. C's `fma(a, b, c)`
  computes `a * b + c` with a single rounding. Together they give results that
  match R everywhere R is correct, and are exact in places where R is not.

Two things in the plan get simpler as a result:

- **No "loss of accuracy" warning.** `myfmod()` warns when the quotient is so
  large that its double subtraction can't be trusted. `fmod()` is exact at any
  size, so there is nothing to warn about.

- **No `long double`, `floorl()`, or `c_eps`.**

A note on R's short circuit in `myfmod()`, which an earlier version of this
plan described wrong: it only applies when `fabs(x2) * DBL_EPSILON > 1`, meaning
the divisor is bigger than 2^52 (about 4.5e15). It is not a general shortcut
for `fabs(x1) <= fabs(x2)`. It matters below, because it is why `-1 %% 1e300`
returns `1e300` in R but `-1e-10 %% 1e9` returns `0`.

# Part 3: The double cores

## `%%`

```c
static inline double rray_modulo_dbl_one(double x, double y) {
  // R returns `NaN` (not `NA`) for a zero divisor, for any `x`, including
  // `NA`. `fmod(x, 0)` would also give `NaN`, but this states it outright and
  // matches R's `NaN` exactly rather than relying on `fmod()`'s choice.
  if (y == 0.0) {
    return R_NaN;
  }

  // The exact remainder of `x / y`, with no rounding. C's `fmod()` truncates,
  // so the result has the sign of `x` (e.g. `fmod(-7, 3)` is `-1`). It also
  // passes `NA` and `NaN` through, and gives `NaN` when `x` is infinite, and
  // returns `x` itself when `y` is infinite.
  double out = fmod(x, y);

  // R's `%%` floors instead, so the result must take the sign of `y`
  // (e.g. `-7 %% 3` is `2`). If the remainder is nonzero and its sign
  // disagrees with `y`, shift it by one whole `y` into the right range:
  // `-1 + 3` is `2`. This addition is the only step that can round, and only
  // when `out` is tiny next to `y`.
  if (out != 0.0 && (out < 0.0) != (y < 0.0)) {
    out += y;
  }

  // When that addition rounds, it can land exactly on `y`
  // (e.g. `-1e-20 + 1` rounds to `1`). R returns `0` in that case, except when
  // `|y| > 2^52`, where R's short circuit returns `y`. Copy both.
  if (out == y && fabs(y) <= 0x1p52) {
    out = 0.0;
  }

  return out;
}
```

## `%/%`

```c
static inline double rray_integer_divide_dbl_one(double x, double y) {
  // The rounded quotient. Usually right, but rounding can push it up onto the
  // next whole number (e.g. `456.09 / 0.01` gives `45609` exactly, while the
  // true quotient is just under that).
  const double q = x / y;

  // Return the plain quotient, like R, when:
  // - `y` is `0`: `q` is already `Inf`, `-Inf` or `NaN`.
  // - `q` is not finite: `Inf`, `NA` or `NaN` pass straight through.
  // - `|q| > 2^52`: every double this large is already a whole number, so
  //   there is nothing to floor.
  if (y == 0.0 || !R_FINITE(q) || fabs(q) > 0x1p52) {
    return q;
  }

  // Our candidate answer. It is never too low: a rounded quotient cannot drop
  // below a whole number that the true quotient is at or above. It can only
  // be one too high, which the next lines check for.
  const double out = floor(q);

  // The leftover `x - out * y`, with a single rounding, so its sign is always
  // correct. An infinite `y` would turn this into `NaN` (`0 * Inf`), but then
  // `out` is `0` or `-1`... in fact `0`, since `x / Inf` is `0` or `-0`, so
  // the leftover is just `x`.
  const double r = R_FINITE(y) ? fma(-out, y, x) : x;

  // For a correct floor, the leftover has the same sign as `y` (or is `0`).
  // If it has the opposite sign, `out * y` overshot `x`, meaning `out` is one
  // too high.
  if (r != 0.0 && (r < 0.0) != (y < 0.0)) {
    return out - 1.0;
  }

  return out;
}
```

`R_NaN` and `R_FINITE()` come from `Rmath.h`, which is already linked and
already used in `src/reduce-mean.c`. `fmod()`, `floor()`, `fabs()` and `fma()`
come from `math.h`. On arm64 `fma()` is a single hardware instruction.

# Part 4: The int cores

For `%%`, C's `%` truncates and R's `%%` floors. They only agree when `x >= 0`
and `y > 0`, so that is the fast path. Everything else goes through the double
core. That round trip is exact, because every `int` fits in a double.

```c
static inline int rray_modulo_int_one(int x, int y) {
  // Unlike the double core, R returns `NA` (not `NaN`) for a zero divisor here
  if (rray_int_is_missing(x) || rray_int_is_missing(y) || y == 0) {
    return r_globals.na_int;
  }

  // Both nonnegative, so C's truncating `%` already gives the floored answer
  if (x >= 0 && y > 0) {
    return x % y;
  }

  // Any other sign combination: reuse the double core, which is exact for
  // `int` inputs
  return (int) rray_modulo_dbl_one((double) x, (double) y);
}
```

For `%/%`, the double core isn't needed. With `int` inputs, `x / y` can never
round up onto a whole number: the gap between the true quotient and the next
whole number is at least `1 / |y|`, far bigger than double rounding error at
these sizes.

```c
static inline int rray_integer_divide_int_one(int x, int y) {
  // R returns `NA` for a zero divisor here too
  if (rray_int_is_missing(x) || rray_int_is_missing(y) || y == 0) {
    return r_globals.na_int;
  }

  // `floor()` rounds toward negative infinity for any signs, which is exactly
  // `%/%`. The result always fits in an `int`, since `INT_MIN` is `NA`.
  return (int) floor((double) x / (double) y);
}
```

Neither int core can error, so both are called with `RRAY_BINARY_NO_ARGS`, the
way `rray_divide_dbl_one()` is.

Both `int` cores are shared across the `lgl_lgl`, `lgl_int`, `int_lgl` and
`int_int` type pairs, the way `rray_multiply_int_one()` is. Both `dbl` cores
are shared across every pair involving a `dbl`, the way `rray_divide_dbl_one()`
is.

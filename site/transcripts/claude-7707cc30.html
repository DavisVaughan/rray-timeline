Strictly by the standard, no. In practice, yes, everywhere R runs.

The rule. C17 6.3.1.5p1: converting a floating value to a narrower floating type is undefined if the value is outside the range the destination can represent. A long double total of 1e400 cast to double is exactly that case.

Why it works anyway. Under Annex F (IEC 60559 / IEEE 754), which every compiler R supports implements, the narrowing is a convertFormat operation: an out-of-range value rounds to ±infinity and raises the overflow flag. So R_FINITE((double) sum) returns false, which is what the code wants. On x86-64 the fstpl instruction does this in hardware.

R does both things. real_mean() in src/main/summary.c:487 uses the identical R_FINITE((double) s) pattern, so the kernels match R's own mean. But rsum() and isum() in the same file guard instead:

if (s > DBL_MAX) *value = R_PosInf;
else if (s < -DBL_MAX) *value = R_NegInf;
else *value = (double) s;

That comparison happens in long double, so nothing narrows. It is the portable version. It is also slightly less accurate at the boundary: values just above DBL_MAX become Inf, where IEEE narrowing would round them down to DBL_MAX.

Where it can actually bite us. Only one value in each kernel can exceed DBL_MAX: the raw total at src/reduce-mean.c:235. Everything after is a mean, bounded by max|x_elt|, so it fits in a double by construction. So the two conversions at risk are ISNAN((double) sum) (line 237) and the first R_FINITE((double) sum) (line 247), both reading that raw total. The rest are safe regardless.

One thing I would change. ISNAN is (isnan(x)!=0), and C99 isnan is type-generic, so it takes a long double directly:

if (ISNAN(sum)) {

Same result, one fewer narrowing.

R_FINITE can't be fixed the same way. Inside R it is isfinite(x) (type-generic), but HAVE_WORKING_ISFINITE is R-internal and we don't define it, so in our package it expands to R_finite(double), a real function call. Dropping the cast there would only hide the conversion, not remove it. The options are to keep the cast, call isfinite(sum) directly, or switch to the DBL_MAX comparison.

Confirmed reachable, and it matters:

  • c(Inf, -Inf, NA) → NA is skipped, then Inf + -Inf makes sum NaN. Result NaN, matching mean().

ISNAN() on the input filters NA and NaN, so no NaN ever enters the sum. But Inf + -Inf creates one. That is the only way, since every other operation on finite values and same-signed infinities stays non-NaN.

Two things the branch is not doing:

  • It isn't handling the all-NA case. There sum stays 0.0 and count stays 0, so the branch is skipped and sum /= count gives 0/0 = NaN further down.

  • It isn't required for correctness. Without it, R_FINITE(NaN) is false, so we fall into the recompute branch, get Inf/3 + -Inf/3 = NaN again, skip the correction, and return NaN. That is exactly what R's real_mean() does, which has no such branch. Ours is a shortcut that skips two extra passes over the data.

The non-na_rm twin looks similar but does more work: there the check also catches real NA and NaN inputs, so it rescans with R_IsNA() to tell NA from NaN. Here only the Inf + -Inf case is left, and that is always NaN, so it returns R_NaN directly.

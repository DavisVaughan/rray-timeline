Strided iterator plan

Optimizes and assists in walking a multidimensional point space defined by v_dimensions. As it walks, it updates a user provided start in an alternate subspace defined by v_strides.

For performance and flexibility, the user is responsible for managing the run loop along the first axis. We’ve tried many alternative approaches but they tend to tank performance quickly as you increase the level of abstractions.

The plan holds only immutable state. The positions that change as it walk are managed by the caller. This lets the compiler keep these positions in registers, which has significant performance implications.

Mostly positive, with one real wart.

What works: "plan" is the right word, and it has good precedent. FFTW's fftw_plan is the closest match: build once from shapes, then execute it many times. A database query plan is the same shape of idea. Both signal "precomputed, immutable, produced by an optimizer, reused." That's exactly this struct, and the coalescing pass really is an optimizer. So plan earns its place, and it pairs naturally with the caller-owned state, which is the un-planned half.

The wart: iterator now names a type that doesn't exist. Before the refactor there was a struct rray_strided_iterator and _plan distinguished the two halves. Now the struct is the only type in the pair, so a reader who meets struct rray_strided_iterator_plan asks "where's the iterator?" and has to discover the answer is "your own local start and v_point, driven by a macro." The suffix implies a sibling that isn't there.

Two things save it. RRAY_STRIDED_ITERATOR_NEXT() keeps the concept name attached to the thing that actually iterates, and the file is strided-iterator.h, so "strided iterator" reads as the name of the subsystem rather than a missing type. Under that reading _plan means "the fixed part of the strided iterator," which is accurate. The header comment you just rewrote carries most of the weight of making that reading obvious.

Secondary gripe: it's long, and the accessors inherit the length. rray_strided_iterator_plan_run_stride(&plan) is six words to ask for v_strides[0]. If the name were ever revisited, rray_stride_plan keeps the good part, drops the misleading part, and shortens every accessor. But that desyncs from the file name, and consistency with strided-iterator.h is worth more than the few characters. I'd leave it.

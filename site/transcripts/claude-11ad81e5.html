static R_INLINE void R_CleanupEnvir(SEXP rho, SEXP val)
{
    if (val != rho) {
	/* release the bindings and promises in rho if rho is no
	   longer accessible from R */
	int refs = REFCNT(rho);
	if (refs > 0)
	    refs -= countCycleRefs(rho, val);
	if (refs == 0) {
	    for (SEXP b = FRAME(rho);
		 b != R_NilValue && REFCNT(b) == 1;

Yes, it's possible, and R does the same thing in its own for loops. There are two catches: the check has to be "more than one reference", not NO_REFERENCES, and the savings may be small.

R already does this

do_for() in src/main/eval.c:2696 reuses the loop variable's storage between iterations:

#define ALLOC_LOOP_VAR(v, val_type, vpi) do {
	if (v == R_NilValue || MAYBE_SHARED(v) ||
	    ATTRIB(v) != R_NilValue || (v) != CAR(cell)) {
	    REPROTECT(v = allocVector(val_type, 1), vpi);
	    ...

So R allocates a new value only when the old one might be shared. Otherwise it writes the next element into the same storage.

Use MAYBE_SHARED(), not NO_REFERENCES()

To call f, the slice has to be reachable from somewhere: a binding like .x in an environment you evaluate f(.x) in, or a cell of the call object. That link counts as one reference. So after every iteration the reference count is at least 1, NO_REFERENCES() never passes, and you would never reuse the buffer.

The right test is MAYBE_SHARED() (reference count above 1), meaning "someone besides me holds it". That's exactly what do_for() checks.

rlang's r_is_shared() won't work here. It's MAYBE_REFERENCED(), the same strict test as NO_REFERENCES(), just negated. You'd call MAYBE_SHARED() directly. It's part of the public API.

When the count drops back

The count only drops back if R releases f's environment after the call. R_CleanupEnvir() (eval.c:2126) does this when a closure returns and nothing has captured its environment. It clears the bindings and promises (the lazy argument wrappers) that point at the slice. Some cases:

  • f is an ordinary closure that doesn't keep the slice: the count returns to 1, and you reuse the buffer.

  • f is identity, or returns the slice inside a list: storing the result adds a reference, so you allocate. Do the check after storing f's result in the output, not before.

  • f builds a closure, e.g. function(x) function() x: the environment is captured, so it is never cleaned up. The count stays high and you allocate.

  • f modifies x: its argument is shared at that point, so R copies it on modify first. Your buffer is untouched.

The risk

A count that's too high is harmless: you just allocate. A count that's too low is dangerous, because you'd overwrite data someone is still holding.

That can happen when something holds the slice in a place R doesn't count references for. The main example is a builtin that saves its argument list; the FIXME in cleanupEnvVector() mentions .External.graphics doing exactly this. It's rare, and R itself accepts the same risk in do_for(). But do_for() only does it for attribute-free length-1 vectors, while you'd be doing it for arbitrary user functions on larger arrays.

Two details:

  • Attributes: Only overwrite the data. The slice's dim and dimnames are the same on every iteration, so set them once. If f keeps dim(x), only that attribute vector is shared, not the slice.

  • Type: The buffer must keep the same type and length on every iteration. It does, since every slice of x has the same shape.

Is it worth it?

Probably only a little. Each iteration already pays for an R closure call (building an environment, a promise, and running the body). Allocating a small slice likely costs less than that call. The saving grows with slice size, but so does the time f spends on the slice.

I'd build the simple version first, where each iteration allocates, and benchmark it. Try many small slices with a cheap f like sum, and a few large slices. Add the reuse only if allocation shows up in the profile. If you add it, the change is small: one MAYBE_SHARED() check after storing the result, then either allocate a new slice or keep the old one.

#include <R.h>
#include <Rinternals.h>
#include <string.h>

SEXP poc_map(SEXP x, SEXP f, SEXP reuse) {
  const R_xlen_t n_row = Rf_nrows(x);
  const R_xlen_t n_col = Rf_ncols(x);
  const bool c_reuse = Rf_asLogical(reuse);
  const double* v_x = REAL_RO(x);

  SEXP out = PROTECT(Rf_allocVector(VECSXP, n_col));

  SEXP env = PROTECT(R_NewEnv(R_GlobalEnv, FALSE, 0));
  SEXP x_sym = Rf_install(".x");
  SEXP f_sym = Rf_install(".f");
  Rf_defineVar(f_sym, f, env);

  SEXP call = PROTECT(Rf_lang2(f_sym, x_sym));

  SEXP slice = R_NilValue;
  PROTECT_INDEX slice_pi;
  PROTECT_WITH_INDEX(slice, &slice_pi);

  R_xlen_t n_alloc = 0;

  for (R_xlen_t j = 0; j < n_col; ++j) {
    if (slice == R_NilValue || !c_reuse || MAYBE_SHARED(slice)) {
      REPROTECT(slice = Rf_allocVector(REALSXP, n_row), slice_pi);
      Rf_defineVar(x_sym, slice, env);
      ++n_alloc;
    }

    memcpy(REAL(slice), v_x + j * n_row, n_row * sizeof(double));

    SET_VECTOR_ELT(out, j, Rf_eval(call, env));
  }

  SEXP result = PROTECT(Rf_allocVector(VECSXP, 2));
  SET_VECTOR_ELT(result, 0, out);
  SET_VECTOR_ELT(result, 1, Rf_ScalarReal((double) n_alloc));

  UNPROTECT(5);
  return result;
}

    f <- fs[[name]]

Reuse gives a real speedup once slices reach about 100 elements or more, and nothing for tiny slices. The catch is that it only works when f is a closure (a function written in R). Builtins like sum never get reused.

The POC is in /tmp/rray-map-poc/: map.c is the C loop, check.R tests correctness, bench.R runs the benchmark. To keep it small, it maps over the columns of a double matrix. The reuse test is MAYBE_SHARED() on the slice, checked after f's result is stored.

Correctness

The reuse version matched the always-allocate version for every f I tried:

  • Reused the buffer: function(x) sum(x); functions that modify x (R copies before modifying); and functions that set attributes on x.

  • Allocated a new slice: identity, function(x) list(x), a closure that captures x, and kept <<- x. All earlier slices stayed intact.

One bug turned up that affects both versions. My first draft bound the slice to .x in an environment and called f(.x). With f <- function(x) function() x, x is never evaluated, so every returned closure looked up .x later and saw only the last slice. The fix is to put the slice value directly into the call.

That fix is what breaks reuse for builtins. R evaluates the constant argument before calling sum, and evaluating a constant marks it as permanently shared. So rray_map(x, sum) allocates every time. That's still safe, just slower. With the .x binding, builtins did reuse, but the capture bug came with it.

  • Slices of 100 or more: about 1.2x when f reads the whole slice, up to about 3x when f barely touches it. GC runs mostly disappear. For 1,000 by 1,000, memory allocated drops from 7.7 MB to 16 KB.

My take

It's worth doing, since it's a single MAYBE_SHARED() check. The open design question is builtins. sum and mean-style builtins are probably the most common f for rray_map(). Getting reuse for them means going back to the .x binding, plus a separate fix for the lazy capture bug (for example, making a fresh environment whenever a closure has kept the old one). I haven't tried that.

Nothing is committed, and nothing in the rray4 repo was touched.

It would work, but you don't need the list. A simpler rule is safer and covers every builtin: pick the calling style from the type of f, and keep the MAYBE_SHARED() check for everything.

The rule

  • f is a builtin: bind the slice to .x and call f(.x). Builtins evaluate their arguments right away, so the lazy capture bug can't happen. And since the slice is never evaluated as a constant, it isn't marked as permanently shared.

  • Anything else: put the slice value directly in the call, as before.

In the POC this is a check on TYPEOF(f) == BUILTINSXP plus an if around how the slice is set.

Why not skip the check for a list of builtins

Some builtins return their argument itself instead of a new value, and the refcount check is what catches them. I added these to check.R:

f New slices with reuse on (of 10)
sum, range, c, length 1
invisible, `(`, list, unclass 10

The second row are builtins that hand back x (or a list holding it). Overwriting the buffer after them would silently corrupt earlier results. A list of builtins deemed safe would need to know exactly which ones do this. It would also have to account for internal S3 dispatch, where sum() on a classed slice calls an R method that could keep the slice. The refcount check already handles all of this.

All the earlier correctness cases still pass, including both capture cases.

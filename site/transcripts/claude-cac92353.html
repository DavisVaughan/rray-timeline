10	// Strided iterator plan
11	//
12	// Optimizes and assists in walking a multidimensional point space defined by
13	// `v_dimensions`. As it walks, it updates a user provided `start` in an
14	// alternate subspace defined by `v_strides`.
15	//
16	// For performance and flexibility, the user is responsible for managing the run
17	// loop along the first axis. We've tried many alternative approaches but they
18	// tend to tank performance quickly as you increase the level of abstractions.
19	//
20	// The plan holds only immutable state. The positions that change as it walks
21	// are managed by the caller. This lets the compiler keep these positions in
22	// registers, which has significant performance implications.
23	//
24	// --------------------------------------------------------------------------
25	// Examples
26	//
27	// For broadcasting, the dimensions you broadcast to make up the larger point
28	// space. This is walked in order. The original dimensions of the array make
29	// up the subspace. So as you walk the output's point space you can create
30	// `location`s back into your original array to pull from.
31	//
32	// For reducing, it's actually a special form of broadcasting. The original
33	// dimensions of the array are the point space. The reduced dimensions are the
34	// subspace. So as you walk the original array, you can create `location`s into
35	// the output to accumulate the reduced result at.
36	//
37	// For permuting axes, the permuted dimensions make up the point space. The
38	// original dimensions of the array make up the subspace. So as you walk the
39	// output's point space you can create `location`s back into your original
40	// array to pull from.
41	//
42	// --------------------------------------------------------------------------
43	// Optimization - First axis runs
44	//
45	// After coalescing, the iterator walks the entire first axis in one inner run
46	// while holding all later axes fixed. It only updates the later point
47	// coordinates between runs, rather than checking and carrying them after every
48	// element. This gives the compiler a small loop where the index and locations
49	// advance by fixed strides, making it much easier to optimize and vectorize.
50	//
51	// Practical examples of when this is useful:
52	//
53	// - Identically shaped binary array operations. Adding two [2, 4, 5] arrays
54	//   coalesces to dimensions [40], so the entire operation is one first axis run
55	//   where both input locations advance contiguously.
56	//
57	// - Broadcasting over a later axis. Broadcasting a [2, 3] array to [2, 3, 4]
58	//   coalesces to dimensions [6, 4] with location strides [1, 0]. The iterator
59	//   performs four first axis runs of size 6, copying six contiguous values
60	//   before updating the later axis.
61	//
62	// - Reducing over a later axis. Reducing a [2, 3, 4] array over its third axis
63	//   also coalesces to dimensions [6, 4] with output strides [1, 0]. Each first
64	//   axis run accumulates one contiguous slice into six output locations before
65	//   advancing along the reduced axis.
66	//
67	// --------------------------------------------------------------------------
68	// Optimization - Coalescing
69	//
70	// Coalescing axes is an important optimization used to reduce the number of
71	// axes we have to iterate over by "merging" adjacent compatible ones. This can
72	// improve performance by 3-5x on its own in some cases.
73	//
74	// Practical examples of when this is useful:
75	//
76	// - Identically shaped binary array operations. Adding two arrays with
77	//   dimensions [2, 4, 5] gives both inputs strides [1, 2, 8]. All adjacent axes
78	//   coalesce (2 * 1 = 2, 4 * 2 = 8) into one dimension [40] with stride [1],
79	//   resulting in one flat vectorizable loop.
80	//
81	// - Scalar broadcasting across an entire array. Adding a scalar to a [2, 4, 5]
82	//   array gives the array strides [1, 2, 8] and the scalar strides [0, 0, 0].
83	//   Both coalesce completely, producing a [40] loop with array stride [1] and
84	//   scalar stride [0].
85	//
86	// - Contiguous adjacent axes within a broadcast operation. Broadcasting a
87	//   [2, 3] array over point dimensions [2, 3, 4] produces location strides
88	//   [1, 2, 0]. The adjacent axes 1 and 2 coalesce (2 * 1 = 2) into size 6,
89	//   leaving dimensions [6, 4] and strides [1, 0].
90	//
91	// - Contiguous regions within a reduction. Reducing a [2, 3, 4] array over its
92	//   third axis maps into a [2, 3] result using location strides [1, 2, 0].
93	//   Coalescing produces dimensions [6, 4], making it the same as the broadcast
94	//   example above.
95	//
96	// - Point-space dimensions of size 1. Output point dimensions of [1, 3, 4] can
97	//   have strides [0, 1, 3]. The dimension 1 first axis is absorbed into the
98	//   dimension 3 second axis, adopting stride 1, after which the dimension 4
99	//   third axis also coalesces. The result is one dimension [12] with stride
100	//   [1]. Note that this isn't broadcasting. This is when both input and output
101	//   have an axis that stays dimension 1, which is somewhat rare.
102	//
103	// For iterator2, note that both sets of location strides must be coalescible,
104	// as coalescing changes the output dimensionality, so it's all or nothing.
105	//
106	// --------------------------------------------------------------------------
107	// Optimization - Fixed zero stride paths
108	//
109	// After coalescing, the first axis is walked by the inner loop. A stride of 0
110	// on this axis means that a subspace location stays fixed while the point space
111	// moves along it. Broadcasting uses this to reuse an input value. Reducing uses
112	// it to accumulate into the same output location. A zero stride on a later axis
113	// does not use this path because later axes advance between inner runs.
114	//
115	// When the inner loop receives the stride as a runtime value, the compiler
116	// can't prove that the location is fixed and falls back to a scalar loop. The
117	// public iteration macros check for a zero stride and pass a literal 0 to a
118	// specialized path. This lets the compiler see that the location does not
119	// change. For binary operations, it can then hoist the fixed load out of the
120	// loop and vectorize the remaining stride 1 work.
121	//
122	// Practical examples of when this is useful:
123	//
124	// - Scalar broadcasting across an entire array. Adding a scalar to a [2, 4, 5]
125	//   array coalesces to point dimensions [40], with array strides [1] and scalar
126	//   strides [0]. The scalar location stays fixed while the array and output
127	//   advance contiguously. The same path is used by arithmetic, comparison,
128	//   equality, and extrema operations.
129	//
130	// - Row broadcasting within a matrix. Adding a [1, 4] row to a [2, 4] array
131	//   gives the array strides [1, 2] and row strides [0, 1]. Each inner run
132	//   therefore reuses one row value while the array and output advance
133	//   contiguously.
134	//
135	// - Higher dimensional row broadcasting. Adding a [1, 3, 4] array to a
136	//   [2, 3, 4] array coalesces to dimensions [2, 12], with array strides [1, 2]
137	//   and broadcast strides [0, 1]. Each of the 12 inner runs uses the fixed
138	//   path.
139	//
140	// - Shared leading dimensions of size 1. Adding [1, 1, 4] to [1, 3, 4]
141	//   absorbs the shared first axis and produces dimensions [3, 4], with first
142	//   input strides [0, 1] and second input strides [1, 3].
143	//
144	// - Reducing over the first axis. Reducing a [2, 3, 4] array to [1, 3, 4]
145	//   produces output strides [0, 1, 3], which coalesce to dimensions [2, 12]
146	//   with output strides [0, 1]. Each inner run accumulates into one fixed

What the numbers say

The split is clean along one line: whether the flat plan's run_stride1 (the out stride) is zero.

When it is non-zero, you are splitting on a leading axis, and each inner run writes a single element into each of run_size different output buffers. That is the scattered write case, and nested is 2.5x to 4.5x faster. It holds at 64 MB too, so it is not just a cache-resident artifact.

When it is zero, the out pointer is already loop invariant and the compiler hoists it, so there is no double indirection to remove. Nested is a wash (1.0 to 1.2x).

The memcpy control is a wash almost everywhere (1.00). So the wins are not coming from bulk copies, they are coming from the write pattern. Worth knowing before you spend effort there.

Two consistent regressions, both around 0.8x: multi-axis splits where the split axes are not adjacent (cube axes 1 and 3, 6d even axes). There the nested form re-reads x with a strided pattern once per output element.

I also swept a fixed 64 MB array splitting on axis 1 with the leading dimension from 50 to 16000. Nested won 1.68x to 2.81x at every size except one anomalous shape (2000 x 4000, 0.81x), where the flat kernel is unusually fast for reasons that look like allocation spacing and cache set conflicts rather than anything about the algorithm.

Recommendation

Worth doing, but not as a blanket replacement. A plain swap costs you ~20% on non-adjacent multi-axis splits.

The cheapest useful version is to dispatch on the flat plan you already build: if rray_strided_iterator2_plan_run_stride1(plan) != 0, run nested, otherwise keep the current kernel. That rule picks up every large win and avoids the six_10^6_even_axes loss. It still picks nested for cube axes 1 and 3, so you would carry that one ~20% regression, or add a second condition on the split axes being a contiguous leading block.

The slow rows are where the output element size lands on a power of two after the allocator rounds it (4000, 8000, 16000, 80000 bytes). The flat kernel keeps run_size write streams open at once, so when the allocation spacing is a power of two those streams collide in the same cache sets. That reframes it. The flat kernel is not "usually fast with rare regressions", it is fast when the shape happens to be lucky. 1000x1000, about as plain a case as exists, is one of the unlucky ones and nested is 5.3x there.

Every row where nested loses (0.65, 0.86, 0.96) is a row where current got lucky. Nested never loses to current's bad cases, only to its best ones.

So yes, ship it unconditionally

The dispatch rule I floated is not worth it. It would buy back the 0.65 and 0.86 rows and cost you the predictability, plus two kernels to maintain.

What you actually give up:

  • Multi-axis splits on non-adjacent axes, about 0.8x. rray_split(x, c(1, 3)) on a 3d array, or 6d even axes. Genuinely rare.

  • Shapes where the allocator happens to space outputs well, up to 0.65x. Not predictable by a user, so not something anyone is relying on.

29	# Part 2: Why the double core isn't just `fmod()`
30	
31	The obvious definition is `x %% y = x - floor(x / y) * y` and
32	`x %/% y = floor(x / y)`. That's what R computes, but not how R computes it.
33	`src/main/arithmetic.c` in R's own source has two static functions, `myfmod()`
34	and `myfloor()`, that compute it more carefully:
35	
36	- A short circuit for `fabs(x1) <= fabs(x2)`, which avoids a division (and the
37	  rounding error a division introduces) whenever the direct sign comparison
38	  already gives the answer.
39	
40	- A `long double` intermediate in the general case
41	  (`tmp = (long double)x1 - floor(q) * (long double)x2`), which halves the
42	  rounding error against doing the same arithmetic purely in `double`.
43	
44	- A warning ("probable complete loss of accuracy in modulus") when
45	  `fabs(q) * DBL_EPSILON > 1`, i.e. when the quotient is large enough that the
46	  double subtraction can't be trusted at all.
47	
48	- `x2 == 0` returns `NaN` for `%%`, not `NA`. `myfloor()` doesn't special case
49	  it at all — `x1 / 0.0` is already `Inf`, `-Inf` or `NaN` under IEEE 754, which
50	  is exactly what R's `%/%` returns for a double `0` divisor.
51	
52	Neither function is exported. They're `static` in `arithmetic.c`, not declared
53	in `Rmath.h`, so matching R here means porting the logic, not calling into R.
54	
55	The comment directly above `myfmod()` reads "Keep myfmod() and myfloor() in
56	step" — they're two instances of the same idea (division with a
57	precision-guarded remainder), and R's own maintainers treat them as a pair that
58	has to be changed together. Do the same if either one is ever touched.

62	# Part 3: The int core doesn't need its own version of this
63	
64	For `%%`, R's int arm is:
65	
66	```c
67	(x1 >= 0 && x2 > 0) ? x1 % x2 : (int) myfmod((double) x1, (double) x2);
68	```
69	
70	C's `%` truncates (sign follows the dividend), but `%%` is documented to floor
71	(sign follows the divisor) — the same convention Python uses. Those only agree
72	when both operands are non-negative, which is the fast path above. Everywhere
73	else, R doesn't hand-roll a second floored-mod implementation in integer
74	arithmetic — it reuses `myfmod()` by promoting to `double`. That round trip is
75	exact: R's integer range fits inside ±2^31, and a `double` mantissa holds
76	integers exactly up to 2^53, so nothing is lost. One canonical implementation
77	of "floored modulo, correctly signed, correctly handling zero" beats two copies
78	that have to be kept in agreement forever.
79	
80	`%/%`'s int arm doesn't need any of this:

83	(int) floor((double) x1 / (double) x2);
84	```
85

88	real: `%%` needs the precision-guarded fallback for integers, `%/%` doesn't.

# Specialize stride 0 in the iterator inner loop

Not built. This document records a measured 1.8x win available in
`RRAY_ITERATOR2_FOR_EACH()`, why it exists, the exact change, and the evidence.

Short version: when either input is broadcast along the innermost axis, the
inner loop silently falls off clang's vectorized path onto a scalar fallback.
Passing a literal `0` for that stride puts it back on the vector path. It costs
code size.

---

# Part 1: What is slow

`RRAY_ITERATOR2_FOR_EACH()` reads both row strides out of the iterator:

```c
const r_ssize rows = v_point_dimensions[0];
const r_ssize row_stride1 = v_location1_strides[0];
const r_ssize row_stride2 = v_location2_strides[0];
```

Both are runtime values. `rray__location_strides_init()` sets a stride to `0`
on any axis where that input has a dimension of 1, which is how broadcasting is
expressed. So `row_stride2 == 0` means "y is broadcast along the innermost
axis".

Timings for `rray_compare_dbl_dbl()` at 1e6 elements, min of 200 reps:

| inner stride pair | min (ms) |
|---|---|
| `(1, 1)` | 0.229 |
| `(1, 0)` | 0.410 |

That is the same compiled function, called twice, with different data in the
iterator. 1.8x apart.

## Which shapes hit it

Not simply "the first axis has a dimension of 1". Coalescing absorbs leading
axes whose broadcast dimension is 1, so the test is on the coalesced axis 0.

The rule: skip leading axes whose broadcast dimension is 1. At the first axis
where the broadcast dimension is greater than 1, if either input has a
dimension of 1 there, that input gets stride 0 and you pay the 1.8x.

For matrices that reduces to: broadcasting a row vector `[1, n]` is slow,
broadcasting a column vector `[m, 1]` is fast. Broadcasting along the
contiguous direction is what costs you, which is a statement about column-major
layout.

Two shapes show why the naive test is wrong:

- `x[1,1000,1000]` against `y[1,1000,1000]` has a leading 1 on both sides, but
  neither is broadcast against the other, so the axis is absorbed and it
  coalesces to one contiguous run. Fast.

- `x[100,100,100]` against `y[100,1,100]` has y broadcast, just not on the
  first axis. Fast.

---

# Part 2: Why it is slow

It is not the cost of `LOCATION2 += row_stride2`. That add executes either way,
in identical machine code.

Clang versions the loop. It emits one vectorized body plus a scalar fallback,
and chooses between them at runtime with a guard emitted just before the loop.
Disassembling `compare_current` from the harness in Part 6:

```asm
38:  cmp   x10, #0x1
3c:  ccmp  x11, #0x1, #0x0, eq
```

That is `row_stride1 == 1 && row_stride2 == 1`. Both strides must be exactly 1.
With `row_stride2 == 0` the guard fails and the whole loop runs scalar.

The reason clang guards rather than handling stride 0 is that with an unknown
runtime stride, `v_y[y_loc]` has an unknown access pattern. Vectorizing it
would need a gather, which is not profitable on NEON, so it guards on the one
case it can vectorize and gives up otherwise.

Passing a literal `0` changes what the compiler can prove about the load, not
about the add. `y_loc` becomes provably constant across the run, so
`v_y[y_loc]` hoists out of the loop body entirely. What remains touches only
`v_x` and `v_out` at stride 1, which vectorizes without needing the guard that
was failing.

Vector compare instructions (`fcmge.2d`, `fcmgt.2d`) in the two functions:

- current: 4, so one vectorized body

- fixed: 12, so three, one per arm

# Rewrite `rray_split()` as a two stage traversal

Not built. This document records a measured 2.5x to 5x win available in
`rray_split()`, why it exists, the exact change, and the evidence.

Short version: the flat kernel keeps one write stream open per output array
while it walks `x`. When you split on a leading axis there are many of those
streams, they collide in the cache, and the cost swings by 8x depending on
where the allocator happened to place the outputs. Walking the split axes and
the retained axes as two nested loops writes one output at a time, which is
both faster and predictable.

Depends on `feature/mean`. That branch introduces `rray_reduce_nested()`, the
per axes plan helper this reuses, and the zero dimensionality normalization in
`rray_strided_iterator_plan()` that the empty complement relies on.

---

# Part 1: What is slow

`rray_split()` builds a single `rray_strided_iterator2_plan` over the point
space of `x`, reporting two locations as it walks: one into the output list,
one into the current output element.

```c
struct rray_strided_iterator2_plan plan = rray_broadcast_iterator2_plan(
  v_out_dimensions,
  dimensionality,
  v_out_elt_dimensions,
  dimensionality,
  v_x_dimensions,
  dimensionality
);
```

Because the list location is a runtime index, `RRAY_SPLIT_ATOMIC()` has to
carry an array of pointers to every output element and index into it:

```c
r_obj* shelter = KEEP(r_alloc_raw(out_size * sizeof(CTYPE*)));
CTYPE** v_v_out = (CTYPE**) r_raw_begin(shelter);
```

Whether that second indirection costs anything depends on the plan's first
axis stride into the list, `run_stride1`.

When it is zero the list location is loop invariant, the compiler hoists
`v_v_out[out_loc]`, and the run is an ordinary contiguous copy. This is what
you get splitting on a trailing axis.

When it is non-zero every iteration writes a single element into a different
output buffer:

```c
} else if (out_elt_run_stride == 0) {
  for (r_ssize i = run_start; i < run_end; ++i) {
    v_v_out[out_loc][out_elt_loc] = v_x[i];
    out_loc += out_run_stride;
  }
}
```

This is what you get splitting on a leading axis, which is the common case:
`rray_split(x, 1)` on a matrix. Reads stay contiguous, but `run_size` separate
write streams stay open at once, each advancing by one element per outer
iteration.

## Why that is worse than it looks

Splitting a `1000x1000` matrix on axis 1 leaves 1000 open streams. The spacing
between them is whatever the allocator chose for a 1000 element double vector,
which after rounding is 8192 bytes. A power of two spacing maps every stream
onto the same cache sets, so essentially every write is a conflict miss.

Change the shape slightly and the spacing stops being a power of two and the
conflicts disappear. That is the 8x swing in Part 2.

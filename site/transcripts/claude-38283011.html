// Wrap an R object in a lightweight ALTREP wrapper
//
// Useful when only modifying the attributes of an object,
// without touching the underlying data.
//
// - Read only accesses to the data are "passed through" to the wrapped object
// - Writable access forces a shallow duplication of the wrapped object if it
//   EVER looks shared, which happens if we are wrapping a basic R object
//   supplied from the R side by a user, or if we rewrap a wrapper's underlying
//   data (because the original wrapper also shares it).
r_obj* r_wrap(r_obj* x) {
  R_altrep_class_t cls = wrapper_class(r_typeof(x));

  // If `x` is a wrapper, unwrap it to gain access to the underlying data. This
  // is what we wrap and bump the reference count of. This avoids a
  // proliferation of wrappers. We manage writable access to the underlying data
  // by always cloning it before giving out a writable handle if it is ever
  // `MAYBE_SHARED()` (i.e. a ref count >1), meaning that we aren't the sole
  // owner of it at that time.
  r_obj* data = is_wrapper(x) ? wrapper_data(x) : x;

  // Reference count on `data` is bumped when we wrap it here.
  // It now looks at least "referenced", but not necessarily "shared".
  r_obj* out = KEEP(R_new_altrep(cls, data, r_null));

  // Creates a fresh attribute pairlist!
  // Note that we always use `x` here, not `data`.
  r_attrib_clone_from(out, x);

  MARK_NOT_MUTABLE(out);

  FREE(1);
  return out;
}

Yes, essentially. After the last few commits, r_wrap() makes a view: a new object with its own attributes that reads the data of x without copying it.

The code now does three things:

  • Its own attributes. r_attrib_clone_from(out, x) gives the view a fresh attribute pairlist.

  • No copy of the data. Every read method (Dataptr, Dataptr_or_null, Elt, Get_region) forwards to wrapper_data(x).

  • Read only. MARK_NOT_MUTABLE(out) makes R copy before it changes the object, and wrapper_duplicate() returns a plain non-ALTREP copy. Nothing ever turns a view back into an owner.

That makes it different from R's own wrapper classes (wrap_integer etc. in altclasses.c). Those copy the data on the first write when it is shared, so they move from "view" to "owner". Ours never does, and "view" describes that better than "wrapper".

Three things to know before renaming:

  1. For atomic types, read only is a promise, not a check. wrapper_double_dataptr() returns the shared pointer even when writeable is true, and ffi_test_wrapper_pointer_is_stable() tests exactly that. It can't abort the way the character and list versions do, because R calls the writable DATAPTR() path inside plain reads (INTEGER(), REAL()). So a C caller that writes through r_dbl_begin() on a view would change x. That is the same rule that applies to any shared R vector, but it is worth knowing.

  2. The block comment above r_wrap() is out of date. It still says writable access "forces a shallow duplication ... if it EVER looks shared". The code no longer does that. I left it alone because it's your comment. If we rename, it should be rewritten along with the rest.

  3. "View" might suggest more than it does. In numpy, a view can also be a slice (an offset and a length into the parent). Ours always covers the whole vector. That's fine for now. If you ever want cheap contiguous slices (for example a leading-axis rray_slice()), a view type is where that would go, which is one more reason the name fits.

The rename itself is mechanical: r_wrap() → r_view(), is_wrapper() → is_view(), wrapper_data() → view_data(), wrapper.c/.h → view.c/.h, the decl header, the wrapper_* ALTREP class names, the ffi_test_* helpers, new_wrapper_arg() in arg.h, and the tests. Changing the class names breaks nothing saved to disk, because wrapper_serialized_state() returns NULL and so views are never serialized as ALTREP. Want me to do it?

# An immutable `r_wrap()`

`r_wrap()` (`src/wrapper.c`) has a memory safety bug. This plan fixes it by
making the wrapper immutable: its data never changes after it is created.
rray keeps its zero-copy reshapes (`rray_set_dimensions()`,
`rray_insert_axes()`, `rray_remove_axes()`, the names and titles setters, and
the internal reshapes in `rray_split()`, `rray_stack()` and
`rray_unstack()`).

The work is one pull request. Part 1 explains the bug, Part 2 the design and
why it is safe, Part 3 the code changes, and Part 4 the tests.

Earlier versions of this plan (commits `9172a64` and `4565791`) took other
routes: locking the wrapper like base R, with `r_unwrap()` everywhere, and
then removing the wrapper entirely. Both are dropped. Nothing from them is
implemented yet.

---

# Part 1: The bug

When something asks the wrapper for a writable pointer, and the wrapped data
might be shared, the wrapper copies the data and puts the copy in `data1`.
Any read-only pointer handed out before that points into the old `data1`:

```c
const double* p = REAL_RO(w);
double* q = REAL(w);
q[0] = 99;
// p[0] == 1, q[0] == 99, w[1] == 99
```

That pointer is stale at best. It can also dangle: refcounts in R only go
down when a slot is overwritten, not when the object holding the reference is
garbage collected. So the old `data1` can look shared while nothing reachable
holds it, and the next GC frees it.

Base R's own wrapper had the same bug, fixed in R-devel by Luke Tierney
(`dbc99e13e8`, `c40bda6593`, `3580627fa3`). His fix locks the wrapper and
copies on the first pointer request of any kind.

There is a second, smaller problem. Today a pointer request on the wrapper
can allocate (the copy), and so can longjmp on an out of memory error. Code
calling `REAL_RO()` does not expect that, and IDEs like RStudio and Positron
(ark) are not always ready for a jump from such a point.

---

# Part 2: Design

## The rules

1. **`data1` never changes.** It is set once in `r_wrap()`. Every pointer
   into it stays valid for as long as the wrapper is reachable, because the
   wrapper keeps `data1` alive.

2. **`data1` is the input itself**, or the `data1` of a wrapper input. An
   ALTREP input from another class (a compact sequence like `1:n`, a
   deferred string, an arrow or vroom vector) is wrapped as is. We rely on
   that class keeping its data pointer stable, which is the basic contract of
   an ALTREP `Dataptr` method. Base R's own wrapper breaks that contract in
   released R versions, but that is base R's bug, every `dim<-` user is
   already exposed to it, and it is fixed in R-devel.

3. **Every wrapper is marked not mutable**, with `MARK_NOT_MUTABLE()`. R then
   treats the wrapper as shared, so it duplicates the wrapper before changing
   it in place.

4. **`Duplicate` always returns a plain vector**, never a wrapper. So every
   change R makes lands on a fresh vector R owns.

5. **A data pointer request never copies.** A read-only request returns a
   pointer into `data1`. A writable request on an atomic wrapper also returns
   a pointer into `data1`. A writable request on a character or list wrapper
   aborts, as it does today.

6. **`Set_elt` aborts.** Only code that writes into an object it does not
   own can reach it.

## Why rule 5 returns a pointer for writable requests

A lot of C code asks for a writable pointer only to read. `REAL()`,
`INTEGER()` and friends are writable requests, and in R 4.6 even `RAW_RO()`
calls `RAW()` internally (see the note in `src/rlang/vec.h`). In testing,
about 600 base R operations made 30,303 writable requests on wrappers. All
of them were reads. Aborting there would break base R.

## Why this is safe

`MARK_NOT_MUTABLE()` sets the refcount to its maximum, and
`DECREMENT_REFCNT()` never lowers it from there (`src/include/Defn.h`). Every
place where R reuses an object's memory, or writes into an argument instead
of allocating, first checks `NO_REFERENCES()`, `MAYBE_REFERENCED()` or
`MAYBE_SHARED()`. That is 72 checks across `arithmetic.c`, `subassign.c`,
`coerce.c`, `attrib.c`, `eval.c` and others. All of them see the wrapper as
shared, and copy first.

The case that matters most is reuse of a temporary. `w + 1` writes the result
into `w`'s memory when `w` has no references (`R_allocOrReuseVector()` in
`src/main/arithmetic.h`). That is how a temporary rray result gets a writable
request today. A not-mutable wrapper never passes that check.

A prototype of this design was tested against R 4.6:

- About 600 base R operations on wrappers of all seven types, sharing data
  with a vector still bound in R: 831 wrappers, 30,303 writable requests, no
  change to any wrapper's data or to any original vector. Character and list
  wrappers got no writable requests and no `Set_elt` calls.

- rray's own test suite: 4,310 wrappers, no change to any wrapper's data.
  The only writable requests from rray itself were raw reads, through the
  `RAW_RO()` issue above.

Part 4 turns this into a permanent test file, run on every CI platform.

## Allocation

The wrapper's own methods never allocate, apart from `Duplicate`, which R
expects to allocate. Dataptr, Dataptr_or_null, Elt, Get_region and Length only
read `data1`.

When `data1` is a plain vector, `REAL_RO()` and friends on a wrapper never
allocate and never longjmp. When `data1` is an ALTREP vector, its own
`Dataptr` may allocate on the first request, the way a compact sequence
expands itself. That is exactly what reading the input directly would do, so
the wrapper adds no new allocation point.

## Costs

- **The first change to a wrapper copies**, even when nothing else shares its
  data. `y <- rray_set_dimensions(x, d); y[1] <- 0` copies `y` once, and
  later changes to `y` happen in place. Base R's `dim<-` would usually have
  copied at the reshape instead, so overall this is no worse than base R.

- **Code that breaks R's rules writes through to the original.** C code that
  writes into an object through `REAL()` without checking whether it is
  shared would write into the user's original vector. That is wrong values,
  not unsafe memory, and the same code already does it to any ordinary shared
  vector.

## `r_wrap()`

```c
r_obj* r_wrap(r_obj* x) {
  R_altrep_class_t cls = wrapper_class(r_typeof(x));

  r_obj* data = is_wrapper(x) ? wrapper_data(x) : x;

  r_obj* out = KEEP(R_new_altrep(cls, data, r_null));

  r_attrib_clone_from(out, x);

  MARK_NOT_MUTABLE(out);

  FREE(1);
  return out;
}
```

## Data section

Replace `wrapper_readonly()` and `wrapper_writable()` with:

```c
static inline r_obj* wrapper_data(r_obj* x) {
  return R_altrep_data1(x);
}
```

Wrapping a wrapper shares its `data1`, as today. Since `data1` never changes,
sharing it between wrappers is safe.

# `r_wrap()` starts with no attributes

Today `r_wrap(x)` copies every attribute of `x` onto the new wrapper. This
plan makes the wrapper start with no attributes, so each caller sets exactly
the ones it wants.

The work is one pull request. It lands before `plans/view.md`, so this plan
still uses the current `wrapper` names.

---

# Why

## Stray attributes leak through

Functions that go through `r_wrap()` keep any attribute the input happens to
carry. Functions that allocate a new result drop them. So two reshapes of the
same input disagree:

```r
x <- array(1:4, c(2, 2))
attr(x, "foo") <- 1
names(x) <- letters[1:4]

attributes(rray_set_dimensions(x, c(4L, 1L)))
#> $dim: 4 1
#> $foo: 1
#> $names: "a" "b" "c" "d"

attributes(rray_permute_axes(x, 2:1))
#> $dim: 2 2
```

`rray_insert_axes()` keeps `foo` and `names` the same way. `class` can't leak,
because `check_unclassed()` rejects classed input first.

After this plan, every function above returns only `dim` and, when there are
any, `dimnames`.

## Every caller only wants `dim` and `dimnames`

All 9 callers of `r_wrap()` set `dim`, `dimnames`, or both, and nothing else.
Two of them spend extra work undoing the copy: `rray_set_dimensions()` clears
`dimnames`, and `vec_as_array()` clears `names`.

## No pairlist copy

`r_attrib_clone_from()` allocates a copy of the attribute pairlist on every
call. A wrapper with no attributes skips that.

## Nothing relies on the copy

No test outside `test-wrapper.R` checks that a stray attribute survives, and
no C code reads an attribute other than `dim` or `dimnames` off the result of
`arg_as_array()`.

---

# Out of scope

Some paths return `x` itself, so stray attributes still pass through them.
This plan leaves them alone. A later plan can decide whether they should also
return a view with only `dim` and `dimnames`:

- `vec_as_array()` when `x` already has `dim`.

- `rray_clear_titles()` and `rray_clear_axis_title()` when there are no
  titles to clear.

- `rray_cast()` when `x` and `to` have the same type, through
  `vec_as_array()`.

---

# A note on order

`Rf_setAttrib()` refuses to set `dimnames` on an object with no `dim`. Every
caller that sets `dimnames` must set `dim` first. The names and titles setters
used to get `dim` for free from the copy, so they now set it themselves from
`r_dim(x)`.

# Rename the ALTREP wrapper to a view

After `plans/wrap.md` and `plans/attributes.md`, `r_wrap(x)` returns an
object that:

- shares the data of `x` and never copies it,

- is read only, since R always copies it before changing it,

- starts with no attributes, so the caller sets its own.

That is a read-only view, and "view" says so better than "wrapper" does. Base
R's own wrapper classes behave differently: they copy their data on the first
write and become the owner. Ours never does.

This plan renames everything. It is a pure rename: no behavior changes, apart
from the wording of a few internal error messages.

The work is one pull request. It lands after `plans/attributes.md`, and
assumes the tests that plan adds and renames are in place.

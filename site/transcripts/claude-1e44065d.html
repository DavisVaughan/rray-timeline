No. No mainstream array library does both things at once. The shape rule in rray_combine() (sum along .axis, broadcast every other axis, pad missing trailing axes with 1) is close to unique. The nearest relatives each do one piece of it.

I could not verify this locally, numpy is not installed on this machine, so the below is from knowledge of the docs rather than a live check.

Library Sum along axis Broadcast other axes Pad missing axes
np.concatenate yes no, exact match required no, ndim must match
np.vstack / hstack / block yes no yes, but prepends 1s
torch.cat, tf.concat, jnp.concatenate yes no no
Julia cat / hcat / vcat yes no yes, appends 1s
base R cbind / rbind yes recycling, not broadcasting yes
xarray.concat yes label alignment, not broadcasting yes, by dimension name

A few notes on the interesting ones:

np.concatenate is strict on purpose. It raises all the input array dimensions except for the concatenation axis must match exactly. The documented idiom is two steps: np.broadcast_shapes() to work out the target, np.broadcast_to() each input, then concatenate. That is exactly what we do internally, we just do it in one pass.

np.vstack() and friends look like they broadcast but they only promote dimensionality, via atleast_2d(). And they prepend the new axis where we append it, because numpy is row-major with leading axes and R is column-major with trailing axes. So np.vstack on shapes (3,) and (2, 3) works, but (2, 1) and (2, 3) still fails.

Julia is the closest on the padding rule. hcat([1, 2], rand(2, 3)) works because a length-2 vector is treated as 2x1, same implicit trailing 1 we use. Julia still refuses to broadcast a dimension of 1 up to n.

xarray.concat() is the closest in spirit, but the mechanism is different. It matches axes by name, not position, and it resolves a size mismatch by joining the labels (outer or inner join) rather than broadcasting a 1. It does broadcast a variable that is missing a dimension entirely, which is the labelled version of our trailing-1 rule. pandas.concat(axis=1) is the same idea in 2d.

The real precedent is the original rray. rray_bind() already did this, and its docs call it out directly: "It uses broadcasting to combine arrays together in a way that the native functions of cbind() and rbind() cannot."

So the fair framing is that we are not following numpy here, we are following base R's cbind() and rbind(), which have always accepted a scalar or short vector alongside a matrix. We replace their length-based recycling with proper shape-based broadcasting.

You're right, that was wrong. Broadcasting each input to one common shape would force the combine axis to a common dimension too, which is exactly what you don't want. np.broadcast_shapes((2, 3), (2, 1)) gives (2, 3), so for axis=2 both inputs become 2x3 and you get a 2x6 result instead of the 2x4 we want. Worse, (2, 3) and (2, 5) would just fail to broadcast at all, even though combining them along axis 2 is perfectly well defined.

I also overstated calling it "documented". numpy doesn't document a broadcasting concat anywhere. It's a hand-rolled pattern, and the naive version of it is broken for the reason you gave.

The correct version has to hold the combine axis out of the broadcast:

def rray_combine(arrays, axis):
    ndim = max(a.ndim for a in arrays)
    # R-style trailing pad; broadcast_to would prepend instead
    arrays = [a.reshape(a.shape + (1,) * (ndim - a.ndim)) for a in arrays]

    # mask the combine axis to 1 so it can't participate
    masked = [a.shape[:axis] + (1,) + a.shape[axis + 1:] for a in arrays]
    common = np.broadcast_shapes(*masked)

    # put each input's own axis dimension back before broadcasting
    arrays = [
        np.broadcast_to(a, common[:axis] + (a.shape[axis],) + common[axis + 1:])
        for a in arrays
    ]
    return np.concatenate(arrays, axis=axis)

Three passes and two temporary allocations per input, versus our single pass that computes the output dimensions and strided-copies straight into the result.

I can't run this here, numpy isn't installed on this machine, so treat the code as reasoning rather than something I checked.

This strengthens the point from before rather than weakening it. The shape rule isn't just missing from numpy, it isn't cleanly expressible in terms of numpy's own broadcasting primitives, because broadcast_shapes() has no notion of an excluded axis. Which is a decent argument that our rule is the right thing to build in at the C level rather than leave to callers.

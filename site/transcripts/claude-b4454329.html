// Wrap an R object in a lightweight ALTREP wrapper
//
// Useful when only modifying the attributes of an object,
// without touching the underlying data.
//
// - Read only accesses to the data are "passed through" to the wrapped object
// - Writable access forces a shallow duplication of the wrapped object if it
//   EVER looks shared, which happens if we are wrapping a basic R object
//   supplied from the R side by a user, or if we rewrap a wrapper's underlying
//   data (because the original wrapper also shares it).
r_obj* r_wrap(r_obj* x) {
  R_altrep_class_t cls = wrapper_class(r_typeof(x));

  // If `x` is a wrapper, unwrap it to gain access to the underlying data. This
  // is what we wrap and bump the reference count of. This avoids a
  // proliferation of wrappers. We manage writable access to the underlying data
  // by always cloning it before giving out a writable handle if it is ever
  // `MAYBE_SHARED()` (i.e. a ref count >1), meaning that we aren't the sole
  // owner of it at that time.
  r_obj* data = is_wrapper(x) ? wrapper_readonly(x) : x;

  // Reference count on `data` is bumped when we wrap it here.
  // It now looks at least "referenced", but not necessarily "shared".
  r_obj* out = KEEP(R_new_altrep(cls, data, r_null));

  // Creates a fresh attribute pairlist!
  // Note that we always use `x` here, not `data`.
  r_attrib_clone_from(out, x);

  FREE(1);
  return out;
}

static r_obj* wrapper_duplicate(r_obj* x, Rboolean deep) {
  if (deep) {
    // Wrapper only guarantees shallow ownership.
    // No need to return another wrapper if we fully duplicate.
    return Rf_duplicate(wrapper_readonly(x));

Yes, you're right, and it is worse than a stale pointer. I reproduced both problems against the current r_wrap().

What goes wrong

wrapper_writable() (src/wrapper.c) swaps a new copy into data1 whenever the wrapped data looks shared. Any read-only pointer handed out before that swap still points at the old data.

1. Stale pointer. If someone else still owns the old data, the pointer stays valid but no longer shows the wrapper's contents:

const double* p = REAL_RO(w);
double* q = REAL(w);   // clones, swaps data1
q[0] = 99;
// p[0] == 1, q[0] == 99, w[1] == 99

2. Use after free. R refcounts are only an upper bound. Here MAYBE_SHARED() is true, yet the wrapper is the only thing that can still reach the data:

x <- as.double(1:1e6)
l <- list(x)   # bumps refcount, never decremented
w <- wrap(x)
rm(x, l)

After the swap, the old vector is unreachable and the next GC frees it. With MallocScribble=1, reading p[0] after a GC returned 1.194531e+103. That is the 0x5555... scribble pattern, so the read really is from freed memory.

The repro is in the scratchpad (repro/repro.c, repro/repro.R). I made no changes to rray.

Base R

Base R's own wrapper class has exactly the same pattern today, in WRAPPER_WRAPPED_RW() at src/main/altclasses.c:1440. It dates from 2018 and I found no commit that changes it. The recent R work I found is nearby but different:

  • Sep 2025 (PR#18759, PR#18761, PR#18762): duplicate1(), R_compute_identical() and copyVector() now read through *_RO accessors, so they no longer trigger a writable copy of ALTREP objects just to read them.

  • Nov 2025: DATAPTR_RW() was added for use inside ALTREP Dataptr methods.

If you remember a commit that fixes the hazard itself, I didn't find it in the log.

R's own code mostly avoids the problem by asking for the writable pointer before the read-only ones (for example real_binary() in arithmetic.c). The trigger is any caller that does it the other way round: read-only first, then writable on the same object.

Fix options

  1. Keep the old data alive. Hold on to the replaced vector (for example in data2) instead of dropping it. This removes the use after free for the life of the wrapper. The stale-pointer behaviour stays, which matches base R. The cost is keeping both copies in memory after a write.

  2. Refuse writable access for every type, as the character and list wrappers already do. This makes the problem impossible, but it may break R code that writes in place through REAL(), such as [<- on a wrapper. I haven't checked which base R paths do that.

  3. Copy on any data pointer request, read-only included. This makes the problem impossible too, but it defeats the purpose of the wrapper.

I'd go with option 1. Do you want me to implement it?

Do we really need the “locked” idea

Claude

Not strictly, but dropping it makes rewrapping more expensive. The lock records one bit that the refcount can't tell us: whether this wrapper has ever handed out a pointer.

What has to stay true

Once a wrapper hands out a pointer, its data1 must never be swapped again. A swap only happens when the data looks shared. Right after a pointer is handed out the data's refcount is 1, so the only risk is it rising later. Nothing outside rray can reach data1, so only our own code can raise it:

  • wrapper_duplicate() with deep = FALSE rewraps the same data.

  • r_wrap() on a wrapper unwraps it and shares the data.

Without the lock

Use the refcount itself as the rule. When rewrapping or duplicating, share the data only if it is already MAYBE_SHARED(), and copy it otherwise.

This is safe because a pointer is only handed out once the data's refcount is 1. Sharing data whose refcount is already 2 or more can't touch any data with a live pointer. Copying in the other case means a refcount of 1 never goes back up. No extra state is needed.

The cost is that a refcount of 1 is ambiguous. It can mean "a pointer is out there", or just "this wrapper owns its data and nobody has looked at it". The rule has to assume the first, so it copies in both cases. The second case is the common one for rray chains:

x |> rray_set_names(nms) |> rray_set_dimensions(dims)

When x is a temporary, the first wrapper is the sole owner of its data. Without the lock, every later rewrap in the chain copies. With the lock, those rewraps share for free, and only a wrapper that actually handed out a pointer copies.

Recommendation

Keep the lock, it's cheap. We don't use data2, so the flag can live there (for example data2 = r_true once locked), with no PRSEEN trick needed.

Note that our own rray_unwrap() borrows would not set the lock. They protect the data themselves, so the wrapper doesn't need to promise anything. Only the official Dataptr and Dataptr_or_null methods lock.

I'd skip R's refcount error check on locked data. Both ways the refcount could rise go through wrapper.c, and the rule above covers both.

Two cases when a pointer is requested

Say a user wraps their own vector and then something asks for a pointer:

x <- c(1, 2, 3)
w <- rray_set_names(x, nms)   # data1(w) is the user's x

1. The data looks shared. While x is still bound, the vector is referenced by the binding and by the wrapper, so its refcount is at least 2. The pointer request copies it with r_clone_data() and installs the copy in data1. The copy is a fresh plain vector, and only the wrapper refers to it, so its refcount is 1. The pointer points into that copy, never into the user's vector.

2. The data doesn't look shared. If the user's binding is gone and R decremented the refcount, the wrapper is the only thing that refers to the vector. Its refcount is 1, so we hand out a pointer into the user's original vector without copying. That's fine: nobody else can see it through R anymore.

So the claim is: after a pointer request, data1 has a refcount of exactly 1. Either it was 1 already, or we just replaced it with a copy whose refcount is 1. It can't be 0, because the wrapper itself counts as a reference.

The case R's third commit handled

R's follow-up commit 3580627fa3 exists because this can fail for R's own wrapper. R copies with shallow_duplicate(). When the wrapped data is itself ALTREP (say a compact 1:10, or a vroom or arrow vector), that call dispatches to the other class's Duplicate method. That method can return an object whose refcount is already above zero. R then marks the lock as 2, meaning locked but with no guarantee about the refcount.

We don't have that problem. r_clone_data() (src/clone.c) never calls Duplicate. It always allocates a fresh plain vector and copies into it, so whatever the input class is, the copy starts at refcount 0 and is 1 once installed.

Effect on the earlier argument

This holds with or without the lock. The lock only decides what happens on a later rewrap: share the refcount-1 data (unlocked) or copy it (locked).

Yes. r_wrap() copies every attribute of x onto the new wrapper, plus the object bit and the S4 bit.

r_attrib_clone_from() is rlang's name for SHALLOW_DUPLICATE_ATTRIB() (src/rlang/attrib.h:31). In R that is (src/main/memory.c:3968):

SET_ATTRIB(to, shallow_duplicate(ATTRIB(from)));
SET_OBJECT(to, OBJECT(from));
IS_S4_OBJECT(from) ? SET_S4_OBJECT(to) : UNSET_S4_OBJECT(to);

What that means for r_wrap():

  • The attribute list is new, its values are shared. The wrapper gets its own pairlist of attributes, but the values (dim, dimnames, class, ...) are the same objects as on x, with their refcounts bumped. Callers like rray_set_names() then replace entries on out without touching x.

  • Attributes always come from x. If x is a wrapper, the wrapper's attributes are copied, not the ones on the data inside it. The code comment at that line says this too.

  • The wrapped data keeps its own attributes. When we wrap a user's vector, data1 still has the user's original attributes attached. Nothing reads them through the wrapper, so this is harmless today.

That last point matters for the rray_unwrap() idea. The unwrapped vector can carry out-of-date dim or dimnames. Code that borrows a pointer from it must still read dimensions and names from x, never from data.

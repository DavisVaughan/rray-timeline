Evaluating axis sorting and allocation trade-offs

Yes. For reduce, split, and squeeze, requiring sorted axes seems too strict. In those operations, axes describes a set. c(3, 1) has the same meaning as c(1, 3), so requiring callers to provide the internal canonical order leaks an implementation detail.

I would normalize internally:

  • Validate type, bounds, missing values, and attributes.
  • Reject duplicate axes. c(1, 1) is more likely a mistake than useful input.
  • Sort the validated axes into increasing order.
  • Let downstream code continue assuming sorted, unique axes.

That preserves the useful invariant without imposing it on users.

The important distinction is whether order carries meaning:

  • rray_sum_along(x, c(3, 1)): order should not matter.
  • rray_split(x, c(3, 1)): with the current result layout, order should not matter.
  • rray_squeeze(x, c(3, 1)): order should not matter.
  • rray_move_axes() and rray_permute_axes(): order absolutely matters and must be preserved.

You already reflect that distinction with arg_as_axes() versus the unsorted and permutation validators. I would make arg_as_axes() a normalizing validator rather than a rejecting validator.

The only reason to retain the restriction would be if you intentionally want reversed axes to signal that the user may misunderstand the API. I do not think that benefit outweighs the friction. Documentation can state that axes are treated as a set and normalized to increasing order.

#'
#' `rray_move_axes()` moves `axes` to new positions. The axes that don't move
#' keep their relative order, and fill in the positions that are left over.
#'
#' @details
#' Names travel with their axis to its new position.
#'
#' @param x An array.
#'
#' @param axes An integer vector of axes to move. It must not use an axis of
#'   `x` more than once.
#'
#' @param to An integer vector of positions to move `axes` to. `axes[[i]]` ends
#'   up at position `to[[i]]`. It must be the same length as `axes`, and must
#'   not use a position more than once.
#'
#' @returns
#' An array with the `axes` of `x` moved to the positions in `to`.
#'
#' @seealso [rray_permute_axes()]
#'
#' @export
#' @examples
#' x <- array(1:24, c(2, 3, 4))
#'
#' # Move the first axis to the end

r_obj* rray_move_axes(
  r_obj* x,
  r_obj* axes,
  r_obj* to,
  struct rray_arg* arg,
  struct r_lazy error_call
) {
  const int dimensionality = rray_dimensionality(x, arg, error_call);
  check_max_dimensionality(dimensionality);

  axes = KEEP(
    arg_as_axes_unsorted(axes, dimensionality, rray_args.axes, error_call)
  );
  to = KEEP(arg_as_axes_unsorted(to, dimensionality, rray_args.to, error_call));

  const r_ssize axes_size = r_length(axes);
  const r_ssize to_size = r_length(to);

  if (axes_size != to_size) {
    r_abort_lazy_call(
      error_call,
      "`axes` and `to` must be the same length, not lengths %" R_PRIdXLEN_T
      " and %" R_PRIdXLEN_T ".",
      axes_size,
      to_size
    );
  }

  const int* v_axes = r_int_cbegin(axes);
  const int* v_to = r_int_cbegin(to);

  r_obj* permutation = KEEP(r_alloc_integer(dimensionality));
  int* v_permutation = r_int_begin(permutation);

  bool v_moved[RRAY_MAX_DIMENSIONALITY] = {false};
  bool v_filled[RRAY_MAX_DIMENSIONALITY] = {false};

  for (r_ssize i = 0; i < axes_size; ++i) {
    const int axis = v_axes[i];
    const int location = v_to[i];

    v_permutation[location - 1] = axis;
    v_moved[axis - 1] = true;
    v_filled[location - 1] = true;
  }

  int axis = 1;

  for (int i = 0; i < dimensionality; ++i) {
    if (v_filled[i]) {
      continue;
    }

    while (v_moved[axis - 1]) {
      ++axis;
    }

    v_permutation[i] = axis;
    ++axis;
  }

  r_obj* out = KEEP(rray_permute_axes(x, permutation, arg, error_call));

  FREE(4);
  return out;
}

Clarifying axis-to pair normalization

Not in the same way. For rray_move_axes(), the order of the pairs does not matter, but the pairing does:

axes = c(3, 1)
to   = c(1, 2)

means 3 -> 1 and 1 -> 2. Sorting axes alone would silently change the operation.

You could sort the (axes, to) pairs together:

axes = c(1, 3)
to   = c(2, 1)

That preserves the meaning, but gains nothing because the implementation already handles the pairs in any order.

So I would characterize them as:

  • Reduction, split, squeeze: axes is a set. Sort internally.
  • Move: (axes, to) is an unordered set of mappings. Accept any order, but do not sort either vector independently.
  • Permute: axes is a sequence. Preserve its exact order.

The existing unsorted validator is therefore right for move_axes().

Analyzing iterator macro optimizations

No meaningful benefit in the actual workload. The point iterator can be a simple per-element loop that advances v_point like an odometer.

Why:

  • Its only consumer is rray_split_names().
  • Each iteration allocates an R list and populates names, so iterator overhead is tiny relative to the loop body.
  • Unlike the location iterators, this loop cannot be vectorized because every coordinate is observable.

I benchmarked the current row-batched structure against a simple loop carrying from axis 0 on every step. Median timings across three independent runs for 10,000 outputs were effectively identical:

//
// Walks the multidimensional point space. Reports a 1D `location` in an
// alternate subspace.
//
// For broadcasting, the dimensions you broadcast to make up the larger point
// space. This is walked in order. The original dimensions of the array make
// up the subspace. So as you walk the output's point space you can fetch
// `location`s back into your original array to pull from.
//
// For reducing, it's actually a special form of broadcasting. The original
// dimensions of the array are the point space. The reduced dimensions are the
// subspace. So as you walk the original array, you can fetch `location`s into
// the output to accumulate the reduced result at.

  r_ssize index;

// performance reasons. We process a run along the first axis while holding all

    /* unlock vectorization optimizations. */                                  \

    const r_ssize size = iterator->size;                                       \

    const int* v_point_dimensions = iterator->v_point_dimensions;              \
    const int point_dimensionality = iterator->point_dimensionality;           \
    r_ssize LOCATION = iterator->location;                                     \
    const r_ssize* v_location_strides = iterator->v_location_strides;          \

  r_obj* out,

) {

  }

  r_obj* x_dimensions = KEEP(rray_dimensions(x, rray_args.x, r_lazy_null));
  const int* v_x_dimensions = r_int_cbegin(x_dimensions);
  const int x_dimensionality =
    rray_dimensionality_from_dimensions(x_dimensions);

  const int* v_dimensions = r_int_cbegin(dimensions);
  const int dimensionality = rray_dimensionality_from_dimensions(dimensions);

    }

  }

  FREE(3);
  return out;

Yes, iterator2 is not fundamentally necessary as a separate data structure—but its fixed-two-location hot loop is necessary if you want today’s binary performance.

The important distinction is:

  • Generalize iterator setup and traversal planning: good.
  • Make operand count dynamic inside every element’s inner loop: expensive.

What iterator2 currently buys

rray_iterator2 walks the multidimensional point space once while advancing two locations in scalar locals. For rray_add(), those are the locations in x and y; for rray_split(), they are the output-list and output-element locations.

Two independent rray_iterators would each own duplicated point state. Driving both separately would either:

  • walk/carry the point coordinates twice, or
  • require a new “zip these iterators” loop that coordinates their runs.

That zip loop would effectively recreate iterator2. It becomes more problematic if axes are coalesced: each single iterator might choose a different computation shape, whereas coalescing must be approved jointly by every location mapping.

What happens with a literal runtime-N loop

I built a temporary experimental version that changed only the bookkeeping:

  • locations stored in an array;
  • runtime location_count, set to 2;
  • a for (location = 0; location < location_count; ++location) loop advanced locations inside every element;
  • arithmetic and type-specialized kernels were unchanged.

For one-million-element additions:

Case Current fixed-2 Runtime-N bookkeeping Slowdown
Double + double 0.707 ns/elt 2.561 ns/elt 3.6×
Double + scalar 0.725 ns/elt 2.569 ns/elt 3.5×
Integer + integer 1.027 ns/elt 2.549 ns/elt 2.5×
First axis size 1 2.219 ns/elt 7.802 ns/elt 3.5×
Crossed broadcast 0.739 ns/elt 2.608 ns/elt 3.5×

That prototype is deliberately the most literal interpretation of a generic iterator, not the best possible N-operand design. But it demonstrates that the compiler needs to see two explicit locations and two explicit strides in the inner loop. Runtime array iteration prevents the scalarization/vectorization responsible for the current speed.

The design that can support both

I would separate the generic traversal plan from the fixed-arity kernel:

  1. A general iterator owns:

    • one computation shape and carry state;
    • an arbitrary number of operand locations;
    • one stride vector per operand;
    • joint axis coalescing across all operands.

  2. It exposes contiguous/strided runs:

    • run length;
    • starting location for every operand;
    • inner stride for every operand.

  3. Fixed-arity kernels consume those runs:

    • binary kernel aliases locations 0 and 1 into scalar locals;
    • ternary kernels can specialize locations 0–2;
    • arbitrary-N kernels use a runtime operand loop.

This could eliminate struct rray_iterator2 as a storage abstraction, but the binary specialization would still exist somewhere. It might be a case 2 selected once before iteration, not a condition inside the element loop.

This is essentially what mature tensor libraries do:

  • NumPy’s general iterator handles multiple operands and exposes per-operand inner strides, but individual ufuncs still have a fixed input count such as np.add.nin == 2. NumPy iterator design, ufunc documentation
  • PyTorch’s TensorIterator stores a runtime operand collection, but cpu_kernel() derives operand arity at compile time from the kernel lambda and checks it against the iterator’s runtime input count. Its operand dereferences are expanded at compile time. TensorIterator, CPU loops

Generalizing rray_add()

rray_add(x, y, ...) can support arbitrary inputs without sacrificing the two-input path:

  • When ... is empty, call the existing binary implementation unchanged.
  • With additional inputs, use an N-ary implementation.

That preserves the exact current C loop and type-pair specialization in RRAY_ARITHMETIC. It also avoids constructing a dots list on the common binary path.

Much of the N-ary setup already exists:

  • rray_dimensions_common()
  • rray_ptype_common()
  • rray_broadcast_names_common()

The other significant complication is type dispatch. Binary arithmetic currently has fully specialized input-type pairs and performs conversions inline without allocating cast inputs. Arbitrary mixed-type inputs would otherwise require runtime type dispatch per operand or up-front casting. That is another reason to preserve the binary fast path.

My recommendation: keep iterator2 for now. If several genuine N-operand operations appear, introduce one generic N-location traversal plan, but retain specialized binary—and perhaps ternary—inner kernels. A generalized public rray_add(x, y, ...) can route two arguments directly to today’s implementation, preserving essentially all current performance. The worktree remains unchanged.

Analyzing accumulator approach trade-offs and optimization ideas

Yes—this is a much more viable generalization. An input-at-a-time accumulator avoids the runtime-N inner loop entirely, because every pass is still a simple, optimizable one-location iterator.

It would be somewhat slower for ordinary binary addition, but not drastically slower.

I prototyped the best form:

  1. Copy/cast x into the output.
  2. Iterate over y and add it into the output.
  3. Repeat for later inputs.

For one million elements:

Case Current fused binary Accumulator Difference
Double + double ~0.72 ns/elt ~0.87 ns/elt ~20% slower
Double + scalar ~0.74 ns/elt ~1.00 ns/elt ~35% slower
Integer + integer ~1.03 ns/elt ~1.19 ns/elt ~16% slower
Crossed broadcast ~0.73 ns/elt ~0.92 ns/elt ~26% slower
Shape [1, 1e6] ~2.20 ns/elt ~0.88 ns/elt accumulator 2.5× faster

Small-array performance was effectively unchanged until around 1,000 elements.

The [1, 1e6] result is interesting: separating the operands gives the compiler two very simple loops, avoiding the current dual-location iterator’s short-row weakness. Axis coalescing would presumably reduce that advantage.

Why it costs 15–35%

The fused binary loop conceptually transfers three vectors:

read x + read y + write output

The accumulator transfers five:

read x + write output
read y + read output + write output

For doubles that is theoretically 24 versus 40 bytes per element. In practice the output often remains cached between passes, so the measured penalty is considerably smaller than the 1.67× traffic ratio. Very large arrays that exceed cache could get closer to that bound.

Don’t actually initialize with zero

The best implementation should seed the output from the first input, not fill it with zero and then add x.

Zero initialization has two problems:

  • Integer addition performs an unnecessary checked 0 + x; my literal zero-initialized prototype made integer addition nearly twice as slow.
  • Floating-point semantics can change. Current binary addition gives:
-0 + -0
# -0

Starting from positive zero produces positive zero instead. The prototype confirmed this difference.

Copying/casting the first operand into the output avoids both problems. Subsequent operands can then accumulate left-to-right, preserving the expected rounding and overflow order.

This is attractive for arbitrary N

For N inputs, the structure becomes very clean:

output <- cast/broadcast first input

for each remaining input:
    iterate that input against the common output shape
    output[i] += input[location]

Benefits:

  • Every input gets its own optimized rray_iterator.
  • No synchronized iterator state is required.
  • No runtime operand loop occurs inside each element.
  • Each input’s type can be dispatched once for its entire pass.
  • Broadcasting remains lazy and requires no materialized intermediate.
  • There is no combinatorial explosion of N-input type combinations.
  • Common dimensions, types, and names already have supporting infrastructure.

The cost is another complete output read/write pass per additional input. That may nevertheless be faster than an element-major generic-N kernel because every pass is predictable, contiguous, and vectorizable.

What this means for iterator2

For rray_add(), this design could remove the need for iterator2 entirely if a roughly 20% binary throughput cost is acceptable.

It does not eliminate every use of iterator2. rray_split() genuinely needs two coordinated locations for each input element: which output array and which position inside that array. There is no analogous accumulator decomposition there.

My preferred design would be:

  • Generalize rray_add(x, y, ...) using first-input seeding plus one single-iterator pass per later input.
  • Keep the existing fused binary path when ... is empty if maximum two-input throughput matters.
  • Otherwise, accepting the modest binary regression gives a remarkably simple unified implementation.
  • Retain iterator2 for operations such as split that intrinsically require two simultaneous mappings.

So: yes, the accumulator approach is credible and substantially better than a runtime-N iterator. It trades roughly 15–35% of ordinary binary throughput for a much simpler arbitrary-N model, while potentially winning on awkward iteration shapes. No repository files were changed.

+
+## Status
+
+This document is an implementation plan. It does not describe code that is
+already present.
+
+The plan branch is based on `main`, at the iterator-performance merge. A future
+implementation should first incorporate the adjacent-axis coalescing work if it
+has landed separately. The design below benefits from that work but does not
+depend on it for correctness.

+## Goal
+
+Extend `rray_add()` from a binary operation to an operation that accepts two or
+more arrays:
+
+```r
+rray_add(x, y, ...)
+```
+
+Keep the existing binary path unchanged when `...` is empty. For three or more
+inputs, allocate one result, seed it from the first input, and accumulate each
+remaining input into it in a separate pass. Every pass uses its own optimized
+`rray_iterator`.
+
+The goals are:
+
+- preserve the current two-input throughput and small-call overhead;
+- support an arbitrary number of broadcastable inputs;
+- avoid a runtime operand loop inside the innermost element loop;
+- avoid materialized broadcast inputs and full-size cast intermediates;
+- allocate only the final output vector, apart from small setup objects;
+- preserve deterministic left-to-right floating-point and integer arithmetic;
+- reuse the existing common-dimension, common-type, and common-name machinery;

+exponentiation have less natural N-ary APIs. Multiplication could adopt the
+same architecture later, but should not be included merely to make the first
+implementation more generic.
+
+## Summary of the design
+
+The public wrapper keeps `x` and `y` as required arguments and adds `...`:
+
+```r
+rray_add <- function(x, y, ...) {
+  if (nargs() == 2L) {
+    return(.Call(ffi_rray_add, x, y, environment()))
+  }
+
+  .Call(ffi_rray_add_n, list2(x, y, ...), environment())
+}
+```
+
+The exact wrapper may need adjustment for project style and missing-argument
+behavior, but the important property is that the binary call does not build a
+list and reaches the existing native entry point unchanged.
+
+The N-ary native path performs these phases:
+
+1. Normalize and validate every input as an unclassed array.
+2. Determine the final arithmetic output type across all inputs.
+3. Determine the common broadcast dimensions across all inputs.
+4. Allocate one output vector of the final type.
+5. Copy and cast the first input into the output through one `rray_iterator`.
+6. For each later input, add and cast it into the output through a fresh
+   `rray_iterator`.
+7. Attach the common dimensions and coalesced names.
+
+In pseudocode:
+
+```text
+xs = normalize(x, y, ...)
+output_type = add_common_type(xs)
+dimensions = dimensions_common(xs)
+out = allocate(output_type, size(dimensions))
+
+copy_cast_pass(out, xs[0], dimensions)
+
+for input in xs[1:]:
+    add_cast_pass(out, input, dimensions)
+
+set dimensions(out)
+set names(out, broadcast_names_common(xs, dimensions))
+```
+
+Every pass writes the output with the flat iterator index and uses the mapped
+location only to read its input. Because passes are independent, they do not
+need synchronized point state or an N-location iterator.
+
+## Why not a runtime-N iterator inner loop
+
+A natural alternative is one iterator containing a runtime-sized array of
+locations and strides:
+
+```text
+for each output element:
+    combine values at locations[0:n]
+    for location in locations[0:n]:
+        advance location
+```
+
+That representation is logically general, but the dynamic location loop sits
+inside the hottest loop. It prevents the compiler from seeing two scalar
+locations and two fixed strides in the binary case.
+
+A temporary experiment replaced the two scalar location fields with a runtime
+location collection while leaving the arithmetic operation and type-specific
+cores unchanged. The runtime location count was still exactly two. On an Apple
+M2 Pro with R 4.6.0 alpha, Apple Clang 17, normal package flags including
+`-O2`, and one million output elements, it produced these medians:
+
+| Case | Fixed two locations | Runtime location collection | Slowdown |
+|---|---:|---:|---:|
+| Double identity shapes | 0.707 ns/element | 2.561 ns/element | 3.62 times |
+| Double plus scalar | 0.725 ns/element | 2.569 ns/element | 3.54 times |
+| Integer identity shapes | 1.027 ns/element | 2.549 ns/element | 2.48 times |
+| First axis size one | 2.219 ns/element | 7.802 ns/element | 3.52 times |
+| Crossed broadcast | 0.739 ns/element | 2.608 ns/element | 3.53 times |
+
+This does not prove that every N-location iterator design must be slow. A
+generic traversal plan that exposes runs to fixed-arity inner kernels can be
+fast. It does show that a literal runtime operand loop must not replace the
+current fixed-arity inner loop.
+
+The accumulator design avoids that problem. Each pass has one location, one
+fixed row stride, and one typed operation.
+
+## Why not run two ordinary iterators in lockstep
+
+Two `rray_iterator` instances cannot simply be nested or independently stepped
+inside the current iterator macros. Each instance owns a complete traversal of
+the point space. Coordinating them element by element would duplicate carry
+work or require a new zip loop, which recreates the role of `rray_iterator2`.
+
+It also complicates coalescing. Two independently initialized iterators can
+choose different private computation shapes because coalescing depends on the
+location mapping. A genuinely fused N-operand iterator must choose a shape
+approved by every operand.
+
+The accumulator avoids synchronization entirely. It completes one input pass
+before starting the next, so each single-location iterator can use the best
+private computation shape for that input alone.
+
+## Do not initialize the result by adding to zero
+
+The conceptual description may sound like this:
+
+```text
+fill output with zero
+output += x
+output += y
+output += z
+```
+
+Do not implement it literally. Instead use:
+
+```text
+output = cast(x)
+output += y
+output += z
+```
+
+Seeding from the first input is important for both performance and semantics.
+
+### Performance
+
+A zero fill adds a complete output write. Adding the first input then requires
+another output read and write. For integer addition it also performs an
+unnecessary checked addition for `0 + x`.
+
+In a temporary prototype, the seeded integer accumulator took about 1.19
+nanoseconds per element for two identity-shaped integer inputs. The literal
+zero accumulator took about 1.94 nanoseconds per element, versus about 1.03 for
+the fused binary implementation.
+
+### Signed zero
+
+IEEE floating-point addition distinguishes positive and negative zero. The
+existing binary implementation preserves the result of the actual binary
+operation:
+
+```r
+rray_add(array(-0, 1L), array(-0, 1L))
+# negative zero
+```
+
+Starting the accumulator from positive zero changes that result to positive
+zero. Copying the first input and then adding the second preserves the binary
+operation. The same caution applies to complex signed-zero components and may
+also matter for NaN payload behavior.

It is an acceptable minimal prototype, not the desired implementation.

### Precast and prebroadcast every input

Casting and broadcasting every input to the final type and dimensions makes the
final arithmetic loop simple, but allocates `N` full-size intermediates and
does more copying than the accumulator. It discards a central benefit of the
iterator design and should not be used.

### One dynamic element-major fused loop

This writes the output once and minimizes theoretical memory traffic, but needs
runtime pointer, type, and stride selection for every input at every output
element. The location-only prototype showed a severe binary regression before
adding dynamic type handling. Do not use it for the common binary path.

### Generic traversal plan with fixed-arity run kernels

A more sophisticated future iterator could own arbitrary operands, coalesce
them jointly, and expose inner runs to fixed-arity kernels. This is compatible
with high binary performance but is a larger architectural project. It is not
needed for N-ary addition when independent accumulator passes are acceptable.

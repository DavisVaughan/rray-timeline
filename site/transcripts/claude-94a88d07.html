28	// space. This is walked in order. The original dimensions of the array make

rray_broadcast_iterator_plan() is the wrong arity. It returns a rray_strided_iterator_plan, which carries one stride set. Combine walks two spaces in one pass: read from x, write into out. That needs rray_strided_iterator2_plan.

  • But we write into the whole output array, so v_out_strides comes from the full v_out_dimensions via rray_fill_strides_from_dimensions() (src/combine.c:130), and each input starts at out_start = axis_offset * v_out_strides[axis - 1] (src/combine.c:169).

Claude

Think of the output as a big empty egg carton, and each input as a small tray of eggs you're going to place into one section of it.

Two different things happen at the same time for each input:

Reading from the input is stretching. If the tray only has one row but the carton section needs four identical rows, you copy that same row four times. The broadcast helper exists for exactly this: it works out "step forward" or "stay put and reuse this value".

Writing into the output is not stretching. You're not blowing a small thing up into a big thing. You're placing a normal-sized tray into a slot partway along a bigger carton. The steps there come from how big the whole carton is, plus an offset for which slot this tray goes in.

rray_broadcast_iterator_plan() and rray_broadcast_iterator2_plan() assume everything they touch is a stretch. The writing side isn't, so they don't fit. In fact the write goes the wrong way for them: the carton is bigger than the tray along the glue axis, and stretching only ever goes small to big.

So combine takes the one piece of the broadcast helper that does apply, the "stretch steps" calculator for the input, computes the carton's own steps itself, and hands both to the two-space walker.

It's not a speed trick. Both paths produce the same plan and the same optimizations.

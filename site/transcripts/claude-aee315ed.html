Promotion: yes, prod promotes and multiply doesn't. rray_prod() on logical or integer input adds up into a double, so the result is double (base R's prod() does the same). rray_multiply(2L, 3L) stays integer and errors on overflow. That integer path never involves floating point NA, so nothing in it is implementation defined.

Where prod's NA handling lives:

  • When x is NA, rray_prod_int_one() checks for it and returns NA_real_. That case is fully defined.
  • Once out is NA_real_, each later step is out * x, which is the same double multiply rray_multiply(NA_integer_, 1.5) runs after casting the NA to a double.

Why it's well defined for integer input: the "implementation defined" case only comes up when both sides of * are NaN-like. The chip then has to pick one, and NA and NaN are two different NaN values. With logical or integer input, x is never NaN by the time it reaches *, because NA is caught first. So only out can be NaN-like, and a single one passes through unchanged. Checking R_IsNA(out) would only matter when both sides are NaN, which needs double input. That's why dropping it is safe here, and why only the double c(NA, NaN) tests had to be loosened.

static bool cprod(SEXP sx, Rcomplex *value, bool narm)
{
    Rcomplex *x = COMPLEX(sx);
    R_xlen_t n = XLENGTH(sx);
    LDOUBLE sr = 1.0, si = 0.0;
    bool updated = false;
    for (R_xlen_t k = 0; k < n; k++) {
	if (!narm || (!ISNAN(x[k].r) && !ISNAN(x[k].i))) {
	    if(!updated) updated = true;
	    LDOUBLE tr = sr, ti = si;
	    sr = tr * x[k].r - ti * x[k].i;
	    si = tr * x[k].i + ti * x[k].r;
	}
    }
    value->r = (double) sr;
    value->i = (double) si;

    return updated;
}

I checked R's sources. The short answers:

  1. Support for the difference: there is none beyond "base R does it this way". R's prod() and * disagree with each other for complex numbers, and I found no stated reason in the R docs, ?prod or NEWS.
  2. Should prod use multiply's version: I think yes, for consistency. It is the same call you made for doubles, where we matched rray_multiply() over prod().

What base R does. The two operations run different code:

  • * uses C's built-in complex multiply (src/main/complex.c:208):

    toC99(&ps1[i1]) * toC99(&ps2[i2])

    The C standard tells that multiply to recover infinities. If the plain formula would give NaN, it returns an infinite result where one makes sense.

  • prod() writes the formula out by hand, using extra-precision long double (cprod(), src/main/summary.c:388):

    sr = tr * x[k].r - ti * x[k].i;
si = tr * x[k].i + ti * x[k].r;

    This does no infinity recovery. It looks like it was written by hand to get the extra precision, not to avoid the recovery.

So base R itself gives different answers:

y <- c(complex(real = Inf, imaginary = Inf), 2 + 0i)
y[1] * y[2]   # Inf+Infi
prod(y)       # NaN+NaNi

rray_prod() currently copies prod() and rray_multiply() copies *, so rray has the same split.

Why I'd switch. For doubles, we already decided rray should agree with itself where base R doesn't. Making rray_prod_cpl_one() return rray_multiply_cpl_one(out, x) applies the same rule, and it would match how rray_sum_cpl_one() calls rray_add_cpl_one(). The recovered answer (Inf+Infi above) is also arguably the better one.

What it would cost:

  • Speed. The built-in complex multiply checks for infinities on every element. Compilers usually do that through a helper function call, which is slower and stops the loop from being vectorized. I haven't benchmarked it, so this is likely, not measured.
  • Tests. Three tests in test-reduce-prod.R would change: "complex infinities are not recovered", the Inf + 0i with NA test that compares against prod(), and maybe the zero times Inf test. They would compare against * instead of prod().
  • Comments. The comments on both helpers, which explain the difference, would be removed or rewritten. You wrote those, so I'd want your go-ahead first.

Want me to benchmark the two versions before you decide, or go ahead and switch?

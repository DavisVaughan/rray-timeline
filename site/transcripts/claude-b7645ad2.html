1	# Macro-free strided iteration
2	
3	## Status
4	
5	The macro-free strided iteration design is implemented on this branch.
6	`RRAY_STRIDED_ITERATOR_FOR_EACH()` and
7	`RRAY_STRIDED_ITERATOR2_FOR_EACH()` have been removed, and every caller now
8	uses explicit run-based loops.
9	
10	The implementation has two parts:
11	
12	- A plan holds the dimensions and strides that stay fixed for one traversal.
13	- An iterator holds only the state that changes while walking the plan.
14	
15	The iterator does not store a pointer to its plan. The few operations that need
16	plan data receive the plan as an argument. This keeps the type honest and had
17	no measurable performance cost.
18	
19	All 1,512 package tests pass.
20	
21	Type-generation macros still exist in arithmetic and similar code. Those are
22	separate from strided iteration. They generate specialized typed workers and
23	avoid runtime type dispatch in hot loops.
24	
25	## Result
26	
27	The main conclusion is that the plan and iterator should remain separate.
28	
29	This is not mainly about `const`, whether construction happens in place, or
30	whether the full struct fits in cache. The important property is that the
31	changing traversal state is a small, local object that Clang can break into
32	independent values and keep in registers.
33	
34	Combining the fixed plan data and changing iterator data into one struct made
35	carry-heavy broadcasts 15% to 19% slower. Moving construction into the typed
36	worker did not help. Reducing the maximum dimensionality from 64 to 8 made the
37	struct much smaller but did not help either.
38	
39	The current two-stage design keeps the large arrays in the plan and the
40	changing run, locations, and point in the iterator.
41	
42	## Requirements
43	
44	A macro-free replacement still has to preserve the optimizations that were
45	inside the old macros:
46	
47	- Coalesce compatible axes before traversal.
48	- Process the coalesced first axis as one run.
49	- Perform point carry work between runs, not for every element.
50	- Keep zero first-axis strides visible as separate fixed paths.
51	- Keep operation, type, and missing-value dispatch outside inner loops.
52	- Support one and two mapped location spaces.
53	- Keep mutable traversal state local to the typed worker.
54	- Stay within normal benchmark noise for the macro implementation.
55	
56	The public shape of the loop matters as much as the iterator functions. A
57	generic iterator API can still be slow if it hides these facts from the
58	compiler.
59	
60	## Current design
61	
62	The one-location plan contains fixed traversal data:
63	
64	```c
65	struct rray_strided_iterator_plan {
66	  r_ssize size;
67	  r_ssize v_dimensions[RRAY_MAX_DIMENSIONALITY];
68	  int dimensionality;
69	  r_ssize v_strides[RRAY_MAX_DIMENSIONALITY];
70	};
71	```
72	
73	The one-location iterator contains only changing state:
74	
75	```c
76	struct rray_strided_iterator {
77	  r_ssize run_start;
78	  r_ssize location;
79	  r_ssize v_point[RRAY_MAX_DIMENSIONALITY];
80	};
81	```
82	
83	The two-location forms follow the same split:
84	
85	```c
86	struct rray_strided_iterator2_plan {
87	  r_ssize size;
88	  r_ssize v_dimensions[RRAY_MAX_DIMENSIONALITY];
89	  int dimensionality;
90	  r_ssize v_strides1[RRAY_MAX_DIMENSIONALITY];
91	  r_ssize v_strides2[RRAY_MAX_DIMENSIONALITY];
92	};
93	
94	struct rray_strided_iterator2 {
95	  r_ssize run_start;
96	  r_ssize location1;
97	  r_ssize location2;
98	  r_ssize v_point[RRAY_MAX_DIMENSIONALITY];
99	};
100	```
101	
102	Plan constructors validate dimensions, compute strides, and coalesce axes.
103	Iterator constructors only initialize changing state:
104	
105	```c
106	struct rray_strided_iterator_plan rray_strided_iterator_plan(...);
107	struct rray_strided_iterator_plan rray_broadcast_iterator_plan(...);
108	struct rray_strided_iterator rray_strided_iterator(void);
109	
110	struct rray_strided_iterator2_plan rray_strided_iterator2_plan(...);
111	struct rray_strided_iterator2_plan rray_broadcast_iterator2_plan(...);
112	struct rray_strided_iterator2 rray_strided_iterator2(void);
113	```
114	
115	Run size and first-axis strides come from the plan. Run start and locations
116	come from the iterator. Only `finished()` and `next()` need both:
117	
118	```c
119	bool rray_strided_iterator_finished(
120	  const struct rray_strided_iterator* it,
121	  const struct rray_strided_iterator_plan* plan
122	);
123	
124	void rray_strided_iterator_next(
125	  struct rray_strided_iterator* it,
126	  const struct rray_strided_iterator_plan* plan
127	);
128	```
129	
130	The `iterator2` functions have the same shape.
131	
132	Passing the plan directly to these inline functions is free in the generated
133	hot loops. The worker already has the plan available, usually in a register.
134	Removing the plan field made the one-location iterator 528 bytes instead of
135	536 and the two-location iterator 536 bytes instead of 544. More importantly,
136	the iterator now represents only mutable state.
137	
138	## Run-based traversal
139	
140	The iterator advances one first-axis run at a time, not one element at a time.
141	
142	After coalescing, `plan->v_dimensions[0]` is the run size. The caller walks
143	that whole run with a small inner loop. `next()` then increments the later
144	point coordinates and updates the mapped locations for the next run.
145	
146	A one-location caller has this shape:
147	
148	```c
149	const r_ssize run_size =
150	  rray_strided_iterator_plan_run_size(plan);
151	const r_ssize run_stride =
152	  rray_strided_iterator_plan_run_stride(plan);
153	
154	for (struct rray_strided_iterator it = rray_strided_iterator();
155	     !rray_strided_iterator_finished(&it, plan);
156	     rray_strided_iterator_next(&it, plan)) {
157	  const r_ssize run_start = rray_strided_iterator_run_start(&it);
158	  const r_ssize run_end = run_start + run_size;
159	  r_ssize location = rray_strided_iterator_location(&it);
160	
161	  if (run_stride == 0) {
162	    const double elt = v_x[location];
163	
164	    for (r_ssize i = run_start; i < run_end; ++i) {
165	      v_out[i] = elt;
166	    }
167	  } else {
168	    for (r_ssize i = run_start; i < run_end; ++i) {
169	      v_out[i] = v_x[location];
170	      location += run_stride;
171	    }
172	  }
173	}
174	```
175	
176	The iterator location always means the beginning of the current run. The
177	caller increments a local copy while processing elements. `next()` must not
178	undo those local increments because the iterator location never made them.
179	
180	There is no separate terminal adjustment. On the last call, `next()`
181	increments `run_start` to `plan->size` and completes the normal point carry.
182	The next `finished()` check ends the loop.
183	
184	An element-at-a-time `next()` would test for a run boundary and possibly carry
185	later axes for every element. Earlier work found that batching first-axis runs
186	can improve these operations by 3 to 4 times. The run boundary must stay
187	outside the element loop.
188	
189	## `rray_mean_along()` plan
190	
191	The macro-free API also makes a better `rray_mean_along()` traversal possible.
192	The current reduction traversal walks `x` in physical order and maps each
193	element to an output location. That works well for sums and products, but a
194	mean needs more numerical state and may need several passes over each reduced
195	slice.
196	
197	R accumulates real means in `LDOUBLE`. It can use a scaled sum if the first sum
198	overflows, then makes a correction pass to reduce rounding error. Removing
199	missing values also requires a count for each slice. Complex means need
200	separate real and imaginary accumulators.

10	// Strided iterator plan
11	//
12	// Optimizes and assists in walking a multidimensional point space defined by
13	// `v_dimensions`. As it walks, it updates a user provided `start` in an
14	// alternate subspace defined by `v_strides`.
15	//
16	// For performance and flexibility, the user is responsible for managing the run
17	// loop along the first axis. We've tried many alternative approaches but they
18	// tend to tank performance quickly as you increase the level of abstractions.
19	//
20	// The plan holds only immutable state. The positions that change as it walks
21	// are managed by the caller. This lets the compiler keep these positions in
22	// registers, which has significant performance implications.
23	//
24	// --------------------------------------------------------------------------
25	// Examples
26	//
27	// For broadcasting, the dimensions you broadcast to make up the larger point
28	// space. This is walked in order. The original dimensions of the array make
29	// up the subspace. So as you walk the output's point space you can create
30	// `location`s back into your original array to pull from.
31	//
32	// For reducing, it's actually a special form of broadcasting. The original
33	// dimensions of the array are the point space. The reduced dimensions are the
34	// subspace. So as you walk the original array, you can create `location`s into
35	// the output to accumulate the reduced result at.
36	//
37	// For permuting axes, the permuted dimensions make up the point space. The
38	// original dimensions of the array make up the subspace. So as you walk the
39	// output's point space you can create `location`s back into your original
40	// array to pull from.
41	//
42	// --------------------------------------------------------------------------
43	// Optimization - First axis runs
44	//
45	// After coalescing, the iterator walks the entire first axis in one inner run
46	// while holding all later axes fixed. It only updates the later point
47	// coordinates between runs, rather than checking and carrying them after every
48	// element. This gives the compiler a small loop where the index and locations
49	// advance by fixed strides, making it much easier to optimize and vectorize.
50	//
51	// Practical examples of when this is useful:
52	//
53	// - Identically shaped binary array operations. Adding two [2, 4, 5] arrays
54	//   coalesces to dimensions [40], so the entire operation is one first axis run
55	//   where both input locations advance contiguously.
56	//
57	// - Broadcasting over a later axis. Broadcasting a [2, 3] array to [2, 3, 4]
58	//   coalesces to dimensions [6, 4] with location strides [1, 0]. The iterator
59	//   performs four first axis runs of size 6, copying six contiguous values
60	//   before updating the later axis.
61	//
62	// - Reducing over a later axis. Reducing a [2, 3, 4] array over its third axis
63	//   also coalesces to dimensions [6, 4] with output strides [1, 0]. Each first
64	//   axis run accumulates one contiguous slice into six output locations before
65	//   advancing along the reduced axis.
66	//
67	// --------------------------------------------------------------------------
68	// Optimization - Coalescing
69	//
70	// Coalescing axes is an important optimization used to reduce the number of
71	// axes we have to iterate over by "merging" adjacent compatible ones. This can
72	// improve performance by 3-5x on its own in some cases.
73	//
74	// Practical examples of when this is useful:
75	//
76	// - Identically shaped binary array operations. Adding two arrays with
77	//   dimensions [2, 4, 5] gives both inputs strides [1, 2, 8]. All adjacent axes
78	//   coalesce (2 * 1 = 2, 4 * 2 = 8) into one dimension [40] with stride [1],
79	//   resulting in one flat vectorizable loop.
80	//
81	// - Scalar broadcasting across an entire array. Adding a scalar to a [2, 4, 5]
82	//   array gives the array strides [1, 2, 8] and the scalar strides [0, 0, 0].
83	//   Both coalesce completely, producing a [40] loop with array stride [1] and
84	//   scalar stride [0].
85	//
86	// - Contiguous adjacent axes within a broadcast operation. Broadcasting a
87	//   [2, 3] array over point dimensions [2, 3, 4] produces location strides
88	//   [1, 2, 0]. The adjacent axes 1 and 2 coalesce (2 * 1 = 2) into size 6,
89	//   leaving dimensions [6, 4] and strides [1, 0].
90	//
91	// - Contiguous regions within a reduction. Reducing a [2, 3, 4] array over its
92	//   third axis maps into a [2, 3] result using location strides [1, 2, 0].
93	//   Coalescing produces dimensions [6, 4], making it the same as the broadcast
94	//   example above.
95	//
96	// - Point-space dimensions of size 1. Output point dimensions of [1, 3, 4] can
97	//   have strides [0, 1, 3]. The dimension 1 first axis is absorbed into the
98	//   dimension 3 second axis, adopting stride 1, after which the dimension 4
99	//   third axis also coalesces. The result is one dimension [12] with stride
100	//   [1]. Note that this isn't broadcasting. This is when both input and output
101	//   have an axis that stays dimension 1, which is somewhat rare.
102	//
103	// For iterator2, note that both sets of location strides must be coalescible,
104	// as coalescing changes the output dimensionality, so it's all or nothing.
105	//
106	// --------------------------------------------------------------------------
107	// Optimization - Fixed zero stride paths
108	//
109	// After coalescing, the first axis is walked by the inner loop. A stride of 0
110	// on this axis means that a subspace location stays fixed while the point space
111	// moves along it. Broadcasting uses this to reuse an input value. Reducing uses
112	// it to accumulate into the same output location. A zero stride on a later axis
113	// does not use this path because later axes advance between inner runs.
114	//
115	// When the inner loop receives the stride as a runtime value, the compiler
116	// can't prove that the location is fixed and falls back to a scalar loop. The
117	// public iteration macros check for a zero stride and pass a literal 0 to a
118	// specialized path. This lets the compiler see that the location does not
119	// change. For binary operations, it can then hoist the fixed load out of the
120	// loop and vectorize the remaining stride 1 work.
121	//
122	// Practical examples of when this is useful:
123	//
124	// - Scalar broadcasting across an entire array. Adding a scalar to a [2, 4, 5]
125	//   array coalesces to point dimensions [40], with array strides [1] and scalar
126	//   strides [0]. The scalar location stays fixed while the array and output
127	//   advance contiguously. The same path is used by arithmetic, comparison,
128	//   equality, and extrema operations.
129	//
130	// - Row broadcasting within a matrix. Adding a [1, 4] row to a [2, 4] array

r_obj* arg_as_axes(
  r_obj* axes,
  int dimensionality,
  struct rray_arg* arg,
  struct r_lazy error_call
) {
  if (r_typeof(axes) != R_TYPE_integer) {
    axes = vec_cast(axes, r_globals.empty_int, arg, NULL);
  }
  KEEP(axes);

  if (r_attrib_has_any(axes)) {
    r_abort_lazy_call(
      error_call,
      "%s can't have attributes.",
      rray_arg_format(arg)
    );
  }

  const r_ssize axes_size = r_length(axes);

  const int* v_axes = r_int_cbegin(axes);

  for (r_ssize i = 0; i < axes_size; ++i) {
    const int axis = v_axes[i];

    if (axis == r_globals.na_int) {
      r_abort_lazy_call(
        error_call,
        "%s must not contain missing values.",
        rray_arg_format(arg)
      );
    }

    if (axis < 1) {
      r_abort_lazy_call(
        error_call,
        "%s must contain values greater than or equal to 1, not %d.",
        rray_arg_format(arg),
        axis
      );
    }

    if (axis > dimensionality) {
      r_abort_lazy_call(
        error_call,
        "%s must contain values less than or equal to the "
        "dimensionality of %d, not %d.",
        rray_arg_format(arg),
        dimensionality,
        axis
      );
    }

    if (i > 0 && axis <= v_axes[i - 1]) {
      r_abort_lazy_call(
        error_call,
        "%s must be in strictly increasing order.",
        rray_arg_format(arg)
      );
    }
  }

  FREE(1);
  return axes;
}

What was built

rray_reduce_grouped() in src/reduce.c — a second reduce shell beside rray_reduce(). It builds two immutable plans from x's physical strides: an outer plan over the retained axes (its run start is the flat output location, since reduced axes have dimension 1 in the output) and an inner plan over the reduced axes (offsets from the base the outer plan reports). Nothing is copied or permuted. The inner plan is restartable, which is what lets mean make several passes over one slice.

Empty axis sets become a plan with one axis of dimension 1 and stride 0. That's needed because the coalescing pass returns a dimensionality of 1 with uninitialized dimensions when handed 0 axes.

src/reduce-mean.c — two file-local macros, #undef'd at the bottom like split.c does:

  • RRAY_REDUCE_GROUPED(X_CTYPE, X_CONST_DEREF, OUT_RTYPE, OUT_CTYPE, OUT_DEREF, ONE) is the outer walk. Same shape and parameter order as RRAY_BINARY, except ONE takes a whole slice (v_x, x_base, inner_plan) instead of two elements.
  • RRAY_REDUCE_SLICE(X_CTYPE, ACCUMULATE) is one pass over the current slice, exposing x_elt. A core calls it once per pass, so the carried state is just local scalars.

That's the piece to lift into reduce.h when variance or cumulative sum arrives; it isn't mean-specific. I left it in reduce-mean.c as you asked.

Neither loop has a zero-stride path. The inner first-axis stride is a physical stride of x, which can only be 0 when a preceding dimension is 0, and in every such case the loop in question has size 0. I convinced myself of that by cases rather than adding a dead branch.

Matching R

The double core is a direct port of real_mean(): sum in long double, divide, then a correction pass of t += x - s. A non-finite first sum retries with x / n before correcting. n is an r_ssize, not a long double, so x_elt / n is a double division exactly as R writes it. na_rm = TRUE mirrors mean.default() dropping NA and NaN first, so the count excludes them. Logical and integer take R's simpler path with no correction pass.

Verified bit-for-bit against apply(x, kept, mean) for every axis combination of a 4D array, with and without na_rm, plus c(1e16, 1, 1, 1) where the correction changes the answer (2500000000000001, not 2500000000000000) and c(1e308, 1e308, 1e308) where the first sum overflows.

The one deliberate difference, as you chose: when the first sum is NaN we scan the slice once and return NA if any NA is present. mean(c(NaN, NA)) is NaN in R and NA here.

Three things fall out.

na_rm = FALSE is at parity or better. Both directions, including the strided one. This is the comparison that means something, since matrixStats pays for the same two passes. It also settles the earlier question: our grouped traversal is not costing us anything against a mature single-purpose implementation.

na_rm = TRUE is 1.6x slower, and that's our bug, not theirs. Look at the none rows: matrixStats costs 1.679 → 1.688 ms going from na_rm = FALSE to TRUE, essentially free. We go 1.58 → 2.76 ms, a 75% penalty for a flag that removes nothing, because there are no missing values in that input. The cause is almost certainly the if (!ISNAN(x_elt)) branch in every pass of the na_rm cores blocking vectorization of the accumulate. A branchless form would be arithmetically identical:

const bool ok = !ISNAN(x_elt);
s += ok ? x_elt : 0;
n += ok;

I have not tried it, so that's a hypothesis with a plausible mechanism, not a result. Want me to measure it? It's a contained change to the three na_rm cores and I'd re-verify bit-for-bit against mean() afterwards.

The dense, na_rm = FALSE column case is a deliberate trade, not a defect. dense makes every other element NA, so every column answer is NA. matrixStats bails out of a column on the first NA and finishes in 7 µs. We run the full sum pass, get NaN, then bail on the first NA of the scan. But their early exit costs them a per-element branch, which is why they are 6% slower than us on the none case. Paying 6% on ordinary data to win on all-NA data is the wrong trade for us, so I'd leave it.

Don’t change anything yet, but is it simply impossible for mean int one to overflow to infinity? So we don’t need to check all that?

Claude

Correct, it's impossible, by a margin so large it isn't close.

The bound is n * INT_MAX. Even at R's absolute ceiling for a vector length, R_XLEN_T_MAX = 2^52 ≈ 4.5e15, the largest magnitude the sum can reach is 2^52 × 2^31 = 2^83 ≈ 9.7e24. DBL_MAX is 1.8e308. That's 283 orders of magnitude of headroom, and you'd need roughly 8e298 elements to close it. For logical it's even more trivial, since the values are 0 and 1, so |s| <= n.

So the int and logical cores already have no R_FINITE() check and no scaled retry, and nothing needs removing. That's also exactly why R's integer_mean() and logical_mean() are five lines each while real_mean() has the three-pass structure: matching R and being safe happen to coincide here.

The failure mode that does exist for int is different, and it's precision, not overflow. On Apple silicon long double is double, so once the running sum passes 2^53 ≈ 9.0e15 it starts rounding, which is reachable at about 4.2 million elements of INT_MAX. R has the identical exposure on the same platform and takes no correction pass for integers, so we still agree with mean() bit-for-bit. On x86 both get the 80-bit accumulator and both are more precise. Nothing to do either way unless you ever want to diverge from R there.

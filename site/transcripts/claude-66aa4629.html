Numbers

1000x1000 integer array, rray_mean_along(x, 1L, na_rm = FALSE), median of 50:

no NAs 0.814 ms 0.758 ms
NA every 101st 0.034 ms 0.758 ms

Branchless buys 7% when there are no NAs and loses 22x when there are. The early return is the right call.

Why the na_rm kernels are different

The two cases look similar but the branch is not the same kind of branch.

In _na_rm, the test is per element and its outcome is data dependent. With scattered NAs the predictor guesses wrong roughly as often as NAs appear, and every miss costs a pipeline flush. sum += ok ? x_elt : 0 removes that.

In the non-na_rm kernels, the test is a loop exit. It is not taken until it is taken once, and then the function returns. The predictor gets it right every single iteration. There is no misprediction to remove, so the only thing branchless changes is that you now always walk the whole run.

The other usual reason to go branchless is vectorization, and it does not apply here: sum is long double, and FP addition is not associative, so the compiler will not vectorize the reduction either way.

One caveat on the measurement

My first pass showed the no-NA case at 1.05 ms, which made branchless look better than it is. That was an artifact of allocating the array immediately before benchmarking it. Building all inputs up front and then timing them gives 0.814 ms, and the numbers become stable across reorderings. Worth knowing for bench/mean.R, which builds its input inside the loop the same way.

Yes, in exactly one case: count == 0.

An empty run leaves sum at 0.0, which passes both ISNAN and the outer R_FINITE, so you reach sum /= count with 0.0 / 0 and get NaN. That's the correct answer (it matches mean(double())), and the inner R_FINITE check right below it is what stops the correction pass from running on it.

For count >= 1 it can't happen. Dividing a finite value by an integer of 1 or more only shrinks the magnitude, so there's no overflow path and no way to make a NaN.

Two things that follow from that:

The inner if (R_FINITE((double) sum)) at src/reduce-mean.c:255 and :299 is purely the empty-run guard. It isn't catching an infinite sum, because the outer branch already routed those to the else. R's own rmean() in summary.c writes the check as one R_FINITE after s /= n precisely because it hasn't split those two cases apart first.

The else branch can't be reached with count == 0, since a zero-length run always leaves sum finite. So sum += x_elt / count there is safe.

The long double to double cast leans the right way too. If sum is out of double range on a platform where long double is wider, the cast gives ±Inf, R_FINITE is false, and you take the else. The guard never lets a too-large value through.

Why it's safe

When count == 0, the correction pass falls through to NaN on its own:

  • sum /= count gives NaN
  • correction stays 0.0 (non-na_rm: the run is empty so the loop body never runs; na_rm: every element is NaN so the ISNAN ternary contributes 0)
  • sum += correction / count is NaN + 0.0/0, so NaN + NaN, so NaN

Same answer, fewer branches. The check was only ever reachable for count == 0, and for that case it was picking between two paths that both return NaN.

Checked directly: array(double(), c(0, 3)), the integer and logical empties, and mean(c(NA, NA), na.rm = TRUE) all still give NaN.

What I left alone

The R_FINITE check in the else branch stays. That one is real. sum there is already ±Inf, so the rescaled sum += x_elt / count can still come out ±Inf (every element Inf, say), and running the correction pass on it would compute Inf - Inf and turn a correct Inf into NaN. The two branches no longer look symmetric, which is the one cost of this change.

One note on the mechanism: the code now leans on 0.0 / 0 producing NaN in two places instead of one. That isn't a new dependency, since the old code already needed sum /= count to yield NaN to return the right answer for an empty run, and this codebase assumes IEEE semantics throughout.

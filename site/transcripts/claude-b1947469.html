We’ve been working on rray index here and I’ve just realized there might be an alternate algorithm for it

Rather than trying to iterate every index in parallel, we could have a locations array of r_ssize that we build one index at a time

It might actually be faster? At the cost of that allocation of course. I’m not sure, but in theory it lets us take advantage of all of the optimizations of the 1 element iterator plan, which we’d just reuse or recreate repeatedly for each index

Do you see what I mean?

r_obj* rray_index(
  r_obj* x,
  r_obj* indices,
  struct rray_arg* x_arg,
  struct rray_arg* indices_arg,
  struct r_lazy error_call
) {
  check_unclassed(x, x_arg, error_call);
  x = KEEP(arg_as_array(x, x_arg, error_call));

  r_obj* x_dimensions = KEEP(r_dim(x));
  const int* v_x_dimensions = r_int_cbegin(x_dimensions);
  const int x_dimensionality =
    rray_dimensionality_from_dimensions(x_dimensions);
  check_dimensionality(x_dimensionality);

  r_ssize v_x_strides[RRAY_MAX_DIMENSIONALITY];
  rray_fill_strides_from_dimensions(
    v_x_dimensions,
    x_dimensionality,
    v_x_strides
  );

  indices = KEEP(rray_as_index_arrays(
    indices,
    v_x_dimensions,
    x_dimensionality,
    indices_arg,
    error_call
  ));
  r_obj* const* v_indices = r_list_cbegin(indices);
  const r_ssize indices_size = r_length(indices);

  r_obj* dimensions =
    KEEP(rray_dimensions_common(indices, r_null, indices_arg, error_call));
  const int* v_dimensions = r_int_cbegin(dimensions);
  const int dimensionality = rray_dimensionality_from_dimensions(dimensions);

  // `...` can take up to `RRAY_MAX_DIMENSIONALITY` inputs, bounded by the
  // dimensionality of `x`. Each input can have dimensionality up to
  // `RRAY_MAX_DIMENSIONALITY`, so the maximum size is known.
  r_ssize v_indices_strides[RRAY_MAX_DIMENSIONALITY * RRAY_MAX_DIMENSIONALITY];
  rray_fill_broadcast_strides_from_arrays(
    v_indices,
    indices_size,
    v_dimensions,
    dimensionality,
    v_indices_strides
  );

  // `...` can have up to `RRAY_MAX_DIMENSIONALITY` inputs, bounded by the
  // dimensionality of `x`.
  const int* v_v_index[RRAY_MAX_DIMENSIONALITY];
  for (r_ssize i = 0; i < indices_size; ++i) {
    v_v_index[i] = r_int_cbegin(v_indices[i]);
  }

  const struct rray_strided_iterator_n_plan plan = rray_strided_iterator_n_plan(
    v_dimensions,
    dimensionality,
    v_indices_strides,
    indices_size
  );

  r_obj* out;

  switch (r_typeof(x)) {
  case R_TYPE_logical:
    out = rray_index_lgl(x, v_x_strides, v_v_index, indices_size, &plan);
    break;
  case R_TYPE_integer:
    out = rray_index_int(x, v_x_strides, v_v_index, indices_size, &plan);
    break;
  case R_TYPE_double:
    out = rray_index_dbl(x, v_x_strides, v_v_index, indices_size, &plan);
    break;
  case R_TYPE_complex:
    out = rray_index_cpl(x, v_x_strides, v_v_index, indices_size, &plan);
    break;
  case R_TYPE_raw:
    out = rray_index_raw(x, v_x_strides, v_v_index, indices_size, &plan);
    break;
  case R_TYPE_character:
    out = rray_index_chr(x, v_x_strides, v_v_index, indices_size, &plan);
    break;
  case R_TYPE_list:
    out = rray_index_list(x, v_x_strides, v_v_index, indices_size, &plan);
    break;
  default:
    r_stop_unreachable();
  }

  KEEP(out);
  r_attrib_poke_dim(out, dimensions);

  FREE(5);
  return out;
}

static r_obj* rray_as_index_arrays(
  r_obj* indices,
  const int* v_dimensions,
  int dimensionality,
  struct rray_arg* indices_arg,
  struct r_lazy error_call
) {
  r_obj* const* v_indices = r_list_cbegin(indices);
  const r_ssize indices_size = r_length(indices);

  if (indices_size != dimensionality) {
    r_abort_lazy_call(
      error_call,
      "Must supply exactly %d coordinate array%s to `...`, not %" R_PRI_SSIZE
      ".",
      dimensionality,
      dimensionality == 1 ? "" : "s",
      indices_size
    );
  }

  if (r_names(indices) != r_null) {
    r_abort_lazy_call(error_call, "All elements of `...` must be unnamed.");
  }

  r_obj* out = KEEP(r_alloc_list(indices_size));

  r_ssize i = 0;
  struct rray_arg* index_arg =
    new_subscript_arg(indices_arg, r_null, indices_size, &i);
  KEEP(index_arg->shelter);

  for (; i < indices_size; ++i) {
    r_obj* index =
      rray_as_index_array(v_indices[i], v_dimensions[i], index_arg, error_call);
    r_list_poke(out, i, index);
  }

  FREE(2);
  return out;
}

1	# Optimizing `rray_index()`
2	
3	## Status
4	
5	This document is an implementation plan. It does not describe code that is
6	already present. Every number in it comes from a throwaway proof of concept
7	that was measured and then discarded, so the code sketches below are known to
8	compile, pass the full test suite, and produce the stated timings.
9	
10	The work is split into four steps. Steps 1, 2 and 3 are measured. Step 4 is
11	not, and is written as a proposal with an expected direction rather than a
12	promised number.
13	
14	## Why
15	
16	`rray_index()` reads one value from `x` for every point in the common
17	dimensions of the coordinate arrays. The inner loop lives in `src/index.c` and
18	is built from three pieces:
19	
20	- `rray_index_plan()` at `src/index.c:199`, which fills a stride table.
21	
22	- `rray_index_plan_location()` at `src/index.c:256`, which turns one set of
23	  coordinates into one location in `x`.
24	
25	- `rray_index_plan_next()` at `src/index.c:275`, which advances the point and
26	  every coordinate array location.
27	
28	This is the same algorithm numpy uses for the equivalent operation. numpy's
29	version is `mapiter_get()` in
30	`numpy/_core/src/multiarray/lowlevel_strided_loops.c.src`, reached from
31	`array_subscript()` in `numpy/_core/src/multiarray/mapping.c`. There are no
32	gather intrinsics, no blocking, and no parallelism on either side. The gap
33	between us is entirely in how much the compiler is allowed to specialize.
34	
35	Measured on the same machine, source arrays small enough to stay in cache so
36	that gather latency does not dominate. The last column is what the proof of
37	concept reached with steps 1 through 3 applied:
38	
39	| Case | numpy | rray today | after steps 1-3 |
40	|---|---|---|---|
41	| 1-d source, 1 coordinate array | 0.94 ns/elt | 3.62 ns/elt | 1.85 ns/elt |
42	| 2-d source, 2 coordinate arrays | 3.38 ns/elt | 4.51 ns/elt | 2.10 ns/elt |
43	| 3-d source, 3 coordinate arrays | 4.22 ns/elt | 6.22 ns/elt | 2.87 ns/elt |
44	| 2-d Cartesian broadcast | 2.79 ns/elt | 3.33 ns/elt | 0.94 ns/elt |
45	
46	numpy's indices are 8 byte `intp` and ours are 4 byte `int`, so we read half
47	the index bytes. After these steps we are ahead of numpy everywhere except the
48	single coordinate array case, where their dedicated `mapiter_trivial_get()`
49	path still wins by 2x.
50	
51	## Measurement harness
52	
53	Rebuild this before changing anything. Every case produces about 1048576
54	output elements, and the source array is deliberately small in most rows so
55	that the loop cost is visible rather than the memory latency.
56	
57	```r
58	n <- 1048576L
59	a <- sample(10L, n, replace = TRUE)
60	b <- sample(10L, n, replace = TRUE)
61	square <- c(1024L, 1024L)
62	a2 <- array(a, square)
63	b2 <- array(b, square)
64	
65	x2_small <- array(1:100, c(10L, 10L))
66	
67	rray_index(x2_small, a2, b2)
68	```
69	
70	The cases that matter are, in order: a 1-d source with one coordinate array, a
71	2-d source with two square coordinate arrays, a Cartesian broadcast of
72	`[1024, 1]` against `[1, 1024]`, 3-d and 4-d sources with matching coordinate
73	counts, and the same 2-d case with coordinate arrays reshaped to 10 and 20
74	axes.
75	
76	Include a leading unit axis case where every coordinate array is shaped `[1, N]`
77	or `[1, 1, N]`. That is the only shape coalescing helps, and a grid without it
78	will make step 3 look pointless. The first version of this plan made that
79	mistake. Include the take-along-axis shapes too, since they are the ones a
80	reader will assume benefit and do not.
81	
82	Two things to know before trusting any number from it.
83	
84	Run to run noise on the `ns/elt` rows is within 3%. Noise on the small call
85	rows is up to 16%, so do not read anything into a small call change under 20%.
86	
87	Passing bare integer vectors as coordinates is measurably slower than passing
88	1-d arrays holding identical data, 0.91 ns/elt against 0.57 ns/elt for the
89	validation pass alone. A pre-wrapped ALTREP array is exactly as fast as a plain
90	array, which rules out ALTREP element access and points at the per-call
91	`vec_as_array()` wrapper. The cause is not confirmed and GC pressure is the
92	leading hypothesis. It is not part of this plan, but benchmarks will disagree
93	with each other if some pass vectors and some pass arrays, so pick one.
94	
95	## What the proof of concept measured
96	
97	Seven builds, collapsed here to the five that matter. `specialize` is step 1
98	limited to 1 and 2 coordinate arrays. `spec 1-4 + coalesce` is steps 1 and 3
99	together. `+ run loop` adds step 2, and the last column removes coalescing
100	again to isolate what step 3 is actually contributing. All values are ns/elt

// pass k, walking coordinate array k with its own 1 operand plan

// final pass

I think it's a good idea, and it probably is faster once K is 2 or more. The main reason isn't obvious at first: coalescing becomes per array.

Why it should win

  • Each array coalesces on its own. Right now the n-way plan can only merge two axes if every coordinate array agrees they can merge. plans/index-optimize.md says crossed strides never coalesce, which is why the take-along-axis shapes get nothing from step 3. With one plan per array, [A, 1, 1] coalesces to [A, B*C] with strides [1, 0], and [1, 1, C] coalesces to [A*B, C] with strides [0, 1], each independently.

  • You get the existing fast paths for free. First axis runs and the literal 0 stride path already exist in src/strided-iterator.h. A coordinate array broadcast along the run axis becomes "add a constant to a contiguous stretch", which vectorizes.

  • Step 1 (specializing on K) goes away. K becomes the outer loop, and the inner loop always handles exactly one operand. No 4-way copy of the loop for every type.

  • Only the last pass depends on type. Building locations is pure r_ssize math, so it's written once, not 7 times. That's a large drop in code size compared with the current macros.

  • The missing value check (step 4) becomes per array. Only arrays that actually contain NA pay for it.

Design points

  • Fuse the ends. The first array writes into the buffer instead of adding to it, so no zeroing pass. The last array does the add and the gather in the same loop. With K = 1 there's then no buffer at all, and the loop is basically RRAY_BROADCAST_ATOMIC with a gather. That's the shape of numpy's mapiter_trivial_get(), the one case where we still lose to them.

  • NA as a large negative value. Let a missing coordinate add a big negative constant, around -2^56. x has fewer than 2^52 elements and there are at most 64 arrays, so the sum never overflows and is negative exactly when some coordinate was NA. #' Index an array by coordinates
#'
#' `rray_index()` selects values from `x` with one coordinate array for each
#' source axis. The coordinate arrays broadcast to common dimensions and are
#' read pointwise. Their common dimensions become the dimensions of the result.
#'
#' @details
#' Each argument in `...` identifies positions on one axis of `x`. The first
#' argument identifies positions on the first axis, the second argument
#' identifies positions on the second axis, and so on. You must supply exactly
#' one unnamed coordinate array for every axis of `x`.
#'
#' A coordinate array must be a bare integer vector or array. Vectors are
#' treated as one-dimensional arrays. Each coordinate must be a positive,
#' one-based position within its source axis. Zero, negative, and out-of-bounds
#' coordinates are errors.
#'
#' Coordinate arrays use left-aligned broadcasting. At each point in the common
#' dimensions, `rray_index()` takes one coordinate from each broadcast array
#' and uses the complete set of coordinates to select one value from `x`.
#' Singleton dimensions can be placed on different axes to form a Cartesian
#' product.
#'
#' A missing coordinate on any source axis produces a missing value at that
#' result point. For raw arrays the missing value is `as.raw(0)`, and for list
#' arrays it is `NULL`.
#'
#' The result has the same storage type as `x`. Its dimensions are the common
#' dimensions of the coordinate arrays. All names are dropped because a result
#' axis does not necessarily correspond to one source axis.
#'
#' @param x A bare array or vector.
#'
#' @param ... Exactly one unnamed integer coordinate array for each axis of
#'   `x`.
#'
#' @returns
#' An array with the common dimensions of `...` and the same storage type as
#' `x`.
#'
#' @export
#' @examples
#' x <- array(1:6, c(2L, 3L))
#'
#' # Pair coordinates pointwise
#' rray_index(x, c(1L, 2L, 1L), c(1L, 2L, 3L))
#'
#' # Form a Cartesian product through broadcasting
#' rows <- array(c(1L, 2L), c(2L, 1L))

#'

#'

#' rray_index(x, !!!coordinates)

What I learned

  • Every shape of coordinate array now costs the same. Flat, [1, N], [1, 1, N], [1, 1024, 1024], 10 axes and 20 axes all land at 2.38 ns/elt. The take-along-axis cases improve a lot, which the old coalescing plan said they couldn't, because each array now coalesces on its own.

  • Chunking wouldn't help. Each extra array costs about 0.95 ns/elt whether the buffer fits in cache (16K elements) or not (4M elements). So memory traffic isn't the limit.

  • Validation is now the biggest cost. It costs 0.57 ns/elt per array. An extra array is about 0.57 for validation plus about 0.36 for its build pass. With one array, validation is over half of the 1.1 ns/elt. A faster validation loop is the next obvious win.

static int rray_index_coalesce(
  r_ssize* v_dimensions,
  r_ssize* v_strides,
  int dimensionality,
  r_ssize n
) {
  int out_axis = 0;

  for (int axis = 1; axis < dimensionality; ++axis) {
    const r_ssize left_dimension = v_dimensions[out_axis];
    const r_ssize right_dimension = v_dimensions[axis];
    r_ssize* v_left = v_strides + (r_ssize) out_axis * n;
    const r_ssize* v_right = v_strides + (r_ssize) axis * n;

    bool coalescible = true;

    for (r_ssize i = 0; i < n; ++i) {
      if (!(left_dimension == 1 || right_dimension == 1 ||
            v_right[i] == left_dimension * v_left[i])) {
        coalescible = false;
        break;
      }
    }

    if (coalescible) {
      if (left_dimension == 1) {
        for (r_ssize i = 0; i < n; ++i) {
          v_left[i] = v_right[i];
        }
      }
      v_dimensions[out_axis] = left_dimension * right_dimension;
    } else {
      ++out_axis;
      v_dimensions[out_axis] = right_dimension;
      r_ssize* v_out = v_strides + (r_ssize) out_axis * n;
      for (r_ssize i = 0; i < n; ++i) {
        v_out[i] = v_right[i];
      }
    }
  }

  return out_axis + 1;
}

What the numbers say

  • One read of all K arrays beats K separate passes. Walking all the arrays together reads each coordinate once and writes nothing extra. The per-array version writes and re-reads an 8 byte location for every element on each extra pass, and that costs more than walking the arrays together.

  • Step 4 is worth doing. It gains 5% to 20% over steps 1-3 in most cases, and 22% on the take shapes. The one array case drops to 1.09 ns/elt.

Yes. Steps 1-4 keep all their state on the stack: one position per coordinate array, plus the plan. So they never allocate anything beyond the result itself.

The per-array version allocates 8 bytes per result element whenever there are two or more coordinate arrays. The size of that buffer relative to the result depends on the type:

  • Double, character, list (8 bytes per element): same size as the result.

  • Integer, logical (4 bytes per element): twice the size of the result.

  • Raw (1 byte per element): 8 times the size of the result.

  • Complex (16 bytes per element): half the size of the result.

A 1e8 element result would need 800 MB of scratch memory on top of the result. That's live at the same time as the result, so it doubles or triples peak memory use and could fail where the plan's approach wouldn't.

So the plan wins on speed and on memory. The per-array version's only advantage is simpler code.

# Optimizing `rray_index()`, part 2

## Summary

This branch implements steps 1 through 4 of `plans/index-optimize.md`:

1. Specialize the loop on 1, 2, 3 and 4 coordinate arrays.

2. Walk the first axis as a run, with a literal stride 1 path.

3. Merge (coalesce) adjacent axes across all coordinate arrays.

4. Skip the missing value check when validation saw no `NA`.

It is 50% to 78% faster than `feature/index` on every large case, and bit identical on every case measured.

We also built and measured a different algorithm, one pass per coordinate array. It lost to steps 1-4 on every case with two or more coordinate arrays, and it needs a scratch buffer as large as the result or larger. We recommend steps 1-4.

## The two algorithms

Both algorithms compute, for every point of the result, a flat location into `x`:

```c
location = (i1 - 1) * x_stride1 + (i2 - 1) * x_stride2 + ...
```

Steps 1-4 walk all K coordinate arrays together. Each output element reads one value from each array, sums the location, and reads `x` once. The only state is one position per coordinate array, which lives on the stack.

The per-array idea walks one coordinate array at a time with the 1 operand strided iterator. Each pass adds that array's part of the location into an `r_ssize` buffer the size of the result:

```c
// first array
v_locations[i] = (v_index[loc] - 1) * x_stride;

// middle arrays
v_locations[i] += (v_index[loc] - 1) * x_stride;

// last array, also reading from `x`
v_out[i] = v_x[v_locations[i] + (v_index[loc] - 1) * x_stride];
```

It looked attractive for three reasons. Each array gets its own coalescing, so crossed strides no longer block a merge. It reuses the existing 1 operand fast paths. And it needs no per-count specialization, so it is much less code. With one coordinate array there is no buffer at all.

Missing values were handled the way we planned for this branch. Validation records whether each array holds an `NA`. Arrays without one are visited first with no check. Arrays with one are visited last, and mark a missing location with `-1`.

## Why we recommend steps 1-4

### It is faster

Steps 1-4 beat the per-array algorithm by 19% to 47% on every case with two or more coordinate arrays. With one coordinate array they tie, because both reduce to the same loop: walk one array, read `x`, no buffer.

The reason is the buffer. Walking all arrays together reads each coordinate once and writes each output once. The per-array algorithm also writes an 8 byte location per element on every pass but the last, and reads it back on the next pass.

Each extra coordinate array cost the per-array build about 0.95 ns/elt. Two measurements split that cost:

- **Validation is about 0.57 ns/elt of it.** `rray_as_index_array()` alone on a 1-d array measured 0.59 ns/elt at 16384 elements and 0.56 ns/elt at 1048576 elements. Every build pays this, once per coordinate array.

- **The build pass is the other 0.36 ns/elt or so.**

The per-array cost did not depend on whether the buffer fit in cache. Timing each coordinate count across output sizes, with one coordinate array per axis of a small `x`:

| Output size | base, K = 1 to 4 | per-array, K = 1 to 4 |
|---|---|---|
| 4096 | 3.33, 4.53, 6.47, 7.67 | 1.67, 3.20, 4.21, 5.19 |
| 16384 | 2.93, 4.12, 6.04, 7.11 | 1.29, 2.66, 3.56, 4.47 |
| 65536 | 2.82, 3.99, 5.82, 6.93 | 1.16, 2.37, 3.28, 4.17 |
| 262144 | 2.77, 3.96, 5.82, 6.90 | 1.09, 2.33, 3.27, 4.18 |
| 1048576 | 2.79, 3.96, 5.77, 6.93 | 1.10, 2.06, 2.99, 4.11 |
| 4194304 | 2.68, 4.01, 5.80, 6.93 | 1.09, 2.38, 3.32, 4.29 |

The step from K to K + 1 is roughly constant from 16384 elements (a 128 KB buffer) up to 4194304 elements (a 32 MB buffer). Memory traffic is not the limit, so processing the result in cache sized chunks would not have rescued it.

### It needs no scratch memory

Steps 1-4 allocate nothing beyond the result. The per-array algorithm allocates 8 bytes per result element whenever there are two or more coordinate arrays, and that buffer is alive at the same time as the result:

| Storage type | Buffer size relative to the result |
|---|---|
| raw | 8x |
| logical, integer | 2x |
| double, character, list | 1x |
| complex | 0.5x |

A 1e8 element result would need 800 MB of scratch on top of the result. That can fail where steps 1-4 would succeed.

### What the per-array algorithm did better

Only code size. It needs no per-count specialization, and only the final pass depends on the storage type. That is not worth a 20% to 45% slowdown and a scratch buffer.

## Findings that change `plans/index-optimize.md`

- **Take shapes do benefit.** The earlier plan said the take-along-axis shapes would not gain from step 3. That is true of coalescing, but the run loop from step 2 still cuts them by 55% to 65%, and step 4 takes a further 7% to 21% off.

- **Step 4 is measured now.** It is worth 5% to 8% on most cases and 12% to 21% on the Cartesian, mixed and take shapes. With one coordinate array it is worth 15%, bringing that case to 1.08 ns/elt. The earlier plan quoted numpy at 0.94 ns/elt for this case, but that number is from a different session, so treat the gap as approximate.

- **Coalescing still does exactly what the earlier plan said.** `[1, N]`, `[1, 1, N]`, `[1, 1024, 1024]`, 10 axes and 20 axes all cost the same as flat coordinates.

- **Short runs are sensitive to how run strides are read.** Reading each run stride through `rray_strided_iterator_n_plan_run_stride()` on every element was 6% to 7% slower on the mixed and J = 2 take shapes, where every run is 2 elements long. Copying the run strides into a local array before the loop removed the difference.

- **A literal stride 1 path did little for the per-array algorithm.** It was worth about 3%, close to noise. It is worth more in steps 1-4, where it pairs with the count specialization, and it was kept there.

## What changed in this branch

- **`src/strided-iterator.h`**: `rray_strided_iterator_n_plan()` now merges adjacent axes through a new `rray__strided_iterator_axes_coalescen()`, the N operand sibling of `rray__strided_iterator_axes_coalesce2()`.

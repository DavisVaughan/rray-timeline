1	# Array slicing and extraction plan
2	
3	## Recommendation
4	
5	Use ordinary R subscripts for slicing and extraction:
6	
7	```r
8	rray_slice(x, ...)
9	rray_slice_assign(x, ..., value)
10	
11	rray_slice_axis(x, i, ..., axis)
12	rray_slice_assign_axis(x, i, ..., axis, value)
13	
14	rray_slice_rows(x, i)
15	rray_slice_assign_rows(x, i, value)
16	
17	rray_slice_columns(x, i)
18	rray_slice_assign_columns(x, i, value)
19	
20	rray_extract(x, i)
21	rray_extract_assign(x, i, value)
22	```
23	
24	`rray_slice()` performs dimension-preserving orthogonal selection across one
25	or more axes. It requires exactly one subscript per source axis, so `TRUE`
26	selects a whole axis. `rray_slice_axis()` performs the same operation on one
27	axis held in a variable, and `rray_slice_rows()` and `rray_slice_columns()`
28	are its first and second axis shortcuts. `rray_extract()` accepts flat
29	positions or coordinate points and always returns a one-dimensional array.
30	
31	Keep subscripts separate from integer coordinate arrays:
32	
33	| Property | Subscript | Coordinate array |
34	|---|---|---|
35	| Used by | `rray_slice()`, `rray_slice_axis()`, `rray_extract()` | `rray_index()`, `rray_index_axis()` |
36	| Meaning | A set of positions | One source coordinate per output point |
37	| Accepted forms | Integer, double, logical, character where defined, `NULL` | Bare integer vector or array |
38	| Negative values | Select the complement | Error |
39	| Zero | Ignored | Error |
40	| Shape | Does not connect positions across axes | Connects coordinates pointwise through broadcasting |
41	
42	The function name determines the contract. The dimensions of `i` never turn a
43	slice subscript into a coordinate array. `rray_extract()` has a separate,
44	explicit matrix rule for coordinate points.
45	
46	Do not add replacement functions. Every `_assign()` function returns a
47	modified copy of `x`. There are no `[` or `[[` methods because rray4 provides
48	functions rather than an array class.
49	
50	## The indexing family
51	
52	The complete family has five read operations:
53	
54	| Operation | Function | Result shape |
55	|---|---|---|
56	| Orthogonal subscripts | `rray_slice(x, ...)` | One output axis per source axis |
57	| One-axis subscript | `rray_slice_axis(x, i, ..., axis)` | Source dimensions with one axis replaced |
58	| First or second axis subscript | `rray_slice_rows(x, i)`, `rray_slice_columns(x, i)` | Source dimensions with one axis replaced |
59	| One-axis coordinate array | `rray_index_axis(x, i, ..., axis)` | Source dimensions with one axis replaced |
60	| Full coordinate arrays | `rray_index(x, ...)` | Common coordinate dimensions |
61	| Flat subscript or point matrix | `rray_extract(x, i)` | One dimensional |
62	
63	`rray_index()` is the general coordinate operation. Every other operation can
64	be described by constructing one explicit coordinate array for every source
65	axis and then calling `rray_index()`. The public wrappers remain important
66	because they accept different inputs, guarantee more specific shapes, retain
67	more names, and can use faster implementations.
68	
69	See `plans/index.md` for strict coordinate arrays and the complete lowering of
70	each operation to `rray_index()`.
71	
72	## Orthogonal slicing
73	
74	Each subscript controls one source axis. Subscripts are normalized separately,
75	then their locations form a Cartesian product.
76	
77	```r
78	x <- array(1:24, c(2, 3, 4))
79	
80	rray_slice(x, c(2, 1), c(3, 1), 2)
81	# dimensions: c(2, 2, 1)
82	
83	rray_slice_axis(x, c(3, 1), axis = 2)
84	# dimensions: c(2, 2, 4)
85	```
86	
87	This is close to base R's `x[..., drop = FALSE]`. Slicing never drops axes.
88	
89	The same Cartesian product can be expressed through full coordinate indexing.
90	After normalizing the three subscripts to positive locations, shape them as an
91	open mesh:
92	
93	```text
94	axis 1 coordinates: (I, 1, 1)
95	axis 2 coordinates: (1, J, 1)
96	axis 3 coordinates: (1, 1, K)
97	common dimensions:  (I, J, K)
98	```
99	
100	The shaped coordinate arrays broadcast to the slicing result dimensions.

102	## `rray_slice()`
103	
104	```r
105	rray_slice(x, ...)
106	rray_slice_assign(x, ..., value)
107	```
108	
109	Each element of `...` applies to the matching source axis. `...` must contain
110	exactly one subscript per source axis. `TRUE` selects a whole axis.
111	
112	```r
113	rray_slice(x, 1, TRUE, TRUE)
114	# dimensions: c(1, 3, 4)
115	
116	rray_slice(x, TRUE, 1, TRUE)
117	# dimensions: c(2, 1, 4)
118	
119	rray_slice(x, TRUE, TRUE, TRUE)
120	# dimensions: c(2, 3, 4)
121	```
122	
123	An empty argument does not select a whole axis. Base R writes a whole axis as
124	a gap between two commas, which is easy to miscount and invisible on screen, so
125	`rray_slice()` asks for `TRUE` instead. Empty arguments get no special error,
126	`list2()` handles them like it does everywhere else: a trailing one is dropped,
127	and any other is an error.
128	
129	```r
130	rray_slice(x, , , 1:2)
131	# Error in `list2()`: Argument 1 can't be empty.
132	
133	rray_slice(x, 1, TRUE, TRUE, )
134	# Same as `rray_slice(x, 1, TRUE, TRUE)`
135	```
136	
137	Too few and too many subscripts are the same error. Subscripts in `...` must
138	be unnamed because selection is positional.
139	
140	Because every argument is an ordinary value, the dots are plain `list2()` dots
141	and splicing needs no special handling:
142	
143	```r
144	indices <- rep(list(TRUE), rray_dimensionality(x))
145	indices[[3]] <- c(3, 1)
146	rray_slice(x, !!!indices)
147	```
148	
149	`value` follows `...` in `rray_slice_assign()`, so it must be supplied by
150	name.

153

157	```

160	supplied by name, so a call always says which axis it means and never reads as
161	a second subscript. This matches `rray_rep()` and `rray_split()`.
162	
163	```r
164	rray_slice_axis(x, c(3, 1), axis = 2)
165	rray_slice_assign_axis(x, c(3, 1), axis = 2, value = 0L)
166	```
167	
168	`rray_slice_axis()` has exactly the same subscript semantics as supplying `i`
169	at the matching position in `rray_slice()`. The same normalized subscript is
170	used for every lane through the selected axis. Only the selected axis
171	dimension can change.
172	
173	```r
174	x <- matrix(
175	  c(
176	    10, 20, 30, 40,
177	    50, 60, 70, 80
178	  ),
179	  nrow = 2,
180	  byrow = TRUE
181	)
182	
183	rray_slice_axis(x, c(4, 1), axis = 2)
184	#      [,1] [,2]
185	# [1,]   40   10
186	# [2,]   80   50
187	```
188	
189	The function replaces the need to pad a call with `TRUE` when `axis` is held
190	in a variable.
191	
192	`i` is always an ordinary subscript. Its dimensions do not affect the result
193	dimensions. A multidimensional object that is not a valid ordinary subscript
194	is an error. Use `rray_index_axis()` when an integer array supplies a different
195	location for different lanes.

1	# Integer coordinate indexing plan
2	
3	## Recommendation
4	
5	Add one fully specified coordinate function and one directional one-axis
6	specialization:
7	
8	```r
9	rray_index(x, ...)
10	rray_index_assign(x, ..., value)
11	
12	rray_index_axis(x, i, ..., axis)
13	rray_index_assign_axis(x, i, ..., axis, value)
14	```
15	
16	`rray_index()` requires exactly one integer coordinate array for every source
17	axis. The arrays broadcast to common dimensions and are read pointwise. The
18	common dimensions are the result dimensions.
19	
20	`rray_index_axis()` accepts one integer array for the selected source axis and
21	supplies identity coordinates for every other axis. `i` must broadcast to the
22	dimensions of `x` outside `axis`. The result has the same dimensionality as
23	`x`, every unselected axis keeps its source dimension, and only the selected
24	axis can change.
25	
26	Every source coordinate is explicit. Different partial indexing behaviors are
27	represented by shaping full coordinate arrays in different ways.
28	
29	The complete family is:
30	
31	| Operation | Read | Assign |
32	|---|---|---|
33	| Orthogonal subscripts | `rray_slice()` | `rray_slice_assign()` |
34	| One-axis subscript | `rray_slice_axis()` | `rray_slice_assign_axis()` |
35	| First axis subscript | `rray_slice_rows()` | `rray_slice_assign_rows()` |
36	| Second axis subscript | `rray_slice_columns()` | `rray_slice_assign_columns()` |
37	| One-axis coordinate array | `rray_index_axis()` | `rray_index_assign_axis()` |
38	| Full coordinate arrays | `rray_index()` | `rray_index_assign()` |
39	| Flat subscript or point matrix | `rray_extract()` | `rray_extract_assign()` |
40	
41	Do not add replacement functions. Every `_assign()` function returns a
42	modified copy of `x`.

44	## Subscripts and coordinates
45	
46	A subscript describes a set of positions. It can be negative, logical,
47	character, missing, or `NULL`. Subscript normalization produces a
48	one-dimensional sequence of positive or missing locations. Subscripts on
49	different axes form a Cartesian product.
50	
51	A coordinate array has a narrower meaning. Each non-missing element is one
52	positive, one-based position on one source axis. Its dimensions connect that
53	coordinate to an output point. Coordinates on different source axes broadcast
54	and pair pointwise.
55	
56	```r
57	rray_slice_axis(x, -1L, axis = 2L)
58	# Complement selection
59	
60	rray_index_axis(x, array(-1L, rray_dimensions(x)), axis = 2L)
61	# Error: coordinates must be positive
62	```
63	
64	The function name determines the input rules. The shape or class of `i` never
65	changes a slice into coordinate indexing.
66	
67	## Full coordinate model
68	
69	Let:
70	
71	- `D` be the source dimensions.
72	- `n` be the dimensionality of `x`.
73	- `L[a]` be the coordinate array supplied for source axis `a`.
74	- `G` be the common dimensions of all `L[a]`.
75	
76	`rray_index()` requires exactly `n` coordinate arrays. At every output point
77	`g` in `G`, each broadcast coordinate array supplies one component of the
78	source coordinate:
79	
80	```text
81	source[a] = broadcast(L[a])[g]
82	out[g] = x[source[1], source[2], ..., source[n]]
83	```
84	
85	The result dimensions are exactly `G`:
86	
87	```text
88	out_dimensions = common_dimensions(L[1], ..., L[n])
89	```
90	
91	The output can have lower, equal, or greater dimensionality than `x`. There is
92	no source-axis placement rule because every output axis belongs to the common
93	coordinate space.
94	
95	Singleton dimensions and missing trailing dimensions follow rray's
96	left-aligned broadcasting rules.
97	
98	## Coordinate validation
99	
100	Each argument in `...` and `i` in `rray_index_axis()` must be a bare integer
101	vector or array. Bare vectors are one-dimensional arrays. Factors and other
102	classed integer objects are errors.
103	
104	Every non-missing coordinate must be positive, one based, and no greater than
105	the dimension of its source axis:
106	
107	- Positive integers identify one source position.
108	- Zero and negative integers are errors.
109	- Missing coordinates produce missing output when reading.
110	- Missing coordinates are errors when assigning.
111	- Out-of-bounds coordinates are errors.
112	
113	Logical, character, and double inputs are errors. Logical values are masks,
114	character values require name matching, and doubles weaken the strict
115	coordinate contract. Those inputs belong to slicing or extraction.
116	
117	Validation happens before allocating or copying the result. Every coordinate
118	array is validated even when the common result has size zero.

1	# rray4 implementation plan
2	
3	## What this is
4	
5	rray4 is a reimagining of rray, written in pure C with no xtensor. It is a
6	toolkit of `rray_*()` functions that broadcast, reshape, reduce and index base R
7	arrays.
8	
9	It works on bare arrays only. There is no rray class, and classed input is an
10	error. The extension system that would let other packages plug their own array
11	classes in is deliberately deferred, and is written up separately in
12	`plans/extensions.md`.
13	
14	This document is the guide for agents working on rray4 across many sessions.
15	Part 4 is the ordered list of pull requests. Part 5 is the catalogue of
16	functions to work through after the foundations land.
17	
18	## How to use this plan
19	
20	Read Part 1 and Part 2 before starting any pull request. They are short on
21	purpose.
22	
23	Then find your pull request in Part 4, or your function in Part 5. Each entry
24	says what to build, which files to touch, and what "done" means.
25	
26	One pull request per entry. Keep them small.
27	
28	---
29	
30	# Part 1: Conventions
31	
32	Terminology (size, axis, dimension, dimensions, dimensionality) is defined in
33	`CLAUDE.md`. Use it exactly.
34	
35	## Files
36	
37	Each feature is a `src/{name}.c` and `src/{name}.h` pair, with an R file at
38	`R/{name}.R` and tests at `tests/testthat/test-{name}.R`.
39	
40	Functions that need per type code split into a shell and a core, both living in
41	`src/{name}.c`. Copy the shape of `src/broadcast.c`.
42	
43	The shell is ordinary C, written once. It holds everything that does not depend
44	on the type: argument checks, dimension arithmetic, iterator setup and names. It
45	ends in a `switch` on `r_typeof(x)` that hands off to the core.
46	
47	The core is one small function per type. It takes `x`, the output size and the
48	iterator, allocates the output at its own type, fills it, and returns it.
49	Allocation belongs to the core because the type is the one thing the shell does
50	not know.
51	
52	Putting the core behind a function call costs nothing. It was benchmarked across
53	five types and four shapes, and every case landed within 1%, which is the run to
54	run noise, because the call happens once per array rather than once per element.
55	Do not re-open this.
56	
57	Two families vary from this.
58	
59	`rray_split()` returns a list of arrays rather than one array, and `r_typeof(x)`
60	is enough to allocate every element at the right type, so the shell builds the
61	list and the core fills what it is handed.
62	
63	The binary arithmetic operators share one shell across many files, so the shell
64	lives in `src/arithmetic.c` and each operator gets its own
65	`src/arithmetic-{op}.c`. They switch on the type pair rather than on one type,
66	and the switch returns the core instead of calling it. 2.4 covers why.
67	
68	The reducers that take `(x, axes, ..., na_rm = FALSE)` share the same shape of
69	shell for the same reason. `rray_reduce()` and the `RRAY_REDUCE` macro live in
70	`src/reduce.c`/`src/reduce.h`, and each reducer gets its own
71	`src/reduce-{name}.c`, switching on `rray_typeof(x)` and returning the core.
72	`rray_sum_along()` is the first of these, in `src/reduce-sum.c`.
73	
74	Each core's whole body is a call into a macro, following `SLICE` in vctrs'
75	`src/slice.c`. There are usually two. `RRAY_{NAME}_ATOMIC` covers `lgl`, `int`,
76	`dbl`, `cpl` and `raw`, which write straight to a data pointer.
77	`RRAY_{NAME}_BARRIER` covers `chr` and `list`, which write through the barrier.
78	Undefine both once the cores are written.
79	
80	The arithmetic family needs only one macro, since it has no `chr` or `list`
81	cores, but several files share it. So `RRAY_ARITHMETIC` lives in
82	`src/arithmetic.h` and nothing undefines it. Only undefine a macro the file
83	defined itself.
84	
85	Write each core's parameter list out in full. Do not hide it behind a macro.
86	
87	A flag that swaps the scalar operation, like `na_rm`, is folded into the same
88	switch that dispatches on type, returning the core instead of calling it:
89	
90	```c
91	case RRAY_TYPE_double:
92	  return na_rm ? rray_sum_along_dbl_na_rm : rray_sum_along_dbl;
93	```
94	
95	So there is one core per type per variant, the flag stays off the core's
96	parameter list, and the loop is written once. `rray_mean()`, `rray_max_along()`, and
97	`rray_min_along()` want the same shape when they land, sharing `rray_reduce()`'s
98	shell. `rray_max_pos()` and `rray_min_pos()` take a single `axis` rather than
99	`axes` and return positions rather than reduced values, so whether they fit this
100	shell at all is still an open question for whoever picks them up.
101	
102	A `.c` file reads top down: the main entry point first, its helpers below, in
103	the order they are used. For `src/broadcast.c` that is `ffi_rray_broadcast()`,

// Strided iterator plan
//
// Optimizes and assists in walking a multidimensional point space defined by
// `v_dimensions`. As it walks, it updates a user provided `start` in an
// alternate subspace defined by `v_strides`.
//
// For performance and flexibility, the user is responsible for managing the run
// loop along the first axis. We've tried many alternative approaches but they
// tend to tank performance quickly as you increase the level of abstractions.
//
// The plan holds only immutable state. The positions that change as it walks
// are managed by the caller. This lets the compiler keep these positions in
// registers, which has significant performance implications.
//
// --------------------------------------------------------------------------
// Examples
//
// For broadcasting, the dimensions you broadcast to make up the larger point
// space. This is walked in order. The original dimensions of the array make
// up the subspace. So as you walk the output's point space you can create
// `location`s back into your original array to pull from.
//
// For reducing, it's actually a special form of broadcasting. The original
// dimensions of the array are the point space. The reduced dimensions are the
// subspace. So as you walk the original array, you can create `location`s into
// the output to accumulate the reduced result at.
//
// For permuting axes, the permuted dimensions make up the point space. The
// original dimensions of the array make up the subspace. So as you walk the
// output's point space you can create `location`s back into your original
// array to pull from.
//
// --------------------------------------------------------------------------
// Optimization - First axis runs
//
// After coalescing, the iterator walks the entire first axis in one inner run
// while holding all later axes fixed. It only updates the later point
// coordinates between runs, rather than checking and carrying them after every
// element. This gives the compiler a small loop where the index and locations
// advance by fixed strides, making it much easier to optimize and vectorize.
//
// Practical examples of when this is useful:
//
// - Identically shaped binary array operations. Adding two [2, 4, 5] arrays
//   coalesces to dimensions [40], so the entire operation is one first axis run
//   where both input locations advance contiguously.
//
// - Broadcasting over a later axis. Broadcasting a [2, 3] array to [2, 3, 4]
//   coalesces to dimensions [6, 4] with location strides [1, 0]. The iterator
//   performs four first axis runs of size 6, copying six contiguous values
//   before updating the later axis.
//
// - Reducing over a later axis. Reducing a [2, 3, 4] array over its third axis
//   also coalesces to dimensions [6, 4] with output strides [1, 0]. Each first
//   axis run accumulates one contiguous slice into six output locations before
//   advancing along the reduced axis.
//
// --------------------------------------------------------------------------
// Optimization - Coalescing
//
// Coalescing axes is an important optimization used to reduce the number of
// axes we have to iterate over by "merging" adjacent compatible ones. This can
// improve performance by 3-5x on its own in some cases.
//
// Practical examples of when this is useful:
//

Here is how broadcasting would work for n, with real numbers.

The rule

A lane is one run of elements along axis. The lane dimensions are dim(x) with axis set to 1. n must broadcast to the lane dimensions, and it can never make x bigger. Every lane gets one shift.

Broadcasting is left aligned, so a plain vector of length A counts as (A, 1, 1, ...). I checked this against the current rray_broadcast().

1. A matrix, one shift per row (your SO question)

x
#      [,1] [,2] [,3] [,4]
# [1,]    1    2    3    4
# [2,]    5    6    7    8
# [3,]    9   10   11   12

# axis = 2, so the lane dimensions are (3, 1)
rray_roll(x, n = c(1, 0, -1), axis = 2)
#      [,1] [,2] [,3] [,4]
# [1,]    4    1    2    3
# [2,]    5    6    7    8
# [3,]   10   11   12    9

A plain vector works because (3) is read as (3, 1).

2. A matrix, one shift per column

x <- matrix(1:12, 3)

# axis = 1, so the lane dimensions are (1, 4)
rray_roll(x, n = matrix(c(0, 1, 2, 3), nrow = 1), axis = 1)
#      [,1] [,2] [,3] [,4]
# [1,]    1    6    8   10

# [3,]    3    5    7   12

This is the one case where broadcasting costs you something. The flat option would take the plain vector here.

3. Where broadcasting helps: three or more dimensions

Take x with dimensions (2, 5, 3): 2 sensors, 5 time points, 3 days. Roll along time, axis = 2. The lane dimensions are (2, 1, 3), so there are 6 lanes.

Goal Broadcasting n Flat n
Same shift everywhere 1 1
One shift per sensor c(1, 2) rep(c(1, 2), times = 3)
One shift per day array(c(0, 1, 2), c(1, 1, 3)) rep(c(0, 1, 2), each = 2)
One shift per lane array(1:6, c(2, 1, 3)) 1:6

With broadcasting, you say which axes the shift varies along, and a size of 1 means "the same for all of these". With the flat option, you have to work out the column-major order of the lanes yourself and build it with rep(). It's easy to mix up times and each, and the mistake isn't caught because the length is still 6.

4. It fits with reducers

Reducers keep the reduced axis as a dimension of 1. So anything computed along axis already has the lane shape and can go straight in:

n <- rray_sum_along(counts, axes = 2)   # dimensions (2, 1, 3)
rray_roll(x, n = n, axis = 2)

A future rray_locate_max(x, axis = 2) would also give (2, 1, 3). So "roll each lane so its maximum comes first" becomes a two-line job. This is the same directional rule plans/index.md already sets out for rray_index_axis(), so the two functions would behave the same way.

Defaults I'll use unless you say otherwise

  • Direction: positive n moves elements toward higher positions, as in NumPy. So rray_roll(1:4, n = 1, axis = 1) gives 4 1 2 3.

  • What n can be: an integer, or a double holding a whole number, cast with vec_cast(). NA is an error. Any size of shift is fine, since it wraps modulo the dimension. A zero dimension is fine with any n.

  • Classed n: an error. Names on n are ignored, the same as i in rray_index_axis().

  • Rolled-axis names: they roll when n has size 1 and are dropped otherwise, as you chose. A size 1 array like array(2L, c(1, 1)) counts as size 1.

  • Scope: no rray_roll_rows() or rray_roll_columns() shortcuts, and it all goes in one pull request.

No. You only give a real dimension on the axes where the shift actually changes. Everywhere else the dimension is 1, which means "the same shift for all of these".

The catch is that broadcasting is left aligned. Axes after the last one that varies can be left off. Axes before it have to be written as 1.

Using the (2, 5, 3) example with axis = 2:

Shift varies along n What you write out
Nothing 1 Nothing
Axis 1 only c(1, 2) Axis 1 (axes 2 and 3 left off)
Axis 3 only array(c(0, 1, 2), c(1, 1, 3)) Axes 1 and 2 as 1, then axis 3
Axes 1 and 3 array(1:6, c(2, 1, 3)) Every axis

So a scalar or "one shift per row" costs nothing. Varying along a later axis means padding the earlier ones with 1. The rolled axis itself is always 1 in n, because a lane gets exactly one shift.

That padding is the same cost we saw for per-column shifts on a matrix (matrix(n, nrow = 1)). It's the main downside of broadcasting. I think it's worth it, because the shape says exactly which axes the shift varies along and mistakes are caught. With the flat option you'd write rep(c(0, 1, 2), each = 2) for the axis 3 case, and nothing checks you got each and times the right way round.

Picture x as a stack of 3 spreadsheets, one per day. Each sheet has 2 rows (sensors) and 5 columns (time).

Rolling along the columns slides each row sideways, and whatever falls off one end comes back on the other. Each row on each sheet is one lane, so there are 2 × 3 = 6 lanes. Each lane needs one number: how far to slide it.

n is a little grid holding those numbers, shaped like one column of the stack: 2 rows by 3 sheets. You don't have to fill in the whole grid. Wherever you give only one number, it gets copied across:

  • One number, n = 1. It's copied to all 6 lanes. Every row on every sheet slides by 1.

  • One number per row, n = c(1, 2). Row 1 slides by 1 and row 2 slides by 2, and that pair is copied onto all 3 sheets.

  • One number per sheet. Each sheet gets its own slide, copied to both rows on that sheet. This is the awkward one. n has to say "I'm talking about sheets" by having a shape of 1 row, 1 column and 3 sheets: array(c(0, 1, 2), c(1, 1, 3)).

  • All 6 numbers. You fill in the whole grid yourself: array(1:6, c(2, 1, 3)).

So you never have to spell out every lane. You spell out only what differs, and everything else is copied. The one annoyance is the per-sheet case, where the shape of n has to point at sheets, because a plain vector is always read as "one per row".

Claude

The idea: treat x as a stack of lanes, work out one shift per lane, then copy each lane into the output with its end wrapped round to the front. No coordinate arrays and no general iterator in the hot loop.

The layout trick

Any array, whatever its dimensionality, can be viewed as three blocks around axis:

x dimensions: (A, B, C, D),  axis = 3

inner = A * B    axes before `axis`
d     = C        the axis we roll along
outer = D        axes after `axis`

element (i, j, g) lives at offset  i + j * inner + g * inner * d

A lane is one (i, g) pair, and j walks along it. There are inner * outer lanes. Rolling by k means:

out[i, j, g] = x[i, (j - k) mod d, g]

Steps

  1. Validate x and axis as src/rep.c does: check_unclassed(), arg_as_array(), check_axis().

  2. Validate n: unclassed, an array (so it keeps its dimensions), cast to integer, no NA. Then call check_broadcastable() against the lane dimensions (dim(x) with axis set to 1). That one call gives the "n can't grow x" rule and its error message for free.

  3. Return early when there's nothing to move: the size is 0, or d is 0 or 1.

  4. Branch on the size of n.

Size 1 n: two copies per group

Normalize once: k = n % d, then add d if it's negative. If k is 0, return a copy of x.

Otherwise, for each group g, the d * inner elements of that group sit next to each other in memory. The roll is just "last part first, then the rest":

x group:   [ j = 0 .. d-k-1 | j = d-k .. d-1 ]
out group: [ j = d-k .. d-1 | j = 0 .. d-k-1 ]

That's two memcpy() calls per group for atomic types, and two plain loops for character and list. This is the common case and it will be about as fast as a copy of x.

Per-lane n

  1. Shift table. Broadcast n to the lane dimensions with the existing rray_broadcast(), then normalize every value into [0, d) in place. That's one integer per lane. It's d times smaller than x, so it's cheap. It also means the modulo runs once per lane rather than once per element.

  2. Main loop, in output order, so writes are sequential:

    for g in 0..outer
  for j in 0..d
    for i in 0..inner
      k   = shift[g * inner + i]
      src = j - k,  plus d if negative
      out[(g * d + j) * inner + i] = x[(g * d + src) * inner + i]

    Reads stay within the current group's block, so they're cache friendly. When inner is 1 (rolling along axis 1), each lane is contiguous, so a lane-by-lane two-memcpy() path would be faster. Following plans/slice.md, I'd only add it if a benchmark shows a real gap.

Code shape

This follows src/rep.c exactly:

  • ffi_rray_roll(), then rray_roll() as the shell.

  • rray_roll_fill_uniform() and rray_roll_fill_varying(), each switching on type into seven cores.

  • The cores are built from RRAY_ROLL_FILL_*_ATOMIC and _BARRIER macros.

  • Files: R/roll.R, src/roll.c, src/roll.h, src/decl/roll-decl.h, a registration in src/init.c, and tests/testthat/test-roll.R.

Testing oracle

Both paths have simple reference definitions in terms of functions we already have or have planned:

  • A size 1 roll is rray_slice_axis(x, c((d - k + 1):d, 1:(d - k)), axis = axis).

  • A per-lane roll is rray_index_axis() with a full coordinate array.

Neither is a good implementation, since the second allocates an integer array as big as x. But they make good test oracles, alongside a plain R loop that uses c(tail(v, k), head(v, d - k)) on each lane.

I'd split it into two functions, the same way slicing and indexing are already split: one function where every lane moves together, and one where each lane can move on its own. Which names you keep then depends only on which function you call, never on the size of n.

The family

rray_roll(x, ..., n, axes)       # one shift per axis, any number of axes
rray_roll_each(x, ..., n, axis)  # one shift per lane, one axis

This matches pairs you already have:

Moves every lane together Moves each lane separately
rray_slice_axis() rray_index_axis()
rray_rep() rray_rep_each()
rray_roll() rray_roll_each()

rray_roll(): NumPy's roll, and names always roll

n has length 1 (reused for every axis) or the same length as axes. Each rolled axis is reordered as a whole, so every position still has exactly one source and its name goes with it.

x
#    a b c
# r1 1 3 5
# r2 2 4 6

rray_roll(x, n = 1, axes = 2)
#    c a b
# r1 5 1 3
# r2 6 2 4

rray_roll(x, n = c(1, 1), axes = c(1, 2))
#    c a b
# r2 6 2 4
# r1 5 1 3

Rolling several axes at once with one shift each is exactly what NumPy's tuple form does.

rray_roll_each(): per-lane shifts, and rolled-axis names always drop

n broadcasts to the lanes, as we discussed. Names on the rolled axis are dropped every time, even when n has size 1. Every other axis keeps its names.

rray_roll_each(x, n = c(1, 2), axis = 2)
#    [,1] [,2] [,3]
# r1    5    1    3
# r2    4    6    2

Here dropping is forced, not chosen. Column 1 came from c in row 1 but from b in row 2, so no single name is correct. Because this function always drops them, n = 1 gives the same names as n = c(1, 2). Nothing changes because a value changed. If you want names kept, you call rray_roll().

How this fits the implementation

  • rray_roll() is a slice. Rolling an axis by k is slicing it with the locations (d - k + 1):d, 1:(d - k). src/slice.c already walks one location table per axis and subsets names from the same tables. So rray_roll() builds rotated tables for the rolled axes, passes NULL (meaning "all of it") for the rest, and calls the slice core. # Rolling plan

## Recommendation

Add two functions:

```r
rray_roll(x, ..., n, axes)
rray_roll_each(x, ..., n, axis)
```

Both move elements along an axis. An element pushed off one end comes back on
the other.

- `rray_roll()` rolls one or more axes, with one shift per axis. Every lane
  through an axis moves by the same amount, so each output position has exactly
  one source position, and names roll with the data.

- `rray_roll_each()` rolls one axis, with one shift per lane. Lanes can move by
  different amounts, so an output position can come from different source
  positions in different lanes. Names on the rolled axis are always dropped.

The split mirrors pairs the package already has:

| Every lane moves together | Each lane moves on its own |
|---|---|
| `rray_slice_axis()` | `rray_index_axis()` |
| `rray_rep()` | `rray_rep_each()` |
| `rray_roll()` | `rray_roll_each()` |

The function decides what happens to names. The size or values of `n` never do.
A caller who wants names kept calls `rray_roll()`.

## Terms

- **Lane.** One run of elements along the rolled axis, with every other
  coordinate held fixed. For a matrix and `axis = 2`, each row is a lane. For
  dimensions `(A, B, C)` and `axis = 2`, there are `A * C` lanes, each of
  length `B`.

- **Lane dimensions.** The dimensions of `x` with the rolled axis set to 1. For
  `(A, B, C)` and `axis = 2`, they are `(A, 1, C)`. There is one lane per
  element of an array with these dimensions.

- **Shift.** The value of `n` for one lane or one axis. It can be negative,
  zero, or larger than the dimension.

## Shared rules

### Direction

A positive shift moves elements toward higher positions, as in NumPy:

```r
rray_roll(1:5, n = 2, axes = 1)
# [1] 4 5 1 2 3
```

A negative shift moves them toward lower positions:

```r
rray_roll(1:5, n = -1, axes = 1)
# [1] 2 3 4 5 1
```

### Wrapping

A shift is reduced modulo the dimension `d` of the rolled axis, into `[0, d)`:

```text
k = n mod d
out[..., j, ...] = x[..., (j - k) mod d, ...]
```

So a shift of `7` on a dimension of `5` is a shift of `2`, and a shift of `-1`
is a shift of `4`:

```r
rray_roll(1:5, n = 7, axes = 1)
# [1] 4 5 1 2 3
```

A shift of `0`, or any multiple of `d`, leaves the axis unchanged.

### Values of `n`

- Integers, and doubles holding whole numbers. Doubles are cast with the
  existing lossless casts, so `1.5` is an error.

## `rray_roll()`

```r
rray_roll(x, ..., n, axes)
```

### Arguments

- `x`: an array or bare vector.

- `...`: must be empty. It forces `n` and `axes` to be named, as in

736	Both functions reduce a shift into `[0, d)` with one `static inline` helper in
737	`src/roll.c`:

740	static inline int rray_roll_shift(int n, int dimension) {

742	    return 0;
743	  }
744	
745	  int out = n % dimension;
746	
747	  if (out < 0) {
748	    out += dimension;
749	  }

758	### `rray_roll()` reuses the slice core
759	
760	A uniform roll of an axis is a slice of that axis with rotated locations.
761	`rray_slice()` already walks one table of one-based locations per axis, with
762	`NULL` meaning "the whole axis in order", and builds the result names from the
763	same tables. `rray_roll()` builds those tables and calls the core.
764	
765	#### Step 1: expose the slice core
766	
767	Split `rray_slice()` in `src/slice.c` at the point where every location table
768	is built. Everything after that point moves into a new function declared in
769	`src/slice.h`:
770	
771	```c
772	r_obj* rray_slice_unsafe(
773	  r_obj* x,
774	  const int* const* v_v_locations,
775	  r_obj* dimensions,
776	  r_ssize size
777	);
778	```
779	
780	- `x` is a validated array.
781	
782	- `v_v_locations` holds one entry per axis of `x`. Each is `NULL` or a table of
783	  one-based locations of length `dimensions[axis]`, possibly containing
784	  `NA_integer_`.
785	
786	- `dimensions` is the output dimensions, poked onto the result as is.
787

791	existing typed cores, pokes the dimensions, and builds names with
792	`rray_slice_names()`. "Unsafe" follows vctrs' `vec_slice_unsafe()`: it trusts
793	its inputs.

796	checked size, then calls `rray_slice_unsafe()`. This step changes no behavior,
797	and the existing slice tests cover it.

802	check_unclassed(x)

Fixed in the plan

  1. Missing protection for x. For a bare vector, arg_as_array() returns a newly built array, and both functions allocate again before they last use x. The pseudocode now protects x, axes, n, and indices with KEEP(), and the protection review says so.

The plan now checks n's shape up front with check_broadcastable(), which allocates nothing and gives the same error messages. Expanding n and building the shift table now happen only when x isn't empty. The lane counts are also computed only then, so they can't overflow.

  3. Logical n is accepted. arg_as_bare_integer() turns TRUE into 1. axes and times already accept logicals this way, so the plan now documents it rather than rejecting it. It also states the integer range, -2147483647 to 2147483647.

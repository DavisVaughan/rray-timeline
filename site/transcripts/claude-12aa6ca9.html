What was wrong with v x group?

Claude

Nothing was wrong with v_x_group itself. It just couldn't live in the shared loop without knowing its type.

The pointer's type differs between the two variants:

  • Atomic: const CTYPE* v_x_group, for example const int*.

  • Barrier: r_obj* const* v_x_group, a pointer to constant r_obj* slots, which is what r_chr_cbegin() and r_list_cbegin() return.

A shared RRAY_ROLL_EACH_FILL_LOOP(POKE) has no CTYPE, so it can't declare that pointer. Passing CTYPE in doesn't fix it either. With CTYPE = r_obj*, const CTYPE* expands to const r_obj**, which puts the const in the wrong place, so it doesn't match r_obj* const*.

There are ways to keep it, none worth it in my view:

  • Pass the full pointer type as a macro argument, such as const int* or r_obj* const*. That works, but it adds a parameter just to name one local.

  • Use __typeof__(v_x). It's a GNU extension, not standard C, so it's best avoided in a package.

Indexing v_x by offset (x_start + source * block_size + i) makes the loop work for any element type with nothing extra. The work per element is the same: the compiler turns v_x + x_start into a base address either way. If you'd rather keep the v_x_group name, the pointer type argument is the way to do it.

Don’t change anything in the actual code yet, but trying to internally broadcast n would probably make things too messy, right?

Claude

Yes, mostly, though there is a middle ground that stays fairly tidy.

Why reading n with strides inside the loop is messy: the fill loop runs group, then j (along axis), then i. Here i flattens every axis before axis, and group flattens every axis after it. To read n in place, you'd need a strided iterator stepping through n's point for both of those flattened ranges. The i part sits in the hottest loop and would restart on every j. Doing that in the shared POKE loop macro is where it gets ugly.

The tidy version: keep a scratch buffer of block_size ints. At the top of each group, fill it once from n using strides, which is one small strided loop. Then run the existing j and i loops unchanged, with the buffer standing in for v_n_group. The fill macros wouldn't change. The new work is the stride setup plus that per-group fill.

What it would save: one allocation of size(x) / axis_dimension ints, the broadcast n. Two things limit how much that matters:

  • When n already has the full broadcast shape, rray_broadcast() returns it without copying, so there is nothing to save.

  • When it does allocate, the result is never bigger than x measured in ints, and usually much smaller, since it has no extent along axis.

The case that really benefited was an empty axis with huge other dimensions, and we just decided not to support that.

So I'd leave it. It's a real but bounded memory saving, paid for with a second iteration scheme. I'd only revisit it if profiling shows the broadcast n actually costs something.

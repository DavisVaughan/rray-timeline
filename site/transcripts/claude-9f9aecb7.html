rray_mean() adds up integers and logicals in an int64_t instead of a double, so the sum is exact. Floating point only comes in at the last step, when the sum is divided by the count. The code is all in src/reduce-mean.c.

Why not sum in a double

A double stores every integer exactly only up to 2^53. Above that, each += can round. An int64_t sum never rounds, and integer adds in a tight loop are also cheaper than double adds.

The two limits

#define RRAY_MEAN_INT64_MAX_COUNT ((r_ssize) 1 << 32)
#define RRAY_MEAN_INT64_MAX_EXACT ((int64_t) 1 << 53)

MAX_COUNT (2^32) keeps the sum from overflowing. Each integer is at most about 2^31 in size, so 2^32 of them add up to at most 2^63, which still fits in int64_t. If a single output cell has more than 2^32 inputs, rray_mean_int() switches to rray_mean_int_fallback(), which sums in a double the old way. Base R's sum() uses the same idea: a 64-bit sum (isum() in summary.c) that moves to irsum() before it can overflow.

Logicals don't need this check. Each value is 0 or 1, so the sum can never be larger than the count.

MAX_EXACT (2^53) controls how rray_mean_int64() (src/reduce-mean.c:621) does the division:

if (-MAX_EXACT <= sum && sum <= MAX_EXACT) {
  return (double) sum / count;
}
return (double) (sum / count) + (double) (sum % count) / count;

  • Small sums (|sum| <= 2^53): the cast to double is exact, so sum / count rounds only once.

  • Large sums: casting sum to double would already round, and then the division rounds again. So the code splits the sum into a whole part and a remainder first, both in integer math:

    • The whole part sum / count is no bigger than about 2^31, so it fits in a double exactly.
    • The remainder is smaller than count, which is at most 2^32, so it also fits exactly.

    Only rem / count and the final add can round. That isn't guaranteed to be perfectly rounded, but it is much closer than the direct way.

Here is a case where it matters: sum = 2^53 + 1, count = 3, and the true mean is the whole number 3002399751580331.

  • Direct: the cast rounds sum to 2^53. Dividing by 3 gives ...330.5, which is wrong.

  • Split: the whole part is ...331 and the remainder is 0, so the result is exact.

A sum this large only needs about 4 million integers near INT_MAX in one cell, so the large-sum path can really be reached for integer input. For logicals, the sum is at most the count, so it would need more than 2^53 elements. In practice logicals always take the small-sum path.

Negative sums work too. In C, / rounds toward zero and % keeps the sign of sum, so the two parts add back up correctly. For example, -7 / 2 = -3 and -7 % 2 = -1, which gives -3 + -0.5 = -3.5.

Handling NA

An int64_t can't hold NA, so the main loop adds 0 for an NA and sets a flag:

const bool na = x_elt == na_lgl;
sum += na ? 0 : x_elt;
any_na |= na;

After dividing, if any_na is set, a second pass (rray_mean_lgl_propagate_na() or rray_mean_int_propagate_na()) goes over the input again and writes NA_real_ into every output cell that had an NA. When there are no NAs, which is the common case, this costs one OR per element and no second pass.

Logicals get their own propagate helper, separate from the integer one, because logical and integer NA are different types even though they hold the same value.

na_rm = TRUE

This version doesn't need the NA pass. It keeps a count for each output cell in the counts buffer, skips NAs while summing, and then calls rray_mean_int64(v_sums[i], v_counts[i]). A cell whose inputs are all NA has a count of 0, so the result is NaN, the same as mean(numeric(0)).

What commit 67fe5b1 changed

Before this commit, the logical kernels summed in a double and relied on NA turning into NaN as it flowed through the sum. The commit made them work like the integer kernels from the commit before it (cd9aac3): an int64_t sum, a separate NA pass, and the shared rray_mean_int64(), which moved up next to rray_mean_count().

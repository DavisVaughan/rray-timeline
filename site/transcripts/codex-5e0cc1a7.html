How rray_add() could double dispatch on classes like vctrs

Codex · Sep 10, 2026 · 2 prompts · 4 replies · didn't ship

Sep 10, 2026, 20:10 UTC

Davis

Eventually we’ll want to make rray_add and other arithmetic functions generic. Ignore the plan for this for now. How might you do it? The idea is that we’d want to double dispatch on x and y so the combination “add” on x and y must be explicitly opted in to. But there should be a way to then use our fast native implementation on the underlying storage types, and then the user should have a chance to recreate their original class (if necessary) from the output.

Codex

I’ll trace the current arithmetic path and compare it with the closest vctrs dispatch patterns. Then I’ll sketch a protocol that keeps dispatch separate from the native storage kernel and class restoration.

r_obj* rray_binary_arithmetic(
  r_obj* x,
  r_obj* y,
  rray_binary_arithmetic_switch_fn fn_switch,
  struct rray_arg* x_arg,
  struct rray_arg* y_arg,
  struct r_lazy error_call
) {

  check_unclassed(y, y_arg, error_call);

  y = KEEP(arg_as_array(y, y_arg, error_call));

  const rray_binary_arithmetic_fn fn =
    fn_switch(x, y, x_arg, y_arg, error_call);

  r_obj* x_dimensions = r_dim(x);
  r_obj* y_dimensions = r_dim(y);

  const int* v_x_dimensions = r_int_cbegin(x_dimensions);
  const int* v_y_dimensions = r_int_cbegin(y_dimensions);

  const int x_dimensionality =
    rray_dimensionality_from_dimensions(x_dimensions);
  const int y_dimensionality =
    rray_dimensionality_from_dimensions(y_dimensions);

  r_obj* dimensions = KEEP(rray_dimensions2(
    v_x_dimensions,
    x_dimensionality,
    v_y_dimensions,
    y_dimensionality,
    x_arg,
    y_arg,
    error_call
  ));
  const int* v_dimensions = r_int_cbegin(dimensions);
  const int dimensionality = rray_dimensionality_from_dimensions(dimensions);

  const r_ssize size = rray_size_from_dimensions(v_dimensions, dimensionality);

  struct rray_iterator2 it;
  rray_iterator2_init(
    &it,
    size,
    v_dimensions,
    dimensionality,
    v_x_dimensions,
    x_dimensionality,
    v_y_dimensions,
    y_dimensionality
  );

  r_obj* out = KEEP(fn(x, y, size, &it, error_call));
  r_attrib_poke_dim(out, dimensions);

  r_obj* out_names = KEEP(rray_broadcast_names2(x, y, dimensions));

  if (out_names != r_null) {
    r_attrib_poke_dim_names(out, out_names);
  }

  FREE(5);
  return out;
}

I would use vctrs-style nested S3 dispatch, followed by a deliberately non-generic native helper. The pair method grants permission, the native helper performs the calculation, and the pair method decides how to restore the result.

rray_add <- function(x, y) {
  if (!is.object(x) && !is.object(y)) {
    return(rray_add_base(x, y))
  }

  UseMethod("rray_add", x)

A class author would provide the second dispatch:

rray_add.quantity <- function(x, y) {
  UseMethod("rray_add.quantity", y)
}

rray_add.quantity.default <- function(x, y) {
  stop_incompatible_add(x, y)
}

rray_add.quantity.quantity <- function(x, y) {
  check_compatible_units(x, y)

  out <- rray_add_base(x, y)

  vec_restore(out, x)
}

This has the desired properties:

  • quantity + quantity exists only because rray_add.quantity.quantity() opts into it.
  • quantity + duration remains an error unless someone defines rray_add.quantity.duration().
  • The reverse direction is separate. rray_add.duration.quantity() must also exist if it is valid.
  • A method can restore from x, restore from y, construct a different class, or leave the result bare.

For interoperability with bare inputs, the class author could explicitly provide methods such as:

rray_add.quantity.numeric <- function(x, y) {
  out <- rray_add_base(x, y)
  vec_restore(out, x)
}

rray_add.default.quantity <- function(x, y) {
  out <- rray_add_base(x, y)
  vec_restore(out, y)
}

The exact base-type bridge may need methods for numeric, integer, array, and similar implicit S3 classes. I would keep those explicit rather than providing a permissive fallback.

rray_add_base() would be the extension API around the existing fast implementation:

rray_add_base <- function(x, y) {
  .Call(ffi_rray_add_base, x, y, environment())
}

Its contract would be narrow:

  • Do no S3 dispatch.
  • Treat x and y according to their underlying R storage types.
  • Perform the existing broadcasting, casting, names handling, and native loop.
  • Ignore their classes.
  • Return a bare array.
  • Never restore a class automatically.

For an ordinary atomic S3 class, the C code can read the storage directly without first copying through vec_data(). Classes with a different proxy representation can extract it themselves:

out <- rray_add_base(vec_data(x), vec_data(y))

On the C side, I would split the current path at check_unclassed():

  1. The ordinary bare-array entry point remains strict.
  2. The extension entry point skips the class check.
  3. Both call the same rray_binary_arithmetic() machinery beneath that check.

I would use vec_restore() as the default reconstruction tool rather than inventing another restoration generic. It already has the right contract: the native result supplies the new storage, dimensions, and names, while the original object supplies its class and other attributes. When the result class depends on both operands, such as multiplication of units, the pair method can call a constructor instead.

The important boundary is that rray_add_base() does not itself authorize arithmetic. Only a concrete pair method should be able to reach it. I would also keep separate generics for add, subtract, multiply, and so on. That makes permission operation-specific, so defining multiplication for two classes does not accidentally authorize addition.

  rray_add_base(x, y, .to = x)
}

Conceptually, rray_add_base() would:

  1. Access the underlying storage without dispatching again.
  2. Run rray’s native broadcasting and addition.
  3. Produce the dimensions and names itself.
  4. Restore the result with vec_restore(out, .to).
  5. Check that restoration did not change structural properties such as size and dimensions.

The method author decides only:

  • Whether the pair is meaningful.
  • Whether either operand needs conversion.
  • What the output prototype is.

For a result that should be bare:

rray_add_base(x, y)

For a result that retains the left class:

rray_add_base(x, y, .to = x)

For a result with metadata derived from both inputs:

to <- new_quantity_ptype(unit = common_unit(x, y))
rray_add_base(x, y, .to = to)

For operations where the output represents something different:

to <- new_quantity_ptype(unit = multiply_units(x, y))
rray_multiply_base(x, y, .to = to)

This feels closer to why vctrs is pleasant. A correct method is short and mostly declarative. Authors do not have to reproduce broadcasting, names handling, storage promotion, native invocation, or reconstruction mechanics.

There should still be hard errors by default:

rray_add.quantity.default <- function(x, y) {
  stop_incompatible_add(x, y)
}

I would avoid any default method that says “both objects have numeric storage, so addition is probably fine.” Numeric storage is an implementation detail, not permission to add the classes.

There is a possible stronger design where the double-dispatch method returns a calculation plan:

rray_add_plan.quantity.quantity <- function(x, y) {
  rray_arith_plan(
    x = x,
    y = vec_cast(y, x),
    to = x
  )
}

Then rray_add() would execute the plan itself. That gives rray even more control, but it also creates a new abstraction that might become awkward for unusual classes. I would not start there.

The smaller vctrs-like design seems like the right balance:

  • Pair methods explicitly authorize semantics.
  • vec_cast() handles required conversions.
  • rray_add_base() handles array mechanics.
  • vec_restore() handles reconstruction.
  • The default is always incompatibility.
  • Authors can violate the contract, as with any S3 method, but the correct path is the shortest and easiest one.

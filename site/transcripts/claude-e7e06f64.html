static rray_reduce_fn rray_sum_switch(
  r_obj* x,
  bool na_rm,
  struct rray_arg* arg,
  struct r_lazy error_call
) {
  switch (rray_typeof(x)) {
  case RRAY_TYPE_logical:
    return na_rm ? rray_sum_lgl_na_rm : rray_sum_lgl;
  case RRAY_TYPE_integer:
    return na_rm ? rray_sum_int_na_rm : rray_sum_int;
  case RRAY_TYPE_double:
    return na_rm ? rray_sum_dbl_na_rm : rray_sum_dbl;
  case RRAY_TYPE_complex:
    return na_rm ? rray_sum_cpl_na_rm : rray_sum_cpl;

  case RRAY_TYPE_character:
  case RRAY_TYPE_raw:
  case RRAY_TYPE_list:
    stop_unsupported_reduce("sum", x, arg, error_call);

  case RRAY_TYPE_scalar:
    stop_scalar_input(x, arg, error_call);
  }

  r_stop_unreachable();
}

Why clang won't vectorize it

Running clang's vectorizer report (-Rpass-missed=loop-vectorize) on src/reduce-sum.c shows both int loops (lines 97 and 113) rejected with "could not determine number of loop iterations".

The cause isn't really NA stopping the loop early. The int loop never breaks on NA. There are two blockers:

  1. check_sum_int_overflow() calls r_abort() inside the loop. A call that never returns is a way out of the middle of the loop, so clang can't know how many iterations will run. This is the one named in the report.

  2. Each step branches on the running total. rray_sum_int_one() checks out == NA and x == NA, and then does the overflow check. Every element depends on the previous result through those branches.

What I suggest

I wrote the kernels as a standalone C benchmark with the same data and flags:

The new kernel does three things:

  1. Add into an int64_t, and check overflow once per output at the end. The 64-bit total can't overflow. Arrays can't be long vectors, so there are fewer than 2^31 elements, each smaller than 2^31 in size, which keeps the total under 2^62. This holds even when NA (INT_MIN) gets added in. So the loop needs no overflow check at all.

  2. Track NA with a flag that never branches: any_na |= elt == NA_INTEGER. If the flag is set at the end, rerun the current scalar kernel. That is the rare case, and it keeps today's NA behavior exactly.

  3. For na_rm, use acc += elt == NA_INTEGER ? 0 : elt. clang turns that into a vector select, with no branch.

The core loop:

int64_t acc = 0;
bool any_na = false;
for (r_ssize i = 0; i < n; ++i) {
  const int elt = v_x[i];
  any_na |= elt == r_globals.na_int;
  acc += elt;
}

Changes this needs in RRAY_REDUCE

Right now ONE(out, x) returns the output's own C type straight into v_out. To support the new kernel, the macro needs:

  • A separate accumulator type (int64_t for int sum) and a scratch buffer of out_size elements. A raw vector under KEEP() would work.

  • A finish step that checks overflow and narrows each total to int.

  • A way for the kernel to report "saw NA, use the fallback".

Updating the running total directly in v_out[out_loc] is fine. I tested that too, and clang still keeps it in a register because the buffer and v_x have different types.

The other types

  • Logical sum: same fix, but an int total is enough because it can't overflow. Only the NA branches need to go.

  • Double sum: the axis 2 case (out_run_stride == 1) would vectorize if the ISNAN() branches became a plain out + x (NaN carries through the addition), with the NA-over-NaN rule fixed in a fallback pass when a result is NaN. The full sum won't vectorize at -O2 whatever you do, because reordering double additions changes the result. Base R's double sum is scalar for the same reason.

You're right, and I was wrong. Arrays can be long vectors. Only each dimension has to fit in an int.

Evidence

  • dimgets() in src/main/attrib.c, which backs dim<-, multiplies the dimensions into an R_xlen_t total and compares that to xlength(vec). The dimensions are ints, but the length isn't limited to one.

  • src/main/array.c has LONG_VECTOR_SUPPORT branches for matrix() and array() that compute the length as (R_xlen_t) nr * nc.

  • rray4 accepts long arrays too. rray_size_from_dimensions_checked() in src/size.c bounds the size by R_SSIZE_MAX, not INT_MAX.

I got the idea from the comment at src/reduce-sum.c:197, which makes the same claim, and I didn't check it.

What this breaks in my suggestion

My bound of "under 2^62, so an int64_t can't overflow" is wrong. The real bound depends on how many elements feed each output:

  • Each element is at most 2^31 in size, so an int64_t total is only safe for fewer than 2^32 elements per output (about 4.3 billion).

  • With long arrays, one output can get more than that. For example, a full sum of a 5-billion-element int array.

Revised fix

The count of elements per output is known before the loop starts: size / out_size. So:

  • If it's under 2^32, use the fast vectorized int64_t kernel. The per-element overflow check can't be needed, so this stays exact.

  • Otherwise, use the current checked scalar kernel. That only happens for 16+ GB int arrays, where speed matters much less.

This keeps the fast path free of any overflow check, and needs no chunking inside the loop.

A bug in the current code

The same wrong premise causes a real bug today. rray_sum_lgl_one() skips the overflow check because of that comment, but an output that receives more than INT_MAX TRUE values will overflow int. That's signed overflow, which is undefined behavior in C, and in practice the sum wraps around silently. Why axis 2 stays slow

The nested reducer computes one output at a time, and its inner loop walks the axes being summed. That loop reads memory one element after another only when axis 1 is one of those axes.

When axis 1 is kept, the inner loop jumps 10,000 elements between reads. clang can't vectorize that, and every read misses the cache.

The flat reducer walks x in memory order no matter which axes you sum. That's why my earlier flat prototype with an int64_t buffer did the axis 2 case in 1.14 ms, and nested can't match that.

What nested gets right

  • The state lives in plain locals: int64_t sum and bool any_na. There's no scratch buffer and no rescan when there's NA, so NA behavior is exact on the first pass.

  • It needs no changes to either macro. The kernel is just:

    RRAY_REDUCE_INNER(int, {
  any_na |= x_elt == r_globals.na_int;
  sum += x_elt;
});

  • The long-array overflow check gets simple. rray_strided_iterator_plan_size(inner_plan) is the count of elements per output, so the kernel can use the checked scalar loop when that count is 2^32 or more.

My recommendation

Pick the reducer at run time:

  • Axis 1 summed (full sums, colSums()-style): use nested. This is about 12x faster and needs no macro changes.

  • Axis 1 kept (rowSums()-style): use the flat reducer with a wider accumulator. This still needs the RRAY_REDUCE change I described before, but it's the only way to beat base R there.

If you want the smallest step first, going nested for int and logical sum already fixes the full-sum case you reported. The axis-2 case would stay slightly slower than base R until the flat reducer gets the wider accumulator.

One side note: mean's long double total is plain double on Apple silicon, which is part of why its na_rm loops vectorize here. On x86, long double is 80 bits and those loops won't vectorize, so don't expect the same speed there.

You don't need the buffer. The running total can stay in v_out itself, and the kernel still vectorizes. It's slower than the buffer version but still about 3x faster than today, and it beats base R.

The kernel

For the axis-1-kept case (out_run_stride == 1), each step does: widen, add, check, narrow.

const int o = v_out[j];
const int e = v_x[i];
const bool na = (o == NA) | (e == NA);
const int64_t s = (int64_t) o + e;
overflow |= !na & ((s > INT_MAX) | (s < -INT_MAX));
v_out[j] = na ? NA : (int) s;

  • overflow is checked once per run, and r_abort() happens outside the loop.

  • NA stays sticky through a select, not a branch.

  • Totals are checked at every step, in the same order as today, so results and errors are identical to the current kernel. I compared all outputs, with and without NA.

  • Since every step is checked, long arrays are no problem here.

    const int* col = x + (int64_t) c * ROWS;
    bool overflow = false;
    for (int j = 0; j < ROWS; ++j) {
      const int o = out[j];
      const int e = col[j];
      const bool na = (o == NA) | (e == NA);
      const int s = (int) ((unsigned) o + (unsigned) e);
      overflow |= !na & ((((o ^ s) & (e ^ s)) < 0) | (s == NA));
      out[j] = na ? NA : s;
    }
    if (overflow) die();
  }
}

How the check works:

  • (unsigned) o + (unsigned) e wraps on overflow instead of being undefined behavior. The cast back to int is implementation-defined rather than undefined. clang and gcc both define it as a two's complement wrap.

  • ((o ^ s) & (e ^ s)) < 0 is true only when o and e have the same sign and s has the other sign. That is exactly when a signed addition overflows. For example, INT_MAX + 1 wraps to INT_MIN: both inputs are positive and the result is negative.

  • s == NA catches a total that lands exactly on INT_MIN. That isn't an overflow in C, but it would be read back as NA. It mirrors the -INT_MAX lower bound in check_sum_int_overflow().

  • !na & ignores lanes where either value is already NA, so a lane holding NA can't trigger a false overflow.

static inline int one_branchless(int out, int x, bool* error) {
  const bool na = (out == na_global) | (x == na_global);
  const int64_t sum = (int64_t) out + x;
  *error |= !na & ((sum > INT_MAX) | (sum < -INT_MAX));
  return na ? na_global : (int) sum;
}

static inline int one_branchy(int out, int x, bool* error) {
  if (out == na_global || x == na_global) {
    return na_global;
  }
  const int64_t sum = (int64_t) out + x;
  *error |= (sum > INT_MAX) | (sum < -INT_MAX);
  return (int) sum;
}

__attribute__((noinline)) int run_branchless(const int* x, int n, bool* error) {
  int out = 0;

  return out;
}

1. Leaving the extra arguments out isn't portable C before C23. The unchecked callers (prod, logical, the double and complex sums) would pass nothing for .... The two usual tricks for that both warn under -pedantic in C99, C11 and C17. I checked with clang 17:

Your ~/.R/Makevars sets -pedantic, and some CRAN check setups use it too, so every use of the unchecked form would warn.

2. Passing extra arguments to the kernel isn't enough. The checked form also needs to declare bool error and to run if (error) STOP(); after each run. __VA_ARGS__ could hand &error to the kernel, but it can't add that per-run code unless the caller passes a statement as an argument. That's what the current RRAY_REDUCE_LOOP() does internally, just without exposing it.

An option that gives you one macro

Give every RRAY_REDUCE() kernel a bool* error parameter, and make RRAY_REDUCE() always declare the flag and check it after each run:

static inline double rray_prod_dbl_one(double out, double x, bool* error) {
  ...
}

  • Kernels that can't fail never write to error. After inlining, clang sees the flag is always false and removes the check, so they should cost nothing. I'd confirm that with a benchmark.

  • That drops RRAY_REDUCE_CHECKED(), and RRAY_REDUCE_LOOP() can fold back into RRAY_REDUCE().

  • The macro also needs something to call on error. It could take a STOP argument, which non-failing reducers pass as r_stop_unreachable.

  • The cost: 12 prod, logical, double and complex sum kernels gain a parameter they never use.

The check also doesn't have to run after every run. Checking once at the end gives the same results and the same error:

  • The flag only goes from false to true, so an overflow anywhere is still caught.

  • After an overflow, the loop keeps adding garbage totals, but that's harmless. The addition is 64-bit, and narrowing an out-of-range value to int is implementation-defined, not undefined. We abort at the end anyway.

  • The only cost is finishing the loop before erroring, and that only happens on the error path.

Because summing along axis 1 builds one total, one element at a time, and checking that total after every step forces that order. The vectorizer report for the axis 1 loop says:

loop not vectorized: value that could not be identified as reduction is used outside the loop

The value it means is out_elt, the running total.

Why axis 2 vectorizes and axis 1 doesn't

  • Along axis 2, one run of the loop touches many different outputs, one element each. Each output's total only depends on its own earlier value, so clang can update 16 of them at once. Each lane still does exactly the same steps as the scalar code.

  • Along axis 1, one run of the loop feeds a single output. To vectorize that, clang would have to split the total into 16 partial totals and add them together at the end. It only does that for operations it recognizes as reorderable, like a plain acc += x. Our step isn't one: it checks the total for NA, adds in 64 bits, and narrows back to int every time.

Clang is right to refuse

Splitting the total changes which intermediate totals exist, and we check every intermediate total. Take c(INT_MAX, 1L, -1L):

  • One at a time: INT_MAX + 1 overflows at step 2, so we error.

  • Split in two: one partial total is INT_MAX + (-1) and the other is 1. Neither overflows, and the result is INT_MAX.

So as long as every step is checked, this loop has to run one element at a time. The 10% gain along axis 1 only comes from removing the r_abort() call and the overflow branches from the loop. It can't vectorize.

Getting it fast without changing results

There's a check that gives the same errors and does vectorize. Along with the 64-bit total, also sum the absolute values:

sum += x_elt;
abs_sum += x_elt < 0 ? -(int64_t) x_elt : x_elt;
any_na |= x_elt == r_globals.na_int;

Both sums use plain 64-bit adds that can be reordered freely, so clang can vectorize them. If |starting total| + abs_sum <= INT_MAX, then no intermediate total could have left the int range, whatever the order. The vectorized result is then exactly what the step-by-step loop would give: NA if any_na is set, otherwise sum. If the bound fails, rerun that run with the current step-by-step loop. That keeps today's results, including overflow before NA and NA before overflow.

  • The bound only fails for totals near 2 billion, where the rerun costs one extra pass.

  • It fits the 64-bit sums: one axis 1 run is at most one axis of the array, so fewer than 2^31 elements, and each absolute value is at most 2^31.

  • For na_rm, both sums skip NA elements, and there's no any_na.

  • It's only for the out_run_stride == 0 loop, which RRAY_REDUCE() doesn't support today. It would need a separate fast path for int and logical sums.

## The user base is thin

- `units` arrays fit well. The `units` attribute does not depend on length.

- A generic "array wrapper" class fits well.

- `Matrix` sparse matrices do not fit. The proxy would have to densify, silently

# Why `main` doesn't vectorize

On `main`, clang rejects the int sum loops with "could not determine number of loop iterations".

- `check_sum_int_overflow()` called `r_abort()` inside the loop. A call that never returns is an exit from the middle of the loop, so clang can't know how many times the loop runs.

- The NA and overflow checks were branches on the running total at every step.

Base R's `isum()` in `src/main/summary.c` is also scalar. It is faster than `main` because it adds into a 64-bit `LONG_INT` and only checks for overflow now and then, not every step.

# What the branch does

## `src/reduce.h`

`RRAY_REDUCE()` gains a `ONE_ARGS` parameter, copying the pattern in `src/binary.h`:

```c
#define RRAY_REDUCE_ARGS(...) , __VA_ARGS__
#define RRAY_REDUCE_NO_ARGS
```

The kernel is called as `ONE(out, v_x[i] ONE_ARGS)`. This is portable C99 and doesn't warn under `-pedantic`, because `...` is never empty. Only the `ONE_ARGS` argument expands to nothing, and C99 allows empty macro arguments.

When `out_run_stride == 0` (one output per run), the loop now keeps the total in a local `out_elt` and writes it to `v_out` once per run. Without it, the full sum took 11.4 ms. clang can't keep the total in a register by itself because `v_x` and `v_out` are both `int*` and might overlap.

That is the whole diff to `reduce.h`. All `RRAY_REDUCE()` callers in `reduce-prod.c`, `reduce-logical.c` and the double and complex sums pass `RRAY_REDUCE_NO_ARGS`.

## `src/reduce-sum.c`

Logical and integer sums share two kernels. The logical kernels are gone.

```c
static inline int rray_sum_int_one(int out, int x, bool* error) {
  if (out == r_globals.na_int) {
    return r_globals.na_int;
  }

  if (x == r_globals.na_int) {
    return r_globals.na_int;
  }

  const int64_t sum = (int64_t) out + x;
  *error |= (sum > INT_MAX) | (sum < -INT_MAX);

  return (int) sum;
}
```

`rray_sum_int_one_na_rm()` is the same, but returns `out` when `x` is NA.

Each checked reducer wraps an `_impl` that runs the macro. The caller checks the flag afterwards, because the macro ends with `return out;`:

```c
static r_obj* rray_sum_int(
  r_obj* x,
  r_ssize out_size,
  const struct rray_strided_iterator_plan* plan
) {
  bool error = false;
  r_obj* out = rray_sum_int_impl(x, out_size, plan, &error);

  if (error) {
    stop_sum_int_overflow();
  }

  return out;
}
```

There are four of these: `rray_sum_lgl()`, `rray_sum_lgl_na_rm()`, `rray_sum_int()` and `rray_sum_int_na_rm()`. `stop_sum_int_overflow()` calls `r_abort("Integer overflow.")`, so the error text and snapshots are unchanged.

Checking once at the end gives the same results as checking every step. The flag only goes from `false` to `true`. After an overflow, the loop keeps adding garbage, but that's harmless: the add is 64-bit, and narrowing an out-of-range value to `int` is implementation-defined, not undefined. We abort at the end anyway.

The vectorizer report shows all four `_impl` axis 2 loops at width 16. Writing the flag through `bool*` doesn't block vectorization.

## Behavior

Results and errors are the same as on `main`. The total is still checked at every step, in the same order.

- An NA before an overflow gives NA: `c(NA, INT_MAX, 1L)` returns `NA`.

- An overflow before an NA errors: `c(INT_MAX, 1L, NA)` errors.

It also fixes a bug on `main`. `rray_sum_lgl_one()` never checked for overflow, based on a comment saying arrays can't be long vectors. They can: `dimgets()` in R's `src/main/attrib.c` computes the total length as `R_xlen_t`, and rray4 bounds sizes by `R_SSIZE_MAX` in `rray_size_from_dimensions_checked()`. An output receiving more than `INT_MAX` `TRUE` values overflowed `int`, which is undefined behavior. Logical sums are now checked like integer sums.

# Designs we rejected, and why

## A one-shot 64-bit buffer with the checks moved out of the loop

This means adding into an `int64_t` scratch buffer of `out_size` elements, tracking NA with a flag that never branches, and checking overflow once per output at the end. Axis 2 ran in 1.14 ms, the fastest option we found.

Rejected because it allocates a buffer that can be large.

It also relied on a wrong premise, that arrays can't be long vectors. With long arrays, a 64-bit total can overflow once one output gets 2^32 or more elements.

## The nested reducer (`RRAY_REDUCE_OUTER()` / `RRAY_REDUCE_INNER()`)

The total lives in a local `int64_t`, like `src/reduce-mean.c`. Prototyped:

| Case | Flat on `main` | Nested |
|---|---|---|
| Full sum | 8.46 ms | 0.73 ms |
| Sum along axis 1 | 8.55 ms | 0.74 ms |
| Sum along axis 2 | 8.50 ms | 7.33 ms |

It is fast only when axis 1 is summed. When axis 1 is kept, the inner loop jumps `nrow` elements between reads, so it can't vectorize and misses the cache.

It also checks overflow only on the final total, so `c(INT_MAX, 1L, -1L)` would return `INT_MAX` instead of erroring, like base R. That changes behavior, and it was never decided.

# Integer coordinate indexing plan

## Recommendation

Add one fully specified coordinate function and one directional one-axis
specialization:

```r
rray_index(x, ...)
rray_index_assign(x, ..., value)

rray_index_axis(x, i, ..., axis)
rray_index_assign_axis(x, i, ..., axis, value)
```

`rray_index()` requires exactly one integer coordinate array for every source
axis. The arrays broadcast to common dimensions and are read pointwise. The
common dimensions are the result dimensions.

`rray_index_axis()` accepts one integer array for the selected source axis and
supplies identity coordinates for every other axis. `i` must broadcast to the
dimensions of `x` outside `axis`. The result has the same dimensionality as
`x`, every unselected axis keeps its source dimension, and only the selected
axis can change.

Every source coordinate is explicit. Different partial indexing behaviors are
represented by shaping full coordinate arrays in different ways.

The complete family is:

| Operation | Read | Assign |
|---|---|---|
| Orthogonal subscripts | `rray_slice()` | `rray_slice_assign()` |
| One-axis subscript | `rray_slice_axis()` | `rray_slice_assign_axis()` |
| First axis subscript | `rray_slice_rows()` | `rray_slice_assign_rows()` |
| Second axis subscript | `rray_slice_columns()` | `rray_slice_assign_columns()` |
| One-axis coordinate array | `rray_index_axis()` | `rray_index_assign_axis()` |
| Full coordinate arrays | `rray_index()` | `rray_index_assign()` |
| Flat subscript or point matrix | `rray_extract()` | `rray_extract_assign()` |

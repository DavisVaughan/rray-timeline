# Rename the ALTREP wrapper to a view

After `plans/wrap.md` and `plans/attributes.md`, `r_wrap(x)` returns an
object that:

- shares the data of `x` and never copies it,

- is read only, since R always copies it before changing it,

- starts with no attributes, so the caller sets its own.

That is a read-only view, and "view" says so better than "wrapper" does. Base
R's own wrapper classes behave differently: they copy their data on the first
write and become the owner. Ours never does.

This plan renames everything. It is a pure rename: no behavior changes, apart
from the wording of a few internal error messages.

The work is one pull request. It lands after `plans/attributes.md`, and
assumes the tests that plan adds and renames are in place.

23	// ported over. Because of that, our `DATAPTR()` ALTREP methods must return a
24	// pointer even in the `writable` case, but we expect that R (and all packages)
25	// hold up their side of the bargain by only actually writing to this pointer
26	// when they fully own it or when there are `NO_REFERENCES()`, which won't be
27	// the case since we've used `MARK_NOT_MUTABLE()`. The `NO_REFERENCES()` case is

+// Create a read-only ALTREP view of an R object's data
+//
+// Useful when ONLY modifying the attributes of the new object, and NEVER the
+// underlying data.
+//
+// The ALTREP view itself is immediately marked as immutable with
+// `MARK_NOT_MUTABLE()`. This is extremely important! It ensures that R won't
+// ever ask for a writable `DATAPTR()` without first calling `Duplicate()`.
+//
+// Note that R will VERY often use `REAL()` instead of `REAL_RO()` when it only
+// needs a read-only pointer. This is due to `REAL_RO()` being a newer idea that
+// was only introduced with ALTREP, and a lot of historical code hasn't been
+// ported over. Because of that, our `DATAPTR()` ALTREP methods must return a
+// pointer even in the `writable` case, but we expect that R (and all packages)
+// hold up their side of the bargain by only actually writing to this pointer
+// when they fully own it or when there are `NO_REFERENCES()`, which won't be
+// the case since we've used `MARK_NOT_MUTABLE()`. The `NO_REFERENCES()` case is
+// relevant for `x + y + 1` where R will attempt to reuse `x + y`'s temporary

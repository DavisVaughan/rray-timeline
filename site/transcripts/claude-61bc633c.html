1	# Rolling plan
2	
3	## Recommendation
4	
5	Add two functions:
6	
7	```r
8	rray_roll(x, ..., n, axes)
9	rray_roll_each(x, ..., n, axis)
10	```
11	
12	Both move elements along an axis. An element pushed off one end comes back on
13	the other.
14	
15	- `rray_roll()` rolls one or more axes, with one shift per axis. Every lane
16	  through an axis moves by the same amount, so each output position has exactly
17	  one source position, and names roll with the data.
18	
19	- `rray_roll_each()` rolls one axis, with one shift per lane. Lanes can move by
20	  different amounts, so an output position can come from different source
21	  positions in different lanes. Names on the rolled axis are always dropped.
22	
23	The split mirrors pairs the package already has:
24	
25	| Every lane moves together | Each lane moves on its own |
26	|---|---|
27	| `rray_slice_axis()` | `rray_index_axis()` |
28	| `rray_rep()` | `rray_rep_each()` |
29	| `rray_roll()` | `rray_roll_each()` |
30	
31	The function decides what happens to names. The size or values of `n` never do.
32	A caller who wants names kept calls `rray_roll()`.
33	
34	## Terms
35	
36	- **Lane.** One run of elements along the rolled axis, with every other
37	  coordinate held fixed. For a matrix and `axis = 2`, each row is a lane. For
38	  dimensions `(A, B, C)` and `axis = 2`, there are `A * C` lanes, each of
39	  length `B`.
40	
41	- **Lane dimensions.** The dimensions of `x` with the rolled axis set to 1. For
42	  `(A, B, C)` and `axis = 2`, they are `(A, 1, C)`. There is one lane per
43	  element of an array with these dimensions.
44	
45	- **Shift.** The value of `n` for one lane or one axis. It can be negative,
46	  zero, or larger than the dimension.
47	
48	## Shared rules
49	
50	### Direction
51	
52	A positive shift moves elements toward higher positions, as in NumPy:
53	
54	```r
55	rray_roll(1:5, n = 2, axes = 1)
56	# [1] 4 5 1 2 3
57	```
58	
59	A negative shift moves them toward lower positions:
60	
61	```r
62	rray_roll(1:5, n = -1, axes = 1)
63	# [1] 2 3 4 5 1
64	```
65	
66	### Wrapping
67	
68	A shift is reduced modulo the dimension `d` of the rolled axis, into `[0, d)`:
69	
70	```text
71	k = n mod d
72	out[..., j, ...] = x[..., (j - k) mod d, ...]
73	```
74	
75	So a shift of `7` on a dimension of `5` is a shift of `2`, and a shift of `-1`
76	is a shift of `4`:
77	
78	```r
79	rray_roll(1:5, n = 7, axes = 1)
80	# [1] 4 5 1 2 3
81	```
82	
83	A shift of `0`, or any multiple of `d`, leaves the axis unchanged.
84	
85	### Values of `n`
86	
87	- Integers, and anything that casts losslessly to integer. Doubles holding
88	  whole numbers work and `1.5` is an error. Logicals work too, with `TRUE` as
89	  `1`, the same as `axes` and `times` accept them today.
90	
91	- Any sign and any magnitude within the R integer range, which is
92	  `-2147483647` to `2147483647`. `-2147483648` is reserved for `NA`, and a
93	  double outside the range fails the cast.
94	
95	- No missing values.
96	
97	- No classed objects.
98	
99	### Zero dimensions
100	
101	When the rolled axis has dimension 0, there is nothing to move. Every shift is
102	valid, and it is still validated. The result equals `x`, with the names rule of
103	the function applied.
104	
105	### Bare vectors
106	
107	`x` goes through `arg_as_array()`, so a bare vector is a one-dimensional array
108	and its names move to `dimnames`. The result is always an array.

112	```r
113	rray_roll(x, ..., n, axes)

117

So rray_roll() is the odd one out, and I agree it should be strictly increasing.

The reason: in rray_roll() the order of axes does not change the result. Rolling axis 1 then axis 3 is the same as rolling axis 3 then axis 1, and your own plan states that as an equivalence (plans/roll.md:674-679). Order only picks which n goes with which axis, and requiring sorted axes costs nothing there: rray_roll(x, n = c(1, -1), axes = c(3, 1)) is just rray_roll(x, n = c(-1, 1), axes = c(1, 3)). Contrast rray_move_axes(), where order genuinely changes what you get.

You also get a nicer error for free. Today axes = c(1, 1) says "must not contain 1 more than once"; sorted gives "must be in strictly increasing order", which covers duplicates and matches every other axes-taking function.

### Reproducing code example:
    
    import numpy as np
    import pandas as pd
    import datetime
    
    >>> np.array([1.0, 2.0, 3.0]) + datetime.datetime.now()
    ...
    TypeError: unsupported operand type(s) for +: 'float' and 'datetime.datetime'
    
    >>> np.array([1.0, 2.0, 3.0]) + pd.Timestamp("2021-01-01")
    ...
    TypeError: Concatenation operation is not implemented for NumPy arrays, use np.concatenate() instead. Please do not rely on this error; it may not be given on all Python implementations.

So for `datetime.datetime` object, this gives the expected TypeError. But for `pd.Timestamp` it gives a confusing error message.

I suppose the difference could stem from the fact that `pd.Timestamp` defines an `__array_priority__`. However, in this case it just returns `NotImplemented` when passed a float ndarray, so I would still expect to get the normal "unsupported operand type" TypeError.

(opening the issue here in numpy because the error message comes from numpy; of course it might also be that we need to change something in `Timestamp.__add__`, although as said above, it's returning `NotImplemented` in this case)

The problem is that nearly NumPy operation is valid on inputs with an arbitrary number of dimensions (even between arguments, with broadcasting). Giving up on shape checks would means we couldn't type ufuncs in a useful way, or catch the common errors with broadcasting. This would basically mean reserving shape/rank checks for the (many) applications and libraries that only use on particular ranks (e.g., vectors and matrices).

With regards to C++ libraries, Eigen at least does allow for either runtime and statically defined shapes. That said, I certainly would not bother with static/compile-time shapes on their own, because it is indeed rare that you know the exact shape of arrays before running a program. But with generics, we have the possibility of doing much more sophisticated pattern matching. This isn't feasible in C++, where you would need to use templates for every possible dimension size. In contrast, we can probably do something more sophisticated in Python to allow for typing shapes without enumerating all of them (similar to what you see in Haskell).

### Mechanism details and dynamic linking

The main part of the mechanism is that without NumPy needs to define a `void **PyArray_API` table for you to look up all functions. Depending on your macro setup, this takes different routes depending on whether :c:macro:`NO_IMPORT_ARRAY` and :c:macro:`PY_ARRAY_UNIQUE_SYMBOL` are defined:

  * If neither is defined, the C-API is declared to `static void **PyArray_API`, so it is only visible within the compilation unit/file using `#include <numpy/arrayobject.h>`.
  * If only `PY_ARRAY_UNIQUE_SYMBOL` is defined (it could be empty) then the it is declared to a non-static `void **` allowing it to be used by other files which are linked.
  * If `NO_IMPORT_ARRAY` is defined, the table is declared as `extern void **`, meaning that it must be linked to a file which does not use `NO_IMPORT_ARRAY`.

The `PY_ARRAY_UNIQUE_SYMBOL` mechanism additionally mangles the names to avoid conflicts.
    
    .. versionchanged::
        NumPy 2.1 changed the headers to avoid sharing the table outside of a
        single shared object/dll (this was always the case on Windows).
        Please see :c:macro:`NPY_API_SYMBOL_ATTRIBUTE` for details.
    
    

In order to make use of the C-API from another extension module, the :c:func:`import_array` function must be called. If the extension module is self-contained in a single .c file, then that is all that needs to be done. If, however, the extension module involves multiple files where the C-API is needed then some additional steps must be taken.

L123: cite73†https://mail.python.org/pipermail/numpy-discussion/2018-August/078493.html†mail.python.org L124: ## Abstractcite74†# L125: 
L126: We propose the `__array_function__` protocol, to allow arguments of NumPy functions to define how that function operates on them. This will allow using NumPy as a high level API for efficient multi-dimensional array operations, even with array implementations that differ greatly from `numpy.ndarray`.
L127: ## Detailed descriptioncite75†# L128: 
L129: NumPy’s high level ndarray API has been implemented several times outside of NumPy itself for different architectures, such as for GPU arrays (CuPy), Sparse arrays (scipy.sparse, pydata/sparse) and parallel arrays (Dask array) as well as various NumPy-like implementations in the deep learning frameworks, like TensorFlow and PyTorch.
L130: Similarly there are many projects that build on top of the NumPy API for labeled and indexed arrays (XArray), automatic differentiation (Autograd, Tangent), masked arrays (numpy.ma), physical units (astropy.units, pint, unyt), etc. that add additional functionality on top of the NumPy API. Most of these project also implement a close variation of NumPy’s level high API.
L131: We would like to be able to use these libraries together, for example we would like to be able to place a CuPy array within XArray, or perform automatic differentiation on Dask array code. This would be easier to accomplish if code written for NumPy ndarrays could also be used by other NumPy-like projects.
L132: For example, we would like for the following code example to work equally well with any NumPy-like array object:
L133: 
L134:     def f(x):
L135:         y = np.tensordot(x, x.T)
L136:         return np.mean(np.exp(y))
L137: 
L138: 
L139: Some of this is possible today with various protocol mechanisms within NumPy.
L140: 
L141:   * The `np.exp` function checks the `__array_ufunc__` protocol
L142: 
L143:   * The `.T` method works using Python’s method dispatch
L144: 
L145:   * The `np.mean` function explicitly checks for a `.mean` method on the argument
L146: However other functions, like `np.tensordot` do not dispatch, and instead are likely to coerce to a NumPy array (using the `__array__`) protocol, or err outright. To achieve enough coverage of the NumPy API to support downstream projects like XArray and autograd we want to support almost all functions within NumPy, which calls for a more reaching protocol than just `__array_ufunc__`.
L147: We would like a protocol that allows arguments of a NumPy function to take control and divert execution to another function (for example a GPU or parallel implementation) in a way that is safe and consistent across projects.
L148: ## Implementationcite76†# L149: 
L150: We propose adding support for a new protocol in NumPy, `__array_function__`.
L151: 
L152: This protocol is intended to be a catch-all for NumPy functionality that is not covered by the `__array_ufunc__` protocol for universal functions (like `np.exp`). The semantics are very similar to `__array_ufunc__`, except the operation is specified by an arbitrary callable object rather than a ufunc instance and method.
L153: 
L154: A prototype implementation can be found in cite77†this notebook†nbviewer.jupyter.org .
L155: Warning
L156: 
L157: The `__array_function__` protocol, and its use on particular functions, is experimental. We plan to retain an interface that makes it possible to override NumPy functions, but the way to do so for particular functions can and will change with little warning. If such reduced backwards compatibility guarantees are not accepted to you, do not rely upon overrides of NumPy functions for non-NumPy arrays. See “Non-goals” below for more details.
L158: 
L159: Note
L160: Dispatch with the `__array_function__` protocol has been implemented but is not yet enabled by default:
L161: 
L162:   * In NumPy 1.16, you need to set the environment variable `NUMPY_EXPERIMENTAL_ARRAY_FUNCTION=1` before importing NumPy to test NumPy function overrides.
L163: 
L164:   * In NumPy 1.17, the protocol will be enabled by default, but can be disabled with `NUMPY_EXPERIMENTAL_ARRAY_FUNCTION=0`.
L165: 
L166:   * Eventually, expect to `__array_function__` to always be enabled.
L167: ### The interfacecite78†# L168: 
L169: We propose the following signature for implementations of `__array_function__`:
L170: 
L171:     def __array_function__(self, func, types, args, kwargs)
L172: 
L173: 
L174:   * `func` is an arbitrary callable exposed by NumPy’s public API, which was called in the form `func(*args, **kwargs)`.
L175: 
L176:   * `types` is a cite79†collection†docs.python.org of unique argument types from the original NumPy function call that implement `__array_function__`.
L177:   * The tuple `args` and dict `kwargs` are directly passed on from the original call.
L178: 
L179: Unlike `__array_ufunc__`, there are no high-level guarantees about the type of `func`, or about which of `args` and `kwargs` may contain objects implementing the array API.
L180: As a convenience for `__array_function__` implementers, `types` provides all argument types with an `'__array_function__'` attribute. This allows implementers to quickly identify cases where they should defer to `__array_function__` implementations on other arguments. The type of `types` is intentionally vague: `frozenset` would most closely match intended use, but we may use `tuple` instead for performance reasons.
L181: In any case, `__array_function__` implementations should not rely on the iteration order of `types`, which would violate a well-defined “Type casting hierarchy” (as described in cite80†NEP-13 ).
L182: ### Example for a project implementing the NumPy APIcite81†# L183: 
L184: Most implementations of `__array_function__` will start with two checks:
L185: 
L186:   1. Is the given function something that we know how to overload?
L187: 
L188:   2. Are all arguments of a type that we know how to handle?
L189: If these conditions hold, `__array_function__` should return the result from calling its implementation for `func(*args, **kwargs)`. Otherwise, it should return the sentinel value `NotImplemented`, indicating that the function is not implemented by these types. This is preferable to raising `TypeError` directly, because it gives other arguments the opportunity to define the operations.
L190: There are no general requirements on the return value from `__array_function__`, although most sensible implementations should probably return array(s) with the same type as one of the function’s arguments. If/when Python gains cite82†typing support for protocols†www.python.org and NumPy adds static type annotations, the `@overload` implementation for `SupportsArrayFunction` will indicate a return type of `Any`.
L191: It may also be convenient to define a custom decorators (`implements` below) for registering `__array_function__` implementations.
L192: 
L193:     HANDLED_FUNCTIONS = {}
L194: 
L195:     class MyArray:
L196:         def __array_function__(self, func, types, args, kwargs):
L197:             if func not in HANDLED_FUNCTIONS:
L198:                 return NotImplemented
L199:             # Note: this allows subclasses that don't override
L200:             # __array_function__ to handle MyArray objects
L201:             if not all(issubclass(t, MyArray) for t in types):
L202:                 return NotImplemented
L203:             return HANDLED_FUNCTIONS[func](*args, **kwargs)
L204: 
L205:     def implements(numpy_function):
L206:         """Register an __array_function__ implementation for MyArray objects."""
L207:         def decorator(func):
L208:             HANDLED_FUNCTIONS[numpy_function] = func
L209:             return func
L210:         return decorator
L211: 
L212:     @implements(np.concatenate)
L213:     def concatenate(arrays, axis=0, out=None):
L214:         ...  # implementation of concatenate for MyArray objects
L215: 
L216:     @implements(np.broadcast_to)
L217:     def broadcast_to(array, shape):
L218:         ...  # implementation of broadcast_to for MyArray objects
L219: Note that it is not required for `__array_function__` implementations to include all of the corresponding NumPy function’s optional arguments (e.g., `broadcast_to` above omits the irrelevant `subok` argument). Optional arguments are only passed in to `__array_function__` if they were explicitly used in the NumPy function call.
L220: 
L221: Note
L222: Just like the case for builtin special methods like `__add__`, properly written `__array_function__` methods should always return `NotImplemented` when an unknown type is encountered. Otherwise, it will be impossible to correctly override NumPy functions from another object if the operation also includes one of your objects.
L223: ### Necessary changes within the NumPy codebase itselfcite83†# L224: 
L225: This will require two changes within the NumPy codebase:
L226: 
L227:   1. A function to inspect available inputs, look for the `__array_function__` attribute on those inputs, and call those methods appropriately until one succeeds. This needs to be fast in the common all-NumPy case, and have acceptable performance (no worse than linear time) even if the number of overloaded inputs is large (e.g., as might be the case for np.concatenate).
L228: This is one additional function of moderate complexity.
L229: 
L230:   2. Calling this function within all relevant NumPy functions.

Explaining broadcasting vs concatenation tradeoffs

concatenate is a structural copy operation, not an elementwise operation. NumPy defines broadcasting for operations that align input elements to one output shape, such as a + b. Concatenation instead places each input into a distinct slice of a new array, so NumPy requires those slices to already have the same shape on every non-concatenated axis. That is its documented contract. NumPy docs

Broadcasting here would be perfectly definable. For example:

a = np.arange(6).reshape(2, 3)
b = np.array([[9]])

np.concatenate([a, np.broadcast_to(b, (1, 3))], axis=0)
# [[0, 1, 2],
#  [3, 4, 5],
#  [9, 9, 9]]

But it would mean that concatenate silently repeats values while copying into its already-materialized result. Keeping that separate makes the allocation and repetition explicit, and keeps concatenation’s shape rule simple and predictable. broadcast_to() itself can be a zero-copy, read-only view, but concatenation must generally allocate and copy regardless. Broadcasting docs

Historically, this looks more like inherited API scope than a carefully recorded rejection. The old concatenate contract predates the public design record. A request to broadcast during concatenation was filed in NumPy’s old tracker on June 22, 2010, imported to GitHub in 2012, and never gained an implementation or substantive public rationale. Issue #2115

The convention has since solidified: the current Python Array API standard also requires equal shapes except along the joining axis. Array API concat

So the short answer is: no fundamental barrier, just a long-standing choice to keep “repeat to fit” separate from “join in sequence.”
